# Стандарты разработки и архитектура на языке C++

Этот модуль определяет архитектурные инварианты, требования к чистоте кода, практики численного моделирования, культуру комментирования и стандарты тестирования для проектов на C++ (стандарты C++17 / C++20).

Модуль действует как постоянный системный промпт для любой нейросети при создании, доработке или рефакторинге кода на C++.

---

## 1. Организация данных и структуры (`struct`)

1. **Группировка связанных данных:**
   - Не передавать множество разрозненных параметров в функции. Объединять физические свойства (геометрию, свойства флюида, коэффициенты) в именованные структуры (`struct`).
2. **Инициализация полей значением `NaN` (Fail Fast):**
   - Для полей типа `double` значением по умолчанию всегда является невалидное число:
     ```cpp
     struct pipe_geometry_t {
         double inner_diameter{std::numeric_limits<double>::quiet_NaN()};
         double length{std::numeric_limits<double>::quiet_NaN()};
         double roughness{std::numeric_limits<double>::quiet_NaN()};
     };
     ```
   - Запрещено использовать правдоподобные значения (`0.0`, `1.0`) в качестве умолчаний: неинициализированное поле обязано немедленно приводить к распространению `NaN` и падению проверок.
3. **Запрет позиционной агрегатной инициализации:**
   - Запрещена позиционная инициализация вида `pipe_geometry_t{0.1, 100.0, 1e-5}`.
   - Разрешено только явное поэлементное присваивание или designated initializers стандарта C++20:
     ```cpp
     pipe_geometry_t pipe{
         .inner_diameter = 0.1,
         .length = 100.0,
         .roughness = 1e-5
     };
     ```
4. **Исключение избыточных данных:**
   - В структурах хранятся только независимые исходные параметры. Производные величины (площадь сечения, объём) рассчитываются константными методами или свободными функциями.
5. **Строгие перечисления (`enum class`):**
   - Фиксированные наборы состояний, режимов или вариантов задаются через `enum class`. Элементы перечисления именуются в `snake_case`:
     ```cpp
     enum class flow_regime_t {
         laminar,
         transitional,
         turbulent
     };
     ```
6. **Фабричные методы для типовых наборов:**
   - Для структур параметров, многократно используемых в тестах, объявлять статические фабричные методы (например, `static pipe_geometry_t standard_pipe();`), чтобы тесты не захламлялись повторяющимися полотнами чисел.

## 2. Архитектурная модель «Параметры → Решатель → Результаты»

В вычислительных модулях и солверах логика строго разделяется на три компонента:

1. **Структура параметров (`*_params_t` / `*_properties_t`):** пассивные данные с валидацией инвариантов.
2. **Класс-решатель (`*_solver_t` / `*_calculator_t`):**
   - Конструктор — единственный способ задания исходных данных. Конструктор по умолчанию запрещен. Все аргументы сохраняются в приватных полях.
   - Решатель не хранит глобального состояния и выполняет вычисления методами `solve()`.
3. **Структура результатов (`*_result_t`):**
   - Результат сохраняется внутри решателя и отдается наружу через константный геттер `const result_t& get_result() const`.
   - Геттер обязан проверять факт выполнения расчета и бросать исключение при попытке получить результат до вызова `solve()`.

## 3. Классы, инкапсуляция и управление ресурсами (RAII)

1. **Приватность по умолчанию:**
   - Все поля данных и внутренние вспомогательные шаги алгоритмов объявляются в секции `private:`.
   - Публичными являются только конструктор, методы интерфейса расчета и геттеры результатов.
2. **Константная корректность:**
   - Все методы, не модифицирующие состояние объекта, обязательно помечаются `const`.
3. **RAII и управление памятью:**
   - Управление временем жизни объектов — исключительно через RAII и стандартные контейнеры (`std::vector`, `std::unique_ptr`, `std::shared_ptr`).
   - Деструктор используется только для освобождения ресурсов.
4. **Категорически запрещенные конструкции:**
   - Запрещены голые операции выделения и освобождения памяти: `new`, `delete`, `malloc`, `free`.
   - Запрещен `reinterpret_cast`.
   - Запрещено подавление предупреждений компилятора через `(void)parameter;`.
5. **Использование `auto`:**
   - Использовать `auto` только тогда, когда конкретный тип очевиден из правой части выражения (вызов конструктора, `std::make_unique`, `std::make_shared`, structured bindings `auto [val, ok] = ...`). В остальных случаях тип объявляется явно.

## 4. Обработка ошибок и исключения

1. **Физическая валидация входных данных:**
   - Входные параметры проверяются на физическую адекватность (диаметры $> 0$, плотность $> 0$, конечность `std::isfinite`).
2. **Inline `throw`:**
   - Исключения выбрасываются непосредственно в месте обнаружения ошибки: `throw std::invalid_argument("...");`.
   - Запрещено выносить выброс исключений в отдельные функции-обёртки (`throw_error()`, `fail()`).
3. **Содержательные сообщения:**
   - Текст исключения обязан содержать контекст: имя ошибочного параметра, недопустимое полученное значение и ожидаемый диапазон.

## 5. Численные методы и солверы

1. **Невязка как изолированная функция:**
   - Расчет невязки физического уравнения оформляется как независимый функтор, свободная функция или лямбда, отделенная от шага оптимизатора.
2. **Обобщенные алгоритмы решения:**
   - Численные алгоритмы (метод бисекции, метод Ньютона, метод секущих) реализуются как обобщенные шаблоны или функции высшего порядка, принимающие целевую функцию как аргумент.
3. **Множественные критерии остановки:**
   - Итерационные алгоритмы обязаны проверять:
     * Достижение допуска по аргументу: $|\Delta x| < \varepsilon_x$;
     * Достижение допуска по невязке: $|f(x)| < \varepsilon_f$;
     * Защиту от бесконечного зацикливания: лимит итераций ($N \le N_{\max}$).
4. **Численная производная:**
   - Для метода Ньютона обязательно предусматривать возможность численной аппроксимации производной (центральной или правосторонней разностью) при отсутствии аналитического выражения.

## 6. Полиморфизм и Объектно-Ориентированная Архитектура

1. **Абстрактные базовые классы:**
   - Интерфейс объявляется как класс с чисто виртуальными методами (`virtual void solve() = 0;`).
   - Базовый полиморфный класс обязан иметь виртуальный деструктор по умолчанию: `virtual ~solver_t() = default;`.
2. **Спецификатор `override`:**
   - Все методы наследников, переопределяющие виртуальные методы базового класса, обязаны помечаться ключевым словом `override`. Ключевое слово `virtual` у наследников опускается.
3. **Принципы SOLID:**
   - **OCP:** добавление новой математической модели осуществляется добавлением нового класса-наследника, а не ветвлением `switch/case` в существующем коде.
   - **LSP:** контракт базового класса должен безусловно выполняться любым наследником без изменения семантики.
   - **DIP:** оркестрирующие подсистемы зависят от абстракций (базовых интерфейсов), а не от конкретных деталей вычислителя.

## 7. Пространства имён и нейминг

1. **Соглашения по именованию:**
   - Переменные, функции, методы, параметры: `snake_case`.
   - Имена структур и классов: `snake_case` с суффиксом `_t` (например, `hydraulic_network_t`).
   - Тесты Google Test: `TEST(TestSuiteName, TestCaseName)` — `CamelCase` без подчеркиваний и транслита.
2. **Запрет `using namespace std;`:**
   - Категорически запрещено использовать директиву `using namespace std;` как в заголовочных, так и в `.cpp` файлах.
3. **Оформление пространства имён:**
   - Открывающая фигурная скобка объявляется на той же строке, а следующая строка содержит точку с запятой:
     ```cpp
     namespace core::solvers {
     ;

     // объявления

     } // namespace core::solvers
     ```
   - Тело пространства имен оформляется без дополнительного табуляционного отступа.

## 8. Комментарии и документация Doxygen

1. **Doxygen только в `.h`:**
   - Документирующие комментарии Doxygen (`///`, `@brief`, `@param`, `@return`) пишутся исключительно в заголовочных файлах `.h`.
   - Запрещено дублировать Doxygen в файлах реализации `.cpp`.
   - В многострочных комментариях Doxygen не делать лишних отступов после `///`:
     ```cpp
     /// @brief Рассчитывает гидравлические потери на трение по формуле Дарси-Вейсбаха.
     /// @param flow_rate Объемный расход жидкости, м³/с.
     /// @return Потери напора, м.
     double calc_friction_loss(double flow_rate) const;
     ```
2. **Внутренние комментарии в телах функций:**
   - Использовать краткие комментарии `//` только для объяснения неочевидной логики, численных трюков или обхода ограничений.
   - Запрещены разделители вида `// ********************`.
   - В комментариях писать сами математические формулы, а не абстрактные номера формул из методички.

## 9. Стандарты тестирования (Google Test)

1. **Структура Arrange / Act / Assert (AAA):**
   - Каждый тестовый кейс обязан содержать три явные секции с однострочными комментариями:
     ```cpp
     TEST(NewtonSolverTest, ReturnsRootForQuadraticEquation) {
         // Arrange: задаем целевую функцию x^2 - 4 = 0 и начальное приближение
         auto equation = [](double x) { return x * x - 4.0; };
         newton_solver_t solver{equation, 1.0e-7, 100};

         // Act: запускаем итерационный процесс с x0 = 3.0
         const auto result = solver.solve(3.0);

         // Assert: проверяем сходимость к значению 2.0
         ASSERT_TRUE(result.is_converged);
         EXPECT_NEAR(result.root, 2.0, 1.0e-6);
     }
     ```
   - Запрещено объединять секции Act и Assert в одном вызове (`EXPECT_TRUE(solver.solve().is_converged)`).
2. **Запрет оборачивания тестов в `namespace`:**
   - Макрос `TEST(...)` и тестовые фикстуры `TEST_F(...)` никогда не оборачиваются в `namespace`.
3. **Методы фикстур:**
   - Поскольку фикстуры не должны нести скрытого неявного состояния, вспомогательные методы в тестовых классах объявляются как `static` внутри тела класса.
4. **Неприкосновенность упавших тестов (поиск причин в коде, а не подгонка тестов):**
   - При падении теста в Google Test категорически запрещено ослаблять ассерты (`EXPECT_*`, `ASSERT_*`), изменять проверяемые эталонные значения или удалять проверки ради получения зеленого статуса сборки.
   - Агент обязан локализовать дефект и исправить его в исходном коде алгоритмов и солверов.
   - Если падение теста обусловлено осознанным изменением контракта или архитектуры, агент **обязан остановить работу и запросить явное разрешение пользователя** на корректировку теста с подробным обоснованием.
   - Любое изменение тестов в ситуации падения требует предельной осторожности и обязательного согласования с пользователем.

## 10. Сборка и структура репозитория

1. **Синхронизация с CMake:**
   - При добавлении, переименовании или удалении файлов `.h`/`.cpp` незамедлительно обновлять списки исходников в `CMakeLists.txt`.
   - Переименование и перемещение файлов выполнять строго через `git mv`.
2. **Чистота репозитория:**
   - В git коммитить только исходный код, тесты, манифесты сборки и markdown-документацию.
   - Никаких скомпилированных библиотек, `.exe`, `.obj`, `.pdb` или временных файлов IDE.

---

## 11. Абсолютные запреты («Никогда»)

1. Реализовывать не согласованную архитектуру или функциональность «на будущее».
2. Инициализировать поля `double` правдоподобными нулями вместо `NaN`.
3. Использовать позиционную инициализацию структур вместо designated initializers.
4. Использовать директиву `using namespace std;`.
5. Использовать сырое ручное управление памятью (`new`, `delete`, `malloc`).
6. Писать тесты без разделения на секции Arrange, Act, Assert.
7. Оборачивать макрос `TEST(...)` в `namespace`.
8. Нарушать физическую монотонность замыкающих соотношений в солверах.
9. Дублировать комментарии Doxygen в `.cpp` файлах.
10. Коммитить скомпилированные бинарники и артефакты сборки.
11. Изменять или ослаблять упавшие тесты ради искусственного прохождения сборки без прямого предварительного разрешения пользователя.
