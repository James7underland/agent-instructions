# Моделирование и разработка в Simulink (Model-Based Design, SATK)

Этот модуль определяет архитектурные принципы, регламент взаимодействия с моделями Simulink через агентный инструментарий (Simulink Agentic Toolkit, SATK), стандарты топологии, правила неразрушающей симуляции и методологию верификации в парадигме модельно-ориентированного проектирования (Model-Based Design, MBD).

Модуль действует как системный промпт для любой нейросети при анализе, создании, модификации, настройке и тестировании моделей Simulink, Stateflow, Simscape и System Composer.

---

## 1. Архитектура агентного взаимодействия с Simulink

Взаимодействие нейросети со средой Simulink строится по трехзвенной схеме:

```
┌───────────────────────┐         ┌──────────────────────────┐         ┌────────────────────────┐
│       AI Agent        │ ◄─MCP─► │        MCP Server        │ ◄────── │    MATLAB / Simulink   │
│  (Claude, Antigravity,│         │ (matlab-mcp-core-server) │ ──────► │ (R2023a+, satk_init,   │
│   Cursor, Copilot)    │         └──────────────────────────┘         │   shareMATLABSession)  │
└───────────────────────┘                                              └────────────────────────┘
            ▲
            │ использует
┌───────────────────────┐
│     MBD-инструкции    │
│  (модуль и стандарты) │
└───────────────────────┘
```

1. **Разделение возможностей (Tools) и инженерных навыков (Skills):**
   - **MCP-инструменты** предоставляют агенту технический доступ к модели (чтение топологии, добавление блоков, соединение сигналов, запуск симуляции).
   - **Инженерные инструкции** определяют семантическую корректность: правила трассировки сигналов, согласование типов данных, предотвращение алгебраических петель, выбор решателя и требования стандартов.
2. **Сессионный режим работы:**
   - Инструменты работают с запущенным процессом MATLAB через флаг `--matlab-session-mode=existing`.
   - Перед вызовом инструментов в командном окне MATLAB должна быть выполнена инициализация:
     ```matlab
     satk_initialize
     ```
     Функция регистрирует пути к утилитам тулкита, публикует сессию через `shareMATLABSession` и выполняет проверку окружения `validate_installation`.
3. **Окружение Windows:**
   - Процесс MCP-сервера требует сохранения переменной окружения `WINDIR`. При ее отсутствии запуск внутренних утилит Simulink блокируется операционной системой.

## 2. Абсолютные инженерные правила и ограничения (Guardrails)

1. **Запрет ручной сборки путей блоков из строк:**
   - Имена блоков в Simulink могут содержать невидимые символы переноса строк (`\n`), косые черты (`/`) и концевые пробелы. Ручная конкатенация строк вида `[model '/' name]` приводит к ошибкам в `get_param`, `set_param` и `hilite_system`.
   - **Обязательное правило:** адресация блоков выполняется исключительно через числовой идентификатор `SID` (Source Identifier), извлекаемый из дескриптора `blk_X`:
     ```matlab
     % Для blk_42 числовой SID равен 42
     blockFullName = Simulink.ID.getFullName('ModelName:42');
     set_param(blockFullName, 'Gain', '2.5');
     ```
2. **Запрет ручного позиционирования и вызова `arrangeSystem`:**
   - Инструмент `model_edit` содержит встроенный движок автотрассировки и размещения блоков.
   - Запрещено вычислять координаты вручную или вызывать `Simulink.BlockDiagram.arrangeSystem`, если об этом прямо не попросил пользователь.
   - При каждом вызове `model_edit` передается параметр `layout_mode`:
     - `"full"` — при построении диаграммы с нуля или наполнении пустой подсистемы;
     - `"incremental"` — при добавлении компонентов в уже существующую диаграмму (сохраняет координаты остальных блоков).
3. **Правило одного скоупа на вызов `model_edit`:**
   - За один вызов модифицируется только один уровень иерархии (корневой уровень `scope="root"`, подсистема `scope="blk_X"` или чарт `scope="sf_X"`).
   - Нельзя смешивать создание блоков на верхнем уровне и подключение портов внутри создаваемой подсистемы в рамках одной операции.
4. **Двухшаговый протокол для Stateflow:**
   - Шаг 1: Создание блока `Chart` на уровне Simulink (`scope="root"` или подсистема).
   - Шаг 2: Вызов `model_read` для определения идентификатора конечного автомата `sf_X`.
   - Шаг 3: Наполнение состояний, переходов и функций в скоупе `scope="sf_X"`.
5. **Защита от бесконечной симуляции (Deadlock Prevention):**
   - Перед любым вызовом симуляции (`sim()`, `parsim`, `model_test`) агент обязан проверить параметр `StopTime`.
   - **Категорически запрещено запускать симуляцию с `StopTime = 'inf'` или незаданным временем.** Это намертво блокирует рабочий поток MATLAB. При обнаружении `'inf'` время обязательно переопределяется конечным значением (например, `StopTime = '10'`).
6. **Запрет обхода инструментов через `eval`:**
   - Запрещено использовать `evaluate_matlab_code` для прямого вызова `add_block` / `set_param` в целях изменения структуры модели. Это ломает историю транзакций, отключает автолейаут и лишает агент диагностики целостности.
7. **Открытие моделей для визуального контроля:**
   - Модели открываются командой `open_system`, а не фоновой `load_system` (за исключением библиотек компонентов). Пользователь должен видеть вносимые изменения в реальном времени.
8. **Безопасные имена для генерации кода:**
   - Имена блоков, сигналов, портов и состояний должны удовлетворять стандарту C/C++ идентификаторов: латинские символы `[a-zA-Z]`, цифры `[0-9]`, знак подчеркивания `_`.
   - Имя не может начинаться с цифры, содержать пробелы, спецсимволы и идущие подряд подчеркивания `__`. Рекомендуемая длина – до 31 символа.
9. **Кодировка `windows-1251` (CP1251) для скриптов с русским текстом:**
   - Все файлы сценариев автоматизации `.m`, создающие или аннотирующие модели Simulink с кириллическими именами подсистем, блоков, сигналов или выносных надписей, обязаны сохраняться в кодировке `windows-1251`. Сохранение в UTF-8 на русскоязычных Windows приводит к моджибейку (нечитаемым кракозябрам) внутри блоков Simulink в версиях MATLAB до R2020b.
10. **Очистка автогенерируемых портов в создаваемых подсистемах:**
   - Команда `add_block('simulink/Ports & Subsystems/Subsystem', ...)` автоматически создает внутри пустой подсистемы стандартные блоки `In1` и `Out1`. При создании специализированных блоков (например, подсистем расчета ошибки или времени регулирования) неиспользуемые порты по умолчанию должны явно удаляться через `delete_block([sys '/In1'])`, чтобы исключить появление «висячих» незадействованных портов в левом верхнем углу схемы.
11. **Прямая направленная трассировка сигналов внутри подсистем (слева направо):**
   - Входные порты `Inport` обязаны позиционироваться строго левее функциональных блоков (`Abs`, `Square`, `Integrator`), обеспечивая естественное направление потока сигналов слева направо без обратных петель (loopback) вокруг блоков.
12. **Разнесение элементов обратной связи:**
   - В схемах фиксации (например, защелках времени регулирования на блоках `Memory` и `Switch`) блоки обратной связи разводятся по вертикали, а сигнальная линия обратной связи должна огибать блок переключателя `Switch` снизу, предотвращая взаимное наложение блоков и линий.

## 3. Матрица и спецификация MCP-инструментов

Набор инструментов предоставляет полный цикл наблюдения, изменения и верификации моделей:

| Инструмент | Тип операции | Назначение | Ключевые параметры |
|---|---|---|---|
| `model_overview` | Чтение | Быстрый аудит иерархии модели и связей между подсистемами | `model`, `scope` (`root` или `blk_X`), `detail` (`tree`, `interfaces`, `full`) |
| `model_read` | Чтение | Топология блоков и семантика формул в скоупе | `model`, `scope`, `depth` (`0`, `1`, `inf`) |
| `model_query_params` | Чтение | Прямой опрос параметров блоков, сигналов и конфигурации решателя | `model`, `targets` (JSON-массив `blk_X`, `config:Model`), `params`, `compile` |
| `model_resolve_params` | Чтение | Разрешение переменных рабочего пространства (`Kp`) в числа | `model`, `expressions` (JSON-массив имен переменных) |
| `model_scan` | Чтение | Быстрый regex-поиск по сохраненному файлу `.slx` на диске (<100мс) | `model`, `command` (`grep`), `pattern` |
| `model_edit` | Запись | Атомарное изменение структуры, портов, параметров и логики Stateflow | `model`, `scope`, `operations` (однострочный JSON), `layout_mode` |
| `model_check` | Валидация | Поиск неподключенных портов, оборванных линий и линтинг Stateflow | `model`, `scope`, `checks` (`["all"]`, `unconnected_ports`, `unconnected_lines`, `stateflow_lint`) |
| `model_read_diagnostics` | Чтение | Чтение ошибок и предупреждений компилятора из Diagnostic Viewer | `model`, `severity`, `scope`, `detail` |
| `model_test` | Тест | Запуск поведенческих тестов по Gherkin-спецификации | `model`, `gherkin_file`, `scenarios`, `draft_mode`, `coverage` |

## 4. Регламент структурного редактирования (`model_edit`)

### 4.1. Формат и нотация выражений `model_read`

При чтении диаграммы через `model_read` алгоритмическая суть блоков представляется математическими выражениями:
- `uN(source)` — входной порт с номером $N$ и указанием источника сигнала в скобках;
- `yN` — выходной порт с номером $N$;
- `@Param(value)` — параметр блока с текущим значением.

Пример:
```
y1 = @Gain(Kp) * u1(blk_4.y1)
```
Выходной сигнал 1 равен произведению параметра `Gain` (ссылающегося на переменную `Kp`) на сигнал с выхода 1 блока `blk_4`.

### 4.2. Операции в `model_edit`

Массив операций `operations` передается строго в одну строку без символов переноса:

1. **Добавление блока (`add_block`):**
   ```json
   {"op": "add_block", "type": "Gain", "name": "Gain_Velocity", "ref": "g1", "params": {"Gain": "2.0"}}
   ```
   *Типы блоков:* для стандартных блоков используется базовый `BlockType` (`Gain`, `Sum`, `Integrator`, `Inport`, `Outport`, `SubSystem`, `Scope`, `Constant`). Для библиотечных блоков передается точное отображаемое имя (`Voltage Source`, `PID Controller`).
2. **Связывание портов (`connect`):**
   - Сигнальные порты Simulink: `blk_X.y1 -> blk_Y.u1` (где `y` — выход, `u` — вход).
   - Физические порты Simscape: `blk_X.portName <-> blk_Y.portName` (двунаправленная связь).
   - Переходы Stateflow: `#srcState -> #dstState` (без номеров портов).
   - Начальный переход Stateflow: `? -> #targetState`.
3. **Отключение связей (`disconnect`):**
   ```json
   {"op": "disconnect", "target": "blk_3.y1 -> blk_7.u1"}
   ```
4. **Конфигурация параметров (`configure`):**
   - Настройка блока: `target="blk_X"`, `params={"Gain": "10.5"}`.
   - Настройка решателя модели: `target="config:ModelName"`, `params={"Solver": "ode45", "StopTime": "20"}`.
   - Настройка чарта Stateflow: `target="chart:ModelName"`, `params={"ActionLanguage": "MATLAB"}`.
5. **Замена блока (`replace_block`):**
   Замена существующего блока с сохранением позиции, имени и внешних подключений.
6. **Удаление (`delete`):**
   Удаление блока по идентификатору `target="blk_X"`.
7. **Создание подсистемы (`create_subsystem`):**
   ```json
   {"op": "create_subsystem", "name": "Plant_Dynamics", "ref": "sub1", "interface": {"inputs": ["Torque"], "outputs": ["Speed", "Angle"]}}
   ```

### 4.3. Цепочки ссылок внутри одного вызова (`ref` и `#ref`)

При добавлении группы блоков в рамках одного запроса для связи новых блоков между собой используется имя ссылки с префиксом `#`:

```json
[
  {"op": "add_block", "type": "Constant", "name": "TargetSpeed", "ref": "c1", "params": {"Value": "100"}},
  {"op": "add_block", "type": "Sum", "name": "ErrorCalc", "ref": "s1", "params": {"Inputs": "|+-"}},
  {"op": "connect", "target": "#c1.y1 -> #s1.u1"},
  {"op": "connect", "target": "blk_2.y1 -> #s1.u2"}
]
```

Ответ инструмента содержит карту `created: {"c1": "blk_15", "s1": "blk_16"}`. В последующих вызовах обязательно используются присвоенные идентификаторы `blk_X`.

## 5. Специфика доменов: Stateflow, Simscape и System Composer

### 5.1. Редактирование автоматов Stateflow

Внутренности Stateflow редактируются через `model_edit` в скоупе `sf_X`:
- **Элементы:** `type="State"`, `type="Junction"`, `type="Data"`, `type="Event"`, `type="EMFunction"` (функция MATLAB).
- **Синтаксис перехода:** `target="#StateA -> #StateB"`.
- **Свойства перехода:** `params={"LabelString": "[speed > 80] / alarm = 1;", "ExecutionOrder": 1}`.
- **Обязательный аудит:** после каждого изменения Stateflow запускается проверка линтером:
  ```matlab
  model_check(model="ModelName", checks='["stateflow_lint"]', scope="blk_ChartID")
  ```

### 5.2. Физическое моделирование в Simscape

- Физические консервативные соединения обозначаются синтаксисом `<->`.
- В каждой изолированной физической сети обязателен блок `Solver Configuration` и соответствующий опорный узел (`Electrical Reference`, `Mechanical Rotational Reference`).
- Перед симуляцией или экспортом данных рекомендуется отключать глобальное логирование Simscape, если не требуется детальный физический аудит:
  ```matlab
  set_param('ModelName', 'SimscapeLogType', 'none');
  ```

### 5.3. Системная архитектура в System Composer

- Создание модели выполняется через `systemcomposer.createModel`.
- Компоненты создаются через `type="SubSystem"`, интерфейсные порты — через блоки шин (`Bus Element`).

## 6. Неразрушающая симуляция и вычислительные эксперименты

Для проведения симуляций, исследования устойчивости, оптимизации параметров и подбора регуляторов применяется объектный интерфейс `Simulink.SimulationInput`. Изменять файл `.slx` на диске ради промежуточных расчетов запрещено.

### 6.1. Базовый шаблон симуляции

```matlab
% Инициализация объекта без изменения файла модели
in = Simulink.SimulationInput('ModelName');

% Установка параметров модели
in = in.setModelParameter('StopTime', '15', 'SolverType', 'Variable-step', 'Solver', 'ode45');

% Переопределение параметров конкретного блока (по SID)
in = in.setBlockParameter(Simulink.ID.getFullName('ModelName:12'), 'Gain', '3.14');

% Переопределение переменной рабочего пространства
in = in.setVariable('Kp_Speed', 2.5);

% Запуск расчета
out = sim(in);
```

### 6.2. Подача входных сигналов через Dataset

Входные воздействия формируются через объект `Simulink.SimulationData.Dataset` и привязываются к корневым портам `Inport` по порядковому номеру:

```matlab
timeVec = (0:0.01:10)';
signalData = sin(2*pi*0.5*timeVec);

ts = timeseries(signalData, timeVec);
ds = Simulink.SimulationData.Dataset;
ds{1} = ts; % сигнал для первого Inport

in = in.setExternalInput(ds);
out = sim(in);
```

### 6.3. Сбор и анализ результатов

Логированные сигналы извлекаются из структуры `out.logsout`:

```matlab
% Проверка доступных сигналов
signalNames = out.logsout.getElementNames();

% Извлечение значений по имени сигнала
speedSignal = out.logsout.get('MotorSpeed').Values;
t = speedSignal.Time;
y = speedSignal.Data;

% Проверка стационарного значения или перерегулирования
overshoot = (max(y) - y(end)) / y(end) * 100;
```

## 7. Верификация, валидация и тестирование (V&V)

В тулките реализовано два взаимодополняющих подхода к тестированию:

### 7.1. Быстрое декларативное тестирование (Gherkin / `model_test`)

Используется в цикле агентной разработки для мгновенной валидации требований и проверки отсутствия регрессий без сохранения тяжелых артефактов.

Файл `.feature` состоит из front-matter заголовка в формате TOML и сценариев:

```gherkin
# --- front-matter:toml ---
model = "MotorController.slx"
component = "MotorController/SpeedControl"
[inputs]
TargetSpeed = "TargetSpeed"
MeasuredSpeed = "MeasuredSpeed"
[outputs]
MotorVoltage = "MotorVoltage"
# --- end front-matter ---

Feature: Регулирование скорости вращения при ступенчатом воздействии
  Проверка отсутствия перерегулирования выше 10% и времени установления.

  Scenario: Разгон до 100 рад/с
    Given inputs
      * TargetSpeed = step(0 -> 100 @ 0.5s)
      * MeasuredSpeed = const(0)
    When simulate for 5s in Normal mode
    Then outputs
      * VoltageLimit: MotorVoltage <= 24
      * PositiveDrive: MotorVoltage >= 0
      * Settled: MotorVoltage < 5 when t > 4s
```

**Режим быстрой разработки (`draft_mode`):**
При отладке сценариев передается `draft_mode="true"` (~3 секунды на итерацию за счет облегченного харнеса без полной компиляции главной модели). После успешного прогона тест запускается в полном режиме `draft_mode="false"` для проверки реальных типов и размерностей сигналов.

### 7.2. Перманентные тесты Simulink Test

Для задач сертификации, формальной сдачи проекта и сквозной прослеживаемости требований:
- Тест-кейсы сохраняются в файлы `.mldatx`.
- Связываются с требованиями Requirements Toolbox (`.slreqx`).
- Запуск осуществляется через `test_run` с оценкой полноты тестового покрытия (Decision, Condition, MCDC через `Simulink Coverage`).

### 7.3. Чтение системных диагностик

После обновления диаграммы или симуляции любые подозрения на ошибки проверяются вызовом `model_read_diagnostics`:
```matlab
% Проверка ошибок компиляции
model_read_diagnostics(model="ModelName", severity="error", scope="root")
```

## 8. Чек-лист проверки и сдачи модели

Перед завершением задачи агент обязан последовательно выполнить аудит:

1. **Структурная целостность:** выполнен вызов `model_check` со скоупом `root` — отсутствуют неподключенные порты (`unconnected_ports`) и висячие линии (`unconnected_lines`).
2. **Компилируемость:** вызвана пробная компиляция диаграммы (Update Diagram) — вызов `model_read_diagnostics` возвращает пустой список ошибок.
3. **Параметризация:** все коэффициенты регуляторов, массы, сопротивления и допуски вынесены в переменные (`Model Workspace` или init-скрипт); отсутствуют магические безымянные константы.
4. **Безопасность симуляции:** параметр `StopTime` имеет строго конечное положительное значение; шаг решателя (при дискретном расчете) синхронизирован по всей цепочке.
5. **Чистота и автолейаут:** сохранена визуальная читаемость без пересечений соединительных линий.
