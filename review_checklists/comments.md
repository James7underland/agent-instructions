## Чек-лист Комментарии

> Этот документ используется при проверке студенческих работ. Нарушения помечаются как замечания к качеству кода.

> [!IMPORTANT]
> **Языковая специфика (C++ vs Python и другие языки):**
> Требования ниже (включая формат `///`, теги `@brief`, `@param`, `@return`, разделение на `.h` и `.cpp`) изначально создавались под разработку на C++.
> Если проект или скрипт пишется на другом языке (например, **Python**), механический перенос C++-конструкций запрещен. В Python действуют общепринятые практики языка: стандартные docstrings (PEP 257 в Google/Sphinx-стиле без `@brief` и собачек) для функций/модулей/классов и комментарии `#` внутри кода. Из этого чек-листа берутся только инварианты смысла: комментировать неочевидные решения, алгоритмы и физические ограничения («зачем»), а не пересказывать очевидный код.


### Обязательные требования

- **Каждая функция должна иметь Doxygen-комментарий перед объявлением.**
  - **Формат:** `///` (автогенерация в Visual Studio).
  - **Где:** перед *объявлением* функции (прототипом) или перед определением, если прототипа нет. Если есть сигнатура функции и комментарий к ней в .h, нельзя его дублировать в .cpp, иначе придется поддерживать две версии комментария
  - **Что должно быть внутри:**
    - `@brief` — кратко: что делает функция и **зачем**. 
    - `@param` — Не обязательно, если из краткого описания функции и нейминга переменной параметр очевиден. Что можно описать из неочевидного: смысл, единицы измерения (если не СИ), ограничения на ожидаемый диапазон (если есть)
    - `@return` — что возвращает (для `void` можно опустить). Не обязательно, если из краткого описания функции и нейминга переменной параметр очевиден.

- **Каждая структура и класс должна иметь Doxygen-комментарий перед объявлением.**
  - **Формат:** `///` (автогенерация в Visual Studio).
  - **Что должно быть внутри:**
    - `@brief` — кратко: общее назначение класса в целом.

Пример:

```cpp
/// @brief Вычисляет площадь круга по заданному радиусу. (Задача Begin5)
/// @param radius Радиус круга (должен быть неотрицательным).
/// @return Площадь круга (вещественное число).
double calculate_circle_area(double radius);
```
### Правила внутри функций 

- **Doxygen-комментарии внутри тела функции не используются.**
  - **Разрешено:** обычные `//` комментарии для пояснения нетривиальных мест (алгоритм, формула, причины проверок/ветвлений).

- **Допустимо (точечно):** локальную переменную можно кратко пояснить в той же строке, **если она входит в ~20% ключевых для понимания функции**.
  Пример:
```cpp
double head_loss = ...; // потери напора на участке, м
```

### Правила для тестов 
- Если функция является тестом TEST(TestSuite, TestCase), то doxygen-комментарий к сигнатуре функции
должен по-русски формулировать то же самое, что заложено в TestSuite, TestCase (см. naming.md строго в части именования тестов и только). 
Рекомендуемая формулировка проверяет способность (того-то - тестируемой подсистемы SUT, указанной в TestSuite) сделать то-то (русская формуликровка TestCase).
- Внутри тела теста обязательно пишутся блоки Arrange, Act, Assert - должно быть понятно, какие действия к какой фазе теста относятся.

### Типовые причины снижения оценки (примеры нарушений)

- **Нет Doxygen перед функцией** или отсутствуют `@param`/`@return`.
- **`@param` без смысла и ограничений:** “вводимое значение” вместо “давление, Па; \(p \ge 0\)”.
- **Комментарии “пересказывают код”** вместо обдуманного краткого объяснения смысла/ограничений/формул.
