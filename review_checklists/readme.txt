ВАЖНО: ЦЕЛЕВОЙ ЯЗЫК ПРОГРАММИРОВАНИЯ И АДАПТАЦИЯ К ДРУГИМ ЯЗЫКАМ
=====================================================================
Все кубики и инструкции в этой папке (code_review_prompts/), а также общие правила проектирования кода в библиотеке agentic изначально создавались под разработку на языке C++ (комментарии Doxygen с тройным слэшем `///`, разделение на заголовочные файлы `.h` и файлы реализации `.cpp`, структуры и классы с суффиксом `_t`, Google Test и т.д.).

Если код пишется на другом языке программирования (например, Python):
1. Учитывай специфику целевого языка:
   Категорически запрещено механически переносить C++-конструкции в другой язык. 
   - Нельзя требовать Doxygen-комментарии (`///`, `@brief`, `@param`, `@return`) в Python: в Python используются стандартные docstrings (PEP 257 / Google / Sphinx стиль) и однострочные комментарии `#`.
   - Нельзя требовать C++-нейминг или синтаксические соглашения там, где у языка есть собственный общепринятый стандарт (например, PEP 8 для Python).
2. Бери из этих правил только язык-независимые инженерные инварианты:
   Применяй только те фундаментальные принципы, которые актуальны для целевого языка:
   - Принцип DRY и отсутствие дублирования;
   - Бритва Оккама (не плодить сущности сверх необходимого);
   - Осмысленность имен переменных и функций (самодокументируемый код);
   - Отсутствие "мертвого" кода и отладочных артефактов;
   - Чистота и логичность архитектурного разделения ответственности.
3. Опирайся на общеизвестные наилучшие практики (Best Practices):
   При разработке и ревью необходимо задействовать наилучшие практики для конкретного языка — не только те, что зафиксированы в библиотеке agentic, но и в целом общеизвестные в индустрии:
   - Для Python: следование стандартам PEP 8, PEP 257, аннотациям типов (type hints, PEP 484), использование контекстных менеджеров (`with`), идиоматичных генераторов и стандартных библиотек.
   - Следование общепринятым практикам тестирования (pytest / unittest).

СТРУКТУРА И ПРИНЦИП ПРОВЕРКИ
=====================================================================
Есть "кубики" проверки типа comments.md, naming.md, dry.md.

Для каждой лабы мы собираем проверку из разных кубиков. Например, не всегда уже рассказали про комментарии, пока есть только требования к неймингу. Пока не рассказали структуры, не выдвигаем требования использовать структуры и так далее.

Есть общий принцип проверки кода с учетом заданных проверок. Тут два варианта:
- общий, чтобы студент еще подумал над указанными недостатками (review_rules.md). Типовые ошибки указываются в духе "проработай такой-то аспект, вот тебе пример, остальное найди и исправь сам". Не надо раскрывать сразу все исправления.
- детальный — полная проверка всех проблем, чтобы оценить, насколько качественно проработан код (review_rules_detailed.md).

Файлы эти студентам не передаем, даем только выдачу (report*.md). Человек должен сам уметь составить такие правила, чтобы автоматизировать заданные проверки. Это честно.
