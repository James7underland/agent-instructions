# Каталог универсальных чек-листов для код-ревью

В этой папке собраны модульные инженерные критерии («кубики») и правила для проверки исходного кода на C++ и Python. Они подключаются через основной модуль [`../code_review.md`](../code_review.md).

---

## 1. Режимы проведения проверки

Перед началом ревью выбирается один из трех регламентов в зависимости от цели:

| Файл режима | Назначение режима | Ключевой подход |
|---|---|---|
| [`review_rules.md`](review_rules.md) | **Обучающий (наставнический)** | Выявление категорий проблем и иллюстрация одной типичной ошибкой. Студент находит и исправляет остальные места самостоятельно. |
| [`review_rules_detailed.md`](review_rules_detailed.md) | **Детальный аудит (полная приемка)** | Исчерпывающий статический анализ всех обнаруженных дефектов со структурированием по файлам и уровням критичности. |
| [`review_rules_production.md`](review_rules_production.md) | **Production / Pull Request** | Анализ строго в пределах измененных файлов текущего MR (`git diff origin/main...HEAD`). |

## 2. Адаптация требований к целевому языку (C++ vs Python)

Правила и критерии проектирования изначально формулировались с учетом специфики C++ (Doxygen `///`, суффиксы типов `_t`, разделение `.h`/`.cpp`, Google Test). 

При проверке кода на Python действует строгий регламент языковой адаптации:
1. **Запрет механического переноса C++ синтаксиса:**
   - Не требовать Doxygen (`///`, `@brief`, `@param`) — в Python используются docstrings `"""` (PEP 257) и комментарии `#`;
   - Не требовать C++ нейминг (суффиксы `_t`) там, где действуют стандарты PEP 8;
   - Не требовать ручного управления памятью или разделения на заголовочные файлы.
2. **Язык-независимые инженерные инварианты:**
   - Принцип DRY (отсутствие дублирования кода);
   - Бритва Оккама (минимизация сущностей и уровней абстракции);
   - Самодокументируемый код и осмысленность имен;
   - Отсутствие неиспользуемого «мертвого» кода и отладочных артефактов;
   - Чистота и логичность архитектурного разделения ответственности.
3. **Опора на наилучшие практики языка (Best Practices):**
   - Для Python: следование PEP 8, PEP 257, аннотациям типов (PEP 484/585/526), контекстным менеджерам `with`, `dataclass(kw_only=True)`, pytest;
   - Для C++: следование RAII, `enum class`, designated initializers (C++20), Google Test.

## 3. Принцип гибкой комплектации проверки

Проверка собирается из специализированных кубиков под конкретную задачу и уровень подготовки:
- **Архитектура классов и структур:** [`structs.md`](structs.md), [`rule_of_7.md`](rule_of_7.md);
- **Надежность, чистота и качество:** [`tests.md`](tests.md), [`dry.md`](dry.md), [`calcs.md`](calcs.md), [`duplicates_occams_razor.md`](duplicates_occams_razor.md);
- **Стиль и оформление:** [`naming.md`](naming.md), [`comments.md`](comments.md), [`namespace.md`](namespace.md);
- **Чистота репозитория:** [`restrict_binary.md`](restrict_binary.md).

## 4. Универсальные кубики инженерного качества

| Файл кубика | Проверяемый аспект | Ключевые требования |
|---|---|---|
| [`naming.md`](naming.md) | **Именование сущностей** | `snake_case` для функций и переменных, суффикс `_t` для C++ типов, отсутствие транслита, CamelCase только для Google Test. |
| [`comments.md`](comments.md) | **Документирование и комментарии** | Doxygen (`///`, `@brief`) в `.h` для C++, docstring `"""` для Python, комментарии только по неочевидной логике, формулы вместо абстрактных ссылок, размерности величин. |
| [`structs.md`](structs.md) | **Структуры данных и инкапсуляция** | Инициализация полей `NaN` (Fail Fast), designated initializers (C++20) / `kw_only` (Python), производные величины через const-методы/@property, бессистемные вычисления свободными функциями, статические фабрики. |
| [`namespace.md`](namespace.md) | **Пространства имен и модули** | Запрет `using namespace std;`, точка с запятой `;` после открывающей скобки `{` пространства имен, логическая изоляция подсистем. |
| [`calcs.md`](calcs.md) | **Физико-математические константы** | Использование `M_PI`, единая именованная константа ускорения свободного падения $g$, устранение магических чисел. |
| [`tests.md`](tests.md) | **Структура и культура тестов** | Паттерн AAA (Arrange / Act / Assert), запрет оборачивания `TEST` в `namespace`, вынос повторяющихся тестовых данных, обязательный тест эталонного расчета (Golden Master). |
| [`dry.md`](dry.md) | **Принцип Don't Repeat Yourself** | Вынос повторяющихся вычислений и валидаций в хелперы, переиспользование базовых классов через `super()`. |
| [`duplicates_occams_razor.md`](duplicates_occams_razor.md) | **Бритва Оккама и устранение дублей** | Осознанное разделение вариативных AAA-матриц сценариев и реального неоправданного дублирования логики. |
| [`rule_of_7.md`](rule_of_7.md) | **Когнитивная сложность ($7 \pm 2$)** | Метрики сложности классов (A/B/C), ограничение количества полей и методов (не более 7), декомпозиция крупных сущностей. |
| [`restrict_binary.md`](restrict_binary.md) | **Чистота репозитория** | В git коммитятся только исходники и текст, запрет сборных бинарников, исполняемых файлов и артефактов IDE. |
