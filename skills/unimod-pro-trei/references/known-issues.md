# Unimod PRO 2 — грабли и ограничения

Правило: любая ошибка, «сломанный после правки файл», неожиданное поведение IDE —
фиксируется здесь СРАЗУ, даже если причина не до конца понятна.

## Проверенные грабли (все воспроизведены экспериментально 2026-09-08)

### Удаление или правка `tags/global.var` уничтожает глобальный словарь
- Что делали: удалили `tags/global.var` в проекте с 333 глобальными переменными,
  открыли проект и сохранили.
- Что произошло: ошибок IDE не показала, но `global.csv` и `base.csv` были
  перезаписаны одной строкой шапки. Все переменные потеряны.
- Вывод: `global.var` — единственный источник истины. `global.csv` IDE **не читает
  никогда**, только перезаписывает. Правка `global.csv` бессмысленна и опасна:
  создаёт иллюзию, что переменные есть.

### Правка `prog.st` не работает — файл затирается
- Что делали: дописали строку в `tasks/main/MB_write/prog.st`, открыли проект,
  сохранили.
- Что произошло: правка исчезла, `prog.st` восстановлен из base64 в `prog.json`.
- Вывод: `prog.st`, `types/*.st`, `*.csv` — генерируемые зеркала. Код правят
  ТОЛЬКО в `text.st` (base64) соответствующего JSON.

### Перенос `prog.var` в `tags/global.var` не работает
- Что делали: скопировали готовый локальный словарь (3 переменные) поверх
  `tags/global.var`.
- Что произошло: проект открылся без ошибок, глобальный словарь пуст.
- Вывод: формат `umvar` контекстно-зависим, «пересадка» словарей невозможна.

### Глобальный словарь нельзя импортировать файлом
- Что делали: положили в корень `global.import.csv`, `tags.import.csv`,
  `Глобальный словарь.import.csv`.
- Что произошло: ни один файл не был потреблён, словарь пуст.
- Вывод: авто-импорт `*.import.csv` работает **только для локальных словарей
  программ** и файл должен называться `<имя_программы>.import.csv`.
  Глобальный словарь — только через GUI.

### `import.prj` и `*.import.csv` в одном заходе дают ошибку
- Что делали: положили одновременно `import.prj` (создаёт `prog_a`) и
  `prog_a.import.csv` (словарь для `prog_a`).
- Что произошло: третьим окном вылезло «Ошибка», объекты не создались.
- Вывод: импорт словаря выполняется раньше импорта структуры, поэтому программы
  ещё не существует. Делать в ДВА захода: сначала `import.prj` (открыть,
  подтвердить, сохранить, закрыть), потом `*.import.csv`.

### Импорт локального словаря обнуляет колонку Attribute
- В локальном словаре программы атрибут доступа не применяется — при импорте
  любое значение приводится к `0`. Это по документации: атрибут задаётся только
  в словаре данных структуры.
- **Исключение — дочерняя программа** (проверено 2026-09-12): в
  `<дочерняя>.import.csv` `Attribute` сохраняется — `1` = «Вход», `2` =
  «Выход». Так и задаются её параметры.

### `<программа>.import.csv` ЗАМЕНЯЕТ локальный словарь целиком
- Что делали (2026-09-12): в `s2_lab` положили `sim_main.import.csv` с двумя
  новыми переменными, рассчитывая дописать их к существующим 24.
- Что произошло: после открытия и сохранения в словаре остались **только**
  эти две. `PI2`, `init_done`, экземпляр `t1` и остальные исчезли, сборка —
  5 ошибок «Ошибка 19: Неизвестное выражение или идентификатор». В «Выводе»
  при этом спокойное «Словарь программы sim_main была обновлен из файла
  импорта».
- У дочерней программы то же самое, но незаметно: защищённая выходная
  переменная (одноимённая с программой) остаётся **как была** — строка с её
  именем в импорте игнорируется, тип из импорта не применяется.
- Правило: в `*.import.csv` всегда класть **полный** словарь — старые строки
  из `prog.csv` + новые. Для экземпляра структуры достаточно строки `Type=U`,
  поля `<экземпляр>.<поле>` IDE развернёт сама (проверено: так словарь и
  восстановили). Перед импортом — копия проекта.

### Модальные диалоги блокируют открытие проекта
- При наличии `import.prj` / `*.import.csv` / `prog.import.st` IDE на старте
  показывает модальные окна («Импорт структуры проекта. Добавить изменения?» и
  информационные). Пока их не подтвердить, главное окно не появляется, и любые
  посланные горячие клавиши уходят в никуда.
- Диалоги «Да/Нет» по умолчанию сфокусированы на «Да» — достаточно
  SetForegroundWindow на окно диалога и Enter. Готово в `assets/scripts/unimod_open.ps1`.

### `cache.tmp` остаётся после аварийного завершения
- При штатном закрытии IDE удаляет `cache.tmp` (лок-файл с pid и hostname).
  Если процесс убит принудительно, файл остаётся. Перед повторным открытием
  проекта его надо удалить.

### В одной IDE можно держать только один проект
- Перед открытием/созданием/распаковкой проекта текущий должен быть закрыт.
  Запуск второго процесса `Unimod.exe` приводит к путанице с окнами.

### В `types/` остаются файлы удалённых ФБ
- В реальном проекте нашлись `types/mna.Ready.st`, `types/mna.fb_0001.st`,
  `types/PID.control.st`, которых нет ни в `proj_structure.prj`, ни в
  `structs.json`. Это мусор от удалённых ФБ.
- Вывод: истина — `structs.json` и `proj_structure.prj`, а не список файлов
  в каталоге. Не делать выводов о составе проекта по `ls types/`.

### Один из «мусорных» .st оказался в CP1251
- `types/PID.control.st` не декодируется как UTF-8. Актуальные файлы — UTF-8.
- Вывод: при чтении `.st` из старых проектов делать fallback на CP1251.

### `tags/base.csv` в CP1251
- В отличие от `global.csv` (UTF-8), генерируемая база тегов — CP1251.
  При чтении скриптом обязательно указывать кодировку явно.

### `*.import.csv` работает ТОЛЬКО для программ, но не для функций
- Что делали: положили `clamp01.import.csv` для функции `clamp01`, открыли проект.
- Что произошло: файл не потреблён и остался лежать, словарь функции не изменился.
  Одновременно лежавший `cycle_ctrl.import.csv` (программа) отработал штатно.
- Вывод: параметры функции добавлять напрямую в `functions/functions.json`,
  массив `programs[i].tags[]`. Такая правка принимается: после сохранения IDE
  сама перегенерирует `functions/<имя>/prog.csv` и `prog.var`.

### Совпавший `offset` у переменных ломает сборку
- Что делали: добавили в `functions.json` параметр `x` с `attributes.offset: 0`.
- Что произошло: сборка падает с «Ошибка в адресации переменных. Переменная
  clamp01.clamp01…», источник «Ошибка в базе». В `tags/base.csv` видно причину:
  у `clamp01.clamp01` и `clamp01.x` одинаковый `offset = 4`.
- Что помогло: вручную проставить свободный `offset` (взять максимум из
  `tags/base.csv` и продолжить с выравниванием: BOOL занимает 1 байт,
  INTEGER/REAL — 4).
- Что НЕ помогло: «Отладка -> Переиндексация базы переменных» — коллизию не
  устраняет, offset'ы добавленных вручную тегов не пересчитывает.
- Важно: у переменных-членов структуры (`structs.json -> tags[]`) значение
  `offset` не используется, там работает `local_offset`; можно оставлять 0.
  Уникальный `offset` нужен для словарей программ и функций.

### После неудачной сборки IDE предлагает отправить проект разработчику
- Диалог: «В проекте обнаружены ошибки. Просьба упаковать проект и отправить
  разработчику по электронной почте на адрес tr-penza@trei.biz. Упаковать проект?»
  Кнопка по умолчанию — **«Да»**.
- Опасность: автоматическое нажатие Enter в цикле разбора диалогов запустит
  упаковку проекта для отправки наружу. В `unimod_build.ps1` шлётся ESC (= «Нет»).
- Следом идёт второй диалог «Исправить обнаруженные ошибки?» — тоже ESC.
- Сами ошибки — во вкладке «Список ошибок» внизу главного окна.

### Скрипты `.ps1` с кириллицей должны быть в UTF-8 **с BOM**
- Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI, кириллица в
  комментариях превращается в мусор и файл падает с ParserError.
- Все скрипты в `assets/scripts/` сохранены как UTF-8 with BOM + CRLF.
  При правке не потерять BOM.

### DPI: клики и скриншоты живут в разных системах координат
- На проверенной машине масштаб 150 %. Для процесса, который **не объявил
  себя DPI-aware**, `SetCursorPos` и `GetWindowRect` работают в
  **логических** пикселях, а `CopyFromScreen` и `PrintWindow` — в
  **физических**: координату с картинки пришлось бы делить на 1.5.
- Скрипты `assets/scripts/ui/` этого больше не касается: `ui_lib.ps1` сразу
  вызывает `SetProcessDPIAware()`, после чего все системы координат
  физические и `Get-UmScale` = 1 (см. ниже «Размер снимка плавал»). Старые
  одиночные скрипты без `ui_lib` по-прежнему живут в логических координатах.

### Схема `configuration.json` для Modbus различается между проектами
- В одном проекте элемент `modbus[i].modbusParameters[j]` выглядит так
  (компактная форма, одно направление на запись):
  `address, beginDataRemote, beginVariableLocal, variablesCount, diagVariable,
  endianness, function, type`
- В другом — расширенная форма с раздельными чтением и записью:
  `beginReadDataRemote, beginReadVariableLocal, readVariablesCount,
  beginWriteDataRemote, beginWriteVariableLocal, writeVariablesCount,
  comment, pollingPeriod, ranges, masksAndOr, isReadTimestamp`
- Вывод: **не писать `configuration.json` по памяти**. Сначала прочитать
  существующий файл, определить набор ключей у уже имеющихся обменов и
  добавлять новые в той же форме.
- **Что пишет сама IDE 2.3.43.15** (проверено 2026-09-11 созданием связей всех
  пяти видов через GUI): только **расширенную** форму — 16 ключей запроса,
  одинаковых у RTU/TCP/UDP и у Master/Slave. Компактная форма, судя по всему,
  досталась от более старой версии IDE. Для нового проекта писать расширенную;
  полный образец — в `file-format-notes.md`, раздел про Modbus.

### Не все теги имеют `attributes.inout`
- У полей структурного типа внутри структуры (например `GV_in` типа `valve`
  внутри `mna`), а также у части внутренних переменных ключ `inout` в
  `attributes` отсутствует вовсе.
- Аналогично может отсутствовать `comment`.
- Вывод: разбирать теги защитно — `tg.get('attributes', {}).get('inout')`,
  а не по индексу. Прямое обращение роняет парсер на реальных проектах.

### `types/io/` есть не всегда
- Каталог `types/io/module<N>.{xml,lib}` появляется только если в проекте
  сконфигурированы модули ввода-вывода на линии связи. В проекте, где обмен
  идёт только по Modbus, каталога нет вообще.
- Вывод: не считать его обязательной частью структуры.

### Элементы массивов перечисляются в словаре поштучно
- В `tags/global.csv` массив даёт строку `Symm_valve_read;A;;R;[54];…`,
  а следом идут строки `Symm_valve_read[0]`, `[1]`, … по одной на элемент.
  Это надо учитывать при подсчёте «сколько в проекте переменных».

### `Unimod.exe -open` НЕ понимает пути с пробелами
- Что делали: `Unimod.exe -open "C:\Claude Unimode PRO 2\tank_sim\project.uprj"`
  (путь передан одним аргументом, с кавычками).
- Что произошло: окно «Ошибка — Не найден файл проекта. Проверьте правильность
  пути: **C:\Claude**». Unimod режет путь по первому пробелу, кавычки не спасают.
  Проект не открывается, а скрипт открытия молча упирается в TIMEOUT.
- Лечение: подставлять короткое имя 8.3 через `GetShortPathName`. Короткое имя
  файла теряет 4-й символ расширения (`PROJEC~1.UPR`), поэтому брать **короткий
  каталог + длинное имя файла**: `C:\CLAUDE~1\tank_sim\project.uprj`.
- В `unimod_open.ps1` это уже сделано автоматически; если 8.3-имена в системе
  отключены, скрипт про это предупредит.

### `-open` с каталогом вместо `.uprj` запускает IDE БЕЗ проекта, и это молча
- Что делали: `unimod_open.ps1 -Project "C:\Claude Unimode PRO 2\gui_lab"` —
  передан каталог проекта, а не файл `project.uprj`.
- Что произошло: Unimod стартовал, окно открылось, скрипт отрапортовал
  `READY after 2 iters` — но проект **не загружен**: оба дерева пустые, в центре
  «Нет открытых редакторов», заголовок окна `Unimod PRO 2` без имени проекта.
  Ошибки не выводится ни в окне, ни в консоли.
- Почему проверка не сработала: маска готовности `'Unimod PRO 2*'` совпадает и с
  пустым окном тоже. Заголовок отличать бесполезно — после «Сохранить проект как»
  он и при открытом проекте остаётся без имени (см. соседнюю запись).
- Лечение: `unimod_open.ps1` теперь сам подставляет `project.uprj`, если передан
  каталог. **Достоверная проверка загрузки — не заголовок, а дерево:**
  `ui_read.ps1 -What tree` должен вернуть узел `[TreeItem]` с именем проекта.
  Пустой список `Узлы деревьев` = проект не открыт.

## Проверенные факты (обратное граблям — работает как ожидалось)

- **`cycle` в `tasks/main/task.json` правится напрямую.** Выставленное вручную
  значение 100 уцелело после открытия и сохранения проекта в IDE.
- **Начальные значения из `*.import.csv` сохраняются точно.** `6.2831853`,
  `0.1`, `60.0` вернулись из IDE без округления и без потери формата.
- **Вызов пользовательской функции с несколькими аргументами компилируется:**
  `t1.Level_pct := norm_pct(h_sim_m, 0.0, TANK_H);` — смесь переменных и
  литералов допустима.
- **Встроенные функции работают из программы:** `SIN(phase)` (REAL → REAL,
  радианы) собирается без объявления чего-либо в словаре. Это проще
  библиотечного ФБ `SIN_GEN`, которому нужен экземпляр системной структуры.
  (Сам `SIN_GEN` тоже работает — проверено 2026-09-11: экземпляр в словаре +
  вызов `gen1.SIN_GEN(true, T, F);`, выход `gen1.Y`; см. `gui-guide.md`,
  раздел «Библиотеки».)
- **Экземпляр пользовательской структуры объявляется прямо в `*.import.csv`:**
  строка `t1;U;;tank;9;;0;…` — IDE сама разворачивает `t1.<поле>` по всем полям.

### Скрытые кнопки с отрицательными координатами — не те, что кажутся
- Что делали: в дереве UIA нашлись кнопки «Экспорт» и «Импорт» с координатами
  вроде `(-787,-629)`. Решили, что это спрятанные в переполнении панели кнопки
  словаря, и вызвали «Импорт» через `InvokePattern`.
- Что произошло: диалог действительно открылся, но это оказался чужой диалог
  выбора файла (фильтр «Файлы JSON»), не относящийся к импорту словаря.
- Разгадка (2026-09-11): это кнопки «Экспорт» и «Импорт» панели
  **«Пользовательская библиотека»** (вкладка внизу левой панели рядом с
  «Контроллеры и коммуникации»). Пока вкладка не активна, её элементы остаются
  в дереве UIA с отрицательными координатами. Диалог «Выбор файла» с фильтром
  JSON — это экспорт/импорт пользовательской библиотеки.
- Вывод: элемент с отрицательными координатами принадлежит нереализованному или
  чужому виджету. Прежде чем звать `Invoke` у невидимого элемента, надо
  убедиться, чей он — например, посмотреть на его родителя в дереве. Вызов
  вслепую открывает не то, что ожидалось.

### Ячейки словаря не открываются мышью — только `{RIGHT}` и `{F2}`
- Что делали: пытались открыть ячейку «Тип» одиночным кликом, двойным кликом,
  двумя кликами с паузой больше интервала двойного клика, кликом по уже
  выделенной строке, `F2`+`Tab`. Ничего не открывало редактор.
- Причина: у таблицы словаря не включён триггер редактирования по клику.
  Текущая ячейка двигается **`{RIGHT}`/`{LEFT}`** (у строк нет потомков, поэтому
  стрелка идёт по колонкам, а не раскрывает узел), редактор открывается **`{F2}`**.
- Рецепт целиком — в `gui-guide.md`, раздел «Редактирование ячеек словаря».
- Попутно: интервал двойного клика в системе 500 мс. Два клика с паузой 200 мс
  склеиваются в двойной — если нужны именно два одиночных, пауза должна быть
  заметно больше 500 мс.

### Принудительное закрытие IDE откатывает незавершённую операцию
- Что делали: запустили «Переименовать проект», ввели новое имя и `{ENTER}`,
  затем вызвали `unimod_close.ps1`.
- Что произошло: скрипт сообщил «не закрылось штатно — убиваю принудительно».
  В дереве имя успело смениться, но **на диске ни каталог, ни `project.uprj`
  не изменились** — операция не довелась до конца, а `cache.tmp` остался.
- Причина: у IDE висел модальный диалог (переименование сопровождается
  подтверждением и перезагрузкой проекта), `CloseMainWindow()` его не закрывает,
  и процесс убивается вместе с несохранённой операцией.
- Как быть:
  - после действий, меняющих проект, **сначала проверять, нет ли открытого
    окна** (`EnumWindows` по процессу), и только потом закрывать;
  - «не закрылось штатно» в выводе `unimod_close.ps1` — это сигнал, что
    что-то осталось неподтверждённым, а не безобидное сообщение;

### `Ctrl+S` сохраняет НЕ весь проект
- В Unimod две разные команды (руководство, §6.9):
  - **`Ctrl+S`** «Сохранить» — только активный редактор, словарь или форму
    настройки. Изменения в остальных элементах проекта **не записываются**.
  - **`Ctrl+Shift+S`** «Сохранить проект» — весь проект целиком.
- Чем это опасно при автоматизации: правишь несколько объектов, жмёшь `Ctrl+S`,
  видишь в дифе только часть файлов и делаешь ложный вывод, что остальное
  «не сохраняется в проекте».
- `unimod_save.ps1` теперь по умолчанию шлёт `Ctrl+Shift+S`; старое поведение
  доступно ключом `-EditorOnly`.

### Win32 и UIA отдают координаты в РАЗНЫХ системах — не сравнивать их

### Модальный диалог вешает весь обход UI Automation

### Защищённый паролем проект НЕЛЬЗЯ открывать через `unimod_open.ps1`
- Почему: скрипт при открытии жмёт `{ENTER}` во всех всплывших окнах (так он

  это **неудачная попытка входа**. По умолчанию после 3 неудачных попыток
  (`maxCountFailInputPassword=3` в `usr.cfg`) проект блокируется, а пароль
  однопользовательского режима не восстанавливается.
- Как быть: для защищённого проекта запускать `Unimod.exe -open …` без
  авто-Enter, дождаться окна входа, снять его снимком и вводить логин/пароль
  через буфер обмена. Перед открытием смотреть `usr.cfg`: непустые секции
  `[user]`/`[role]` или `edition` ≠ 0 — признак защищённого проекта.

### В режиме «по циклам» каждый шаг длится 3000 мс, а не период задачи
- Что делали: в эмуляции `tank_sim` с системным ФБ `gen1 : SIN_GEN`
  (`gen1.SIN_GEN(true, PERIOD_S, 0.0)`, период 60 с) включили «Выполнение по
  циклам» и шагали F8, сравнивая `gen1.Y` с собственной синусоидой программы
  (`t_s := t_s + CYCLE_S` с `CYCLE_S = 0.1`).
- Что произошло: пока приложение заморожено, `gen1.Y` совпадает с
  `sin(phase)` (разница ~10⁻³), но за каждый шаг F8 фаза `SIN_GEN` сдвигается
  на **0,3142 рад = 3,000 с**, а `t_s` — на 0,1 с. Сдвиг одинаковый при паузе
  между нажатиями 6 с и 11 с — это не реальное время.
- Причина: «Отладка → Установить время цикла» открывает диалог «Изменить

  столько, и всё, что интегрирует время цикла (системные генераторы, таймеры),
  шагает на 3 с. Логика программы, которая сама прибавляет константу, этого не
  видит — отсюда расхождение.
- Вывод: перед пошаговой отладкой кода с системными ФБ времени выставлять
  «Установить время цикла» = периоду задачи (у `main` — 100 мс). В основном
  режиме выполнения расхождения нет.
- Проверено: после ввода 100 в диалоге три шага F8 дали сдвиг фазы
  `SIN_GEN` 0,01047 рад = **0,1000 с** на шаг, ровно как `t_s`. Значение
  сохраняется в проекте: `settings.ini` → `[General] debugCycleTime=100`
  (ключ появляется только после первого ввода; 3000 — значение по умолчанию,
  не путать с `[Emulate] Watchdog=3000`). Диалог модальный: в нём только
  клавиатура — `^a`, число, `{ENTER}`.

### Уставка ровно на экстремуме синусоиды никогда не срабатывает
- Что видели: в `tank_sim` уровень моделируется как
  `h = BASE_M + AMP_M·SIN(2π·t_s/PERIOD_S)` — от 1,0 до 4,0 м, то есть
  `Level_pct` от 20 до 80 %, а уставки аварий заданы ровно `LIM_HI = 80`,
  `LIM_LO = 20`. В эмуляции на вершине волны `Level_pct` дошёл только до
  `79.99838` (при `t_s = 15.0993`, а не 15.0), `Alarm_hi` остался `false`.
- Почему: время модели шагает по 0,1 с, а `t_s` накапливает ошибку float
  (после 619 циклов `t_s = 1.8996550` вместо 1.9). Выборка почти никогда не
  попадает точно в пик, а `sin` рядом с пиком меньше единицы — сравнение

  сигнала** (например, 70/30 при размахе 20..80), иначе авария формально есть,
  а на деле мёртвая. Компилятор и сборка такое не ловят — видно только в
  эмуляции.

### В редакторе FBD оба режима оказываются включены — после `TogglePattern.Toggle()`
- «режим редактирования» и «режим соединения» при кликах **мышью**

  после клика верен (проверено 2026-09-13).
- `TogglePattern.Toggle()` через UIA меняет только вид кнопки: состояние
  редактора не меняется, и получаются «оба включены». Редактор тогда ведёт себя
  как в режиме редактирования: протяжка от вывода к выводу **двигает блок**, связь
  не создаётся. На этом застрял первый заход в FBD.
- Лечение: переключать только кликом мыши и проверять `ToggleState` —
  `fbd_lib.ps1` → `Set-FbdMode`.

### Выводы блоков FBD: куда кликать
- Клик по выводу — **внутри блока**, в 0,6 клетки от края: вход — левый край
  + 0,6·sx, выход — правый край − 0,6·sx; по вертикали — строка вывода. Клик по
  кромке или снаружи либо ничего не выбирает, либо попадает в провод.
- Сетка **не зашита**: шаг клетки и начало поля читаются из полос прокрутки
  (`sx = (Maximum + ширина поля) / 500`), левый край блока
  `поле.X + sx·column − прокрутка`, строка k-го вывода
  `поле.Y + sy·(line + k) − прокрутка`. Прежняя формула `663 + 15.96·column`,
  `218 + 23.5·line` была приближением — из-за неё и мазали.
- Ширина блока — целое число клеток и зависит от длины имени; берётся с экрана
  пиксельным детектором (`fbd_lib.ps1` → `Get-FbdRect`).

### Линия связи FBD выделяется только в режиме редактирования
- В режиме соединения клик по линии ничего не выделяет, кнопка «удалить»
  неактивна. Переключиться в «режим редактирования», кликнуть по линии —
  «удалить» становится активной.

### Пока в схеме есть неподключённый блок, «Вывести код на ST» молчит
- Пункт печатает только заголовок «Полученный ST код:» без кода.
- Диагностика — «Сборка → Редактор → Проверить программу» (Ctrl+F9): пишет,
  например, «OR : входы оператора не присоединены» и указывает строку и
  колонку блока **в координатах схемы** (`line`/`column` из `prog.json`).
- Меню «Сборка → Редактор» доступно, только когда активна вкладка схемы.

### Всплывающее меню бывает не видно в UIA, а координаты UIA расходятся с экраном
- В том же сеансе `ui_menu.ps1` перестал находить подпункты: UIA не отдавала
  пункты открытого меню, а у пунктов главного меню координаты пришли в другой
  системе — у «Сборка» (180,34) вместо экранных (230,61).
- Обход: открыть меню кликом по координатам **из снимка** и дальше идти так же
  по снимку. Подменю раскрывается кликом, наведения мало.

### Элементы FBD без списка ставятся только «значком-рукой»
- Константа, метка, прыжок и шина не имеют списка в панели «Добавить/Изменить»,
  и перетаскивание значка палитры для них не работает.
- Тащить надо **значок слева от надписи «Применить в программе»** (панель,
  под полями параметров). Ищется по имени: элемент, чьё `Name` содержит
  «Применить в программе»; точка захвата — его левый край + 14 px.

### Виток и контакт FBD/LD принимают только логическую переменную
- Перетаскивание вещественной переменной на схему в режиме «Виток»/«Контакт»
  молча не даёт ничего: ни блока, ни сообщения. С BOOL-переменной всё ставится.

### Два блока одного экземпляра ФБ: при сохранении пропадают ВСЕ связи программы
- Узел экземпляра (`_TON_1`) из списка «из Словаря» второй раз на схему не
  перетаскивается — но **дочерний узел метода** (`TON` под `_TON_1`)
  перетаскивается сколько угодно (проверено 2026-09-13, песочница `fbd_d`).
- На экране всё выглядит нормально: оба блока стоят, связи нарисованы, звёздочки
  изменений нет. Но при «Сохранить проект» в `prog.json` этой программы
  записывается `"Links": []` — **все** связи программы, не только связи ФБ.
  Ни сообщения, ни ошибки.
- После удаления второго блока и повторного сохранения связи записались.
- Лечение: на каждый блок ФБ — свой экземпляр (`_TON_1`, `_TON_2`, …). После
  любой правки мышью сверять файл: `Assert-FbdFile -Links N` или `fbd_dump.py`.
  `fbd_gen.py`, `fbd_dump.py` и `Invoke-FbdPlace -Prog` такой дубль ловят.

### Блок не ставится, если у нижнего края поля не хватает высоты
- ФБ занимает несколько строк. Бросок в точку ближе ~40 px к нижней границе
  схемы молча игнорируется — блок не появляется. Целиться выше.

### Схему из `prog.json` IDE читает молча и молча теряет
- Проверено 2026-09-12 (песочницы `fbd_b`, `fbd_c`). Блок без обязательного
  поля (`sequence`, `dict`, `mode`, у оператора `subtype`), блок с неизвестным
  `type`, связь на несуществующий `save_id` — всё это **выбрасывается без
  единого сообщения**. Ни диалога, ни строки в «Списке ошибок»; кнопка
  «проверить» отвечает «ошибок нет».
- `Define.block_count`/`track_count` — не справка, а указание, сколько читать:
  при нуле схема открывается пустой, при заниженном числе часть схемы пропадает.
- Опаснее всего, когда исчезает **целая цепочка**: сборка проходит успешно, и
  проект собран без этой логики. Если же пропажа оставила у оператора
  неподключённый вход — сборка падает, и это как раз хороший случай.
- Единственная надёжная проверка после генерации: «Сборка → Редактор →
  Вывести код на ST» и сверка числа строк. Скрипт `assets/scripts/fbd_gen.py`
  ловит эти ошибки до записи файла, `fbd_dump.py` — после.

### Повторяющийся `sequence` рушит генерацию кода
- Все блоки с `sequence = 0` → в ST вышло `sum_real := ;` вместо двух
  присваиваний, «проверить» и сборка дали «Ошибка 19: Неизвестное выражение или
  идентификатор» с координатами блока в клетках схемы.
- Порядок выполнения берётся именно из `sequence`, а не из расположения на
  поле: нижняя цепочка с номерами 0–2 выполняется раньше верхней с 3–5.
  Поэтому «перенумеровать для порядка» в чужой схеме = поменять логику.

### Переменная из чужой программы: ST печатается, сборка падает
- Словари программ локальные. Блок, названный именем переменной другой
  программы, рисуется, и «Вывести код на ST» печатает строку как ни в чём не
  бывало, но сборка встаёт с «Ошибка 19».
- Проверять надо по `prog.csv` **своей** программы (он в UTF-8, а не CP1251).
- **С префиксом программы работает** (проверено 2026-09-14): блок переменной
  `big60.any_alm` (`dict 0`, `mode 4`) в программе `big400` собирается, и в
  эмуляции значение следует за переменной `big60`. Так программы обмениваются
  без глобального словаря. Запись по префиксу не проверялась.

### Две связи на один вход рисуются, но ломают сборку
- Вторая связь рисуется пунктиром наискось, ошибок при открытии нет; сборка
  сообщает «: входы оператора не присоединены».

### `*.import.csv` — единственный способ завести экземпляр ФБ файлами
- Строка `Type=U` (`_TON_1;U;;TON;4;…`) плюс строки полей с `Attribute` 1/2
  создают полноценный экземпляр системного ФБ: в словаре он показан как `TON`
  и раскрывается. В `types/` при этом ничего создавать не надо.
- Помнить общее правило импорта: он **заменяет** словарь программы целиком.

### «Висящий» выбор вывода в режиме соединения съедает следующий клик
- Связь в режиме соединения — два клика по выводам в **любом порядке**.
  Выбранный вывод помечается **пурпурной точкой**; клик по пустому месту выбор
  снимает (проверено 2026-09-13).
- Если второй клик промахнулся, выбор остаётся. Следующий клик по выводу
  соединяется с ним, а клик после него начинает новый выбор — связи уходят не
  между теми выводами. Именно так в прогоне `fbd_test` из 16 связей записались 3.
- Лечение: перед каждой связью клик по пустому месту и проверка, что пурпурных
  пикселей на поле нет; после первого клика — что точка появилась; после
  второго — что появился провод. `fbd_lib.ps1` → `Invoke-FbdLink`.
- Проверка провода по пикселям: «тёмное» считать как max(R,G,B) < 200, а не
  среднее — у пурпурной точки среднее 170 и она сошла бы за провод.
- Провод на экране ещё не значит, что связь есть в модели IDE, — см. «Связь,
  проведённая мышью, не попадает в модель до следующей правки блока».

### Обход дерева UIA медленный — для частых запросов `FindAll`
- `Get-UmAllElements` (TreeWalker по всему окну) — около 500 мс на вызов. Когда
  таких вызовов по нескольку на действие, связь в FBD занимала 15 секунд.
- `AutomationElement.FindAll(Descendants, PropertyCondition)` на главном окне —
  40 мс, `FindFirst` по имени — 6 мс. Вместе с опросом вместо фиксированных пауз
  связь стала занимать 1,5 с (`fbd_lib.ps1` → `Find-FbdFast`).
- `Invoke-UmClick` по умолчанию спит 600 мс после клика; в сериях передавать
  `-SleepMs` поменьше и ждать нужного признака на экране.

### Меню «Сборка → Редактор» иногда не видно в UIA
- В сеансах 2026-09-12 и 2026-09-13 `ui_menu.ps1` открывал «Сборка», но не
  находил подпункт «Редактор» (popup невидим для UIA). Клики по координатам

### Цикл по связям в схеме роняет IDE
- Схема, где выход `*` идёт на вход `+`, а выход `+` — на вход `*`, открывается
  и рисуется (обратный провод уходит петлёй вниз), но «Сборка → Редактор →
  Вывести код на ST» **завершает процесс IDE** без сообщения; остаётся `cache.tmp`
  (проверено 2026-09-13, `fbd_e`).
- Обратная связь делается двумя блоками одной переменной (читает / пишет) —
  так циклом не считается и работает. `fbd_gen.py` цикл не пропустит,
  `fbd_dump.py` о нём предупредит.

### Неизвестная буква типа в `*.import.csv` роняет IDE при открытии — и так раз за разом
- `t_byte;Y;…` и `t_dbl;D;…` в импорте словаря: процесс IDE завершается через
  несколько секунд после старта, `cache.tmp` остаётся (воспроизведено дважды).
- Файл импорта при этом **не удаляется** — каждое следующее открытие снова
  падает, пока файл не убрать руками.
- Импорты других программ, прочитанные до падения, **удаляются, хотя результат
  так и не сохранён** — их надо класть заново.
- Проверенные буквы: B, I, R, T, M, U (экземпляр), A (массив). Буквы BYTE и
  DOUBLE не выяснены — такие переменные пока заводить через GUI.

### Оператор на 3+ входа без поля `args` теряет входы при первом сохранении
- `AND`/`+` с `inp_count: 3` открываются и дают правильный код
  (`( a AND b AND c )`), но стоит программу поправить в редакторе и сохранить —
  IDE пишет оператор с двумя входами и молча выбрасывает связи к третьему.
- `subtype` на это не влияет (у многовходовых операторов он 1). Число входов
  хранит поле `args`: `{"args": 4, "inp_count": 4, "subtype": 1, …}` — так пишет
  сам редактор (проверено 2026-09-13).

### `mode: 1` у связи — это «закомментирована», а не инверсия
- Связь с `mode 1` рисуется серым, «проверить» считает вход пустым («входы
  оператора не присоединены»), код по ней не генерируется. Инверсия — `mode 2`
  (кружок у приёмника, `NOT` в коде). Закомментированный блок: `mode 1`,
  `sequence −1`, все его связи тоже `mode 1`.

### Константы: компилятор строже, чем генератор ST
- Генератор печатает `name` константы как есть, поэтому «Вывести код на ST»
  проходит, а сборка — нет. Ошибки: `2` в REAL и `1` в BOOL — «Ошибка 29:
  Неправильный тип выражения»; `2,5`, `1e3`, `a + -1.5` — «Ошибка 30: Нет
  закрывающей скобки» и «Ошибка 58: Ожидается ;». Правильно: `2.0`, `1.0E3`,
  `(-1.5)`, `TRUE`.
- Неявных преобразований нет вообще: `real := int` и `int + real` — «Ошибка 29».
  Нужны операторы `INT_TO_REAL`, `REAL_TO_INT` и т. п.; `REAL(x)`/`INT(x)` не
  компилируются.
- Компилятор выдаёт максимум 5 ошибок: пока первые не исправлены, остальных не
  видно.

### IDE перенумеровывает `save_id` при сохранении
- После удаления двух блоков и сохранения `save_id` стали подряд 0…35, связи
  пересчитаны. Скрипт, запомнивший `save_id` до сохранения, после него
  промахнётся — адресовать блоки по `name` и `column`/`line`.

### В эмуляции частые UIA-запросы однажды уронили IDE
- 2026-09-13: сразу после запуска эмуляции `FindAll` по дереву вернул
  `RPC_E_SERVERFAULT`, процесс IDE завершился. Повтор той же схемы и тех же шагов
  прошёл нормально. Во время эмуляции держать опрос UIA умеренным; значения
  видны и на самой схеме.

### Выход из эмуляции после частого опроса словаря завершил IDE
- 2026-09-18: 40 чтений словаря подряд (раз в 1,2 с, около 2,5 минут), затем клик
  по кнопке «Эмуляция» — процесс IDE закрылся, остался `cache.tmp`. Файлы схемы
  целы: последнее сохранение было до эмуляции. Повтор с 10 чтениями раз в 2,5 с

- Правила: словарь в эмуляции опрашивать не чаще чем раз в 2 с; то, что должно
  быть замечено в каждом цикле, копить в самой схеме (защёлка расхождений), а не
  вычитывать опросом; перед выходом из эмуляции сделать паузу; после падения
  удалить `cache.tmp`.

### Часть операторов палитры компилятор не принимает
- `SETBIT`, `MLEN`, `CHAR`, `ASCII` в палитре есть, но сборка на них падает
  («Ошибка 19: неизвестное выражение», 30, 58, 43) при всех пробованных
  сигнатурах (2026-09-18). Пользоваться ими нельзя, пока не найден верный вид.
- У части операторов сигнатура не та, что кажется: `LOG` требует **два**
  аргумента (иначе «Ошибка 40»), `EXPT` — целую степень, `TRUNC` возвращает
  REAL, `RAND` принимает и возвращает INT.
- Проверять новый оператор дешевле всего так: одна цепочка на оператор, сборка,
  затем по номеру строки в «Списке ошибок» найти виновника (номер строки
  совпадает с номером в «Вывести код на ST»). Компилятор показывает максимум
  пять ошибок за раз.

### Контакты LD по фронту и спаду заводят скрытую переменную
- Контакт (P) или (N) IDE разворачивает так: `q3:=( TRUE ) AND (trig_in AND
  (NOT _temp_front_7 ));`, а в конце программы дописывает `_temp_front_7:=trig_in;`.
  Этой переменной нет ни в схеме, ни в словаре программы.
- Поэтому построчная сверка кода (`--check-st`) такие цепи пропускает: в дампе
  они помечены `<фронт/спад>`.

### Параметр дочерней программы без `Attribute 1` не становится входом блока
- В `ch_lim.import.csv` параметр `x` импортировали с `Attribute 0` — словарь
  дочерней принял строку, но блок дочерней программы на схеме получился **без
  входов** (`inp_count 0`), и вызвать её с аргументом было нечем (2026-09-18).
- Лечение: в импорте словаря дочерней у параметров `Attribute 1`; строку
  возвращаемого значения (имя программы, `Attribute 2`) не трогать — её ведёт IDE.

### Блок структуры, поставленный мышью, заводит новый экземпляр в словаре
- Перетаскивание «Структура» или «Структура с полями» из палитры создаёт в
  словаре программы экземпляр `_tank_1`, `_tank_2` (как `_TON_1` у ФБ) со всеми
  полями. Словарь растёт незаметно, а лишние экземпляры занимают память
  контроллера.
- Если нужен конкретный экземпляр, заводить его импортом словаря
  (`t2;U;;tank;9;…`) и ставить блок файлом, указав это имя.

- Блоки `sim_main.h_sim_m`, `sim_main.t1.Level_pct` на схеме другой программы в

- Пурпурная заливка блока целиком — это не «висящий» выбор вывода (там пурпурная
  точка на выводе).

### Двойной клик мимо узла дерева свернул окно IDE из развёрнутого

- Лечение: узлы дерева искать с проверкой прямоугольника (ниже родителя в

### Правка схемы мышью перенумеровывает порядок выполнения по расположению
- Схема `fbd_f`: цепочку OR файлом опустили ниже цепочки AND, которая читает
  `or_res`; `sequence` при этом сохранили — в коде OR выполнялась раньше AND.
  После правки в редакторе IDE заново пронумеровала всю схему, OR стала
  последней: AND теперь видит значение прошлого цикла (2026-09-13, `fbd_diff.py`).
- **Точное правило** (2026-09-14, номер в номер на 30 схемах): блоки без
  исходящих связей — по верхнему краю (у переменной `line`, у оператора и ФБ
  `line − 1`), при равенстве по `column`; перед каждым — его источники в глубину
  по номерам входов, у ФБ после входов eni/eno. Положение источников не важно.
- Перенумеровывают: перенос блока, удаление блока, удаление связи, новый блок.
  Не перенумеровывают: открытие и сохранение без правок, проведение связи.
- `fbd_gen.py` ставит порядок по этому правилу (`ide_order`); `fbd_dump.py` и
  `save()` предупреждают, если порядок в файле другой или цепочка читает
  переменную раньше, чем её пишет другая.

## Библиотека блоков и чтение значений (2026-09-19)

### Значения словаря читаются нулями у строк, которых нет на экране
- Что делали: в эмуляции читали словарь программы через UIA (таблица — это Grid,
  `GridPattern.GetItem(строка, колонка)`).
- Что произошло: у первых ~28 строк значения живые, у остальных — пусто, и в
  разборе они выглядят нулями. Вывод напрашивался неверный: «программа
  останавливается на середине цикла».
- Причина: таблица отдаёт **имена всех строк**, но колонку «Значение» — только у
  строк, которые сейчас отрисованы.
- Лечение: листать таблицу (`{PGDN}`) и склеивать страницы —
  `um_emul.ps1 -Action read` делает это сам. Контрольный приём: ставить в
  программе метки стадий (`z_stage := N;` между группами) — если метка доросла
  до последней, цикл программы отработал целиком, и нули означают чтение, а не
  исполнение.

### Вывод ФБ, названный как сам блок, из ST не прочитать
- У `INDEX` выход называется `INDEX`, как и метод. Строка `v := x_index.INDEX;`
  даёт «Ошибка 29: Неправильный тип выражения» — компилятор видит вызов метода.
- Лечение: в ST читать такой выход нельзя; остальные выводы (`FAULT`) доступны.
  На схеме FBD связь идёт по номеру вывода, так что там ограничения нет
  (отдельно не проверялось).

### Счётчики CTU/CTUD считают каждый цикл, а не по фронту
- В МЭК 61131-3 `CTU` считает по переднему фронту `CU`. Здесь (и в руководстве,
  и в опыте) счёт идёт **в каждом цикле, пока `CU=TRUE`**: пять циклов с
  `CU=TRUE` дали `CV=5`.
- Лечение: если нужен счёт событий, подавать на `CU` импульс длиной один цикл —
  `RF_TRIG`/`F_TRIG` дают ровно такой.

### LRATE не ограничивает самый первый переход
- Блок на первом вызове принимает `Y := X`, и ограничение начинает работать
  только со следующих изменений. Опыт с постоянным `X=10.0` показал `Y=10.0`
  сразу — похоже на «блок не работает», но это инициализация.
- `V` задаётся в единицах **в секунду** (`V=1.0` при цикле 100 мс → 0.1 за цикл).

### DELAY отстаёт на N−1 цикл, если читать выход в том же цикле
- `DELAY(TRUE, rn, 3, 100)`: при входе 20.0 выход равен 18.0, а не 17.0.
  Порядок «вызвали блок → прочитали Y» съедает один цикл задержки.

### TIME_TO_TEXT: пример в руководстве не сходится с поведением
- `TIME_TO_TEXT(d#1711021435000.0, 0, 3)` вернул `21.03.2024 14:43:55`, а в
  руководстве для того же вызова напечатано `11:43:55`. Фактически `TZ`
  прибавляет часы к UTC; в примере руководства сдвиг не применён.

### Имена в дереве проекта сравнивать с учётом регистра
- PowerShell `-eq` регистронезависим, и поиск программы `t1` в дереве находил
  вывод функционального блока `T1` (`DDERIV.T1`). Сравнивать `-ceq` и проверять
  уровень вложенности по `BoundingRectangle.X`.

## Разбор чужого проекта с Modbus TCP (2026-09-28)

### Сборка падает: «Удаленный узел … недоступен из текущей конфигурации сети»
- Что было: проект с Modbus TCP Master к серверу `192.168.233.100:502` не собирался,
  единственная ошибка — «Modbus (1. Modbus). Удаленный узел 192.168.233.100 недоступен
  из текущей конфигурации сети», источник «Внешние коммуникации».
- Причина: сборка проверяет, что адрес Modbus-сервера лежит в одной из сетей портов
  контроллера (`configuration.json` → `controllers[0].net_eth1…4` с масками). Там были
  192.168.1.1 … 192.168.4.1 /24.
- Лечение: перевести порт контроллера в сеть сервера (на копии хватило
  `net_eth1 = net_eth1_1 = 192.168.233.1`) — проект собрался без ошибок. Адрес в
  `settings.ini [connectionPLC]` (ПК → ПЛК) на это не влияет.

### Запрос записи Modbus пишет ВСЕ регистры массива
- Функция 16 передаёт `variablesCount` значений целиком. Если программа заполняет
  только часть массива (например, «вкл/выкл» насосов, а соседние элементы — частоту
  вращения не трогает), в устройство каждый цикл уходят начальные нули. При разборе
  чужого проекта сверять, что каждый элемент массива записи чем-то заполняется.

### Эмуляция проекта с Modbus: значения можно подавать прямо в массив чтения
- В эмуляции Modbus-обмена нет, массивы чтения не перетираются: `ValuePattern.SetValue`
  в элемент `Symm_sensor_read[0]` (строку массива сначала раскрыть `{RIGHT}`) проходит
  через программу разбора в переменные и логику. Строки ниже края таблицы значения не
  принимают — прокрутить колесом (`mouse_event 0x0800`, дельта вниз — `[uint32]4294967176`).
