# FBD: как собирать схемы и на чём не спотыкаться

Справочник по языку FBD в Unimod PRO 2 (2.3.43.15). Формат файла — в
`file-format-notes.md` → «Формат FBD-программы»; карта панелей редактора — в
`gui-guide.md` → «Редактор FBD/LD». Здесь — рабочий путь, инструменты,
стандарт расположения и таблица симптомов.

## Главное

**Схему можно не рисовать.** `prog.json` программы принимается редактором как
есть: схема открывается, рисуется, даёт код на ST и собирается. Проверено
2026-09-12 на 22 схемах: операторы, вложенные выражения, ветвление, накопитель
с обратной связью, функциональный блок TON — всё работает и считает правильно
в эмуляции.

**Семантика проверена в эмуляции** (2026-09-13): сети ФБ (BLINK → CTU, RS,
HYSTER → F_TRIG, eni), защёлка, инверсия связи, операторы на 3 входа,
константы всех типов, преобразования типов, порядок выполнения. Любой из 204
системных ФБ генератор ставит сам — выводы и строки словаря берутся из
библиотеки IDE.

**Импульс в один цикл — считать в схеме, а не опросом.** `F_TRIG` даёт `Q` ровно
на один цикл: счётчик фронтов (`CTU`) и счётчик тактов, в которых импульс был
истинным (`n := n + BOOL_TO_INT(pls_q)`), после трёх фронтов показали одно и то
же число (проверено 2026-09-18). Опросом словаря такой импульс не поймать —
копить надо прямо на схеме.

**Схема сверяется с эталоном.** Контрольный прогон 2026-09-18: логика `tank_sim`
(модель уровня, проценты через функцию проекта, объём, две аварии) повторена на
FBD в той же задаче, рядом с оригиналом на ST. FBD-программа читает переменные
ST-программы по префиксу и сама считает расхождения. За полный период синусоиды
(~600 циклов по 100 мс) расхождений нет: `d_pct = d_m = d_v = 0`, обе аварии
переключались в тех же циклах, что у ST. Приём — «Рецепт 15».

**Большие схемы IDE не тяготят** (2026-09-14). Схема на 402 блока открывается за
4 с, код ST выводится за 4 с, сохраняется за 0,6 с. Сборка проекта из ~630 блоков
занимает меньше секунды. Правки мышью на ней идут так же быстро, как на десяти
блоках. Логика 21 канала аварий проверена в эмуляции. Трудность больших схем —
не скорость, а порядок выполнения и сверка: см. «Порядок выполнения» и «Большие
схемы».

**Мышь — для точечных правок, и она тоже надёжна.** С 2026-09-13 координаты не
угадываются: шаг сетки и прокрутка читаются из полос прокрутки через UIA, провод
проверяется по пикселям сразу после создания, «висящий» выбор вывода
обнаруживается и снимается. Проверено на трёх масштабах, с прокруткой, с
изменённым размером панелей и на поле 1000×1000. **Но провод на экране — ещё не
связь:** IDE вносит связь в модель только при следующей правке блока. Серию
связей завершает `Submit-FbdLinks` (или `fbd_do.ps1 save`), итог сверяется по
файлу.

Инструменты:

| Скрипт | Зачем |
|---|---|
| `scripts/fbd_gen.py` | собрать схему из описания и записать в `prog.json`: `expr()`/`fb_call()` сами раскладывают выражения по клеткам и проверяют типы; порядок выполнения — по правилу IDE; каталог системных ФБ; перед записью проверяет больше двадцати видов ошибок |
| `scripts/fbd_dump.py` | прочитать любую (в том числе чужую) схему: выражения в порядке выполнения, блоки, связи, замечания (включая порядок); `--check-st` — сверка с выводом IDE «Вывести код на ST» |
| `scripts/fbd_diff.py` | смысловой дифф двух версий схемы: блоки, связи, порядок выполнения, изменившиеся выражения |
| `scripts/ui/fbd_lib.ps1` | мышь в редакторе: геометрия поля, прокрутка, режимы, связи с проверкой, размещение блоков |
| `scripts/ui/fbd_do.ps1` | то же одиночными командами: `view`, `mode`, `link`, `place`, `save` (сначала фиксирует связи), `scroll`, `clear`, `st`, `menu`, `delete`, `unlink`, `move`, `undo`, `redo` |

```python
import sys; sys.path.insert(0, '<skill>/scripts')
from fbd_gen import Scheme, K
s = Scheme(dict_csv='tasks/main/logic/prog.csv')     # типы и имена берутся из словаря
s.expr('sum_real', ('+', 'a_real', 'b_real'), line=3)
s.expr('alarm', ('AND', ('>', 'level', K('90.0', 'R')), '!manual'), line=s.next_line)
s.save('tasks/main/logic/prog.json')                  # порядок, проверка, предупреждения
```

```bash
python fbd_dump.py tasks/main/logic/prog.json --blocks --links
python fbd_dump.py tasks/main/logic/prog.json --check-st st.txt   # st.txt — текст «Вывести код на ST»
```

## Предполётный чеклист

1. **Копия каталога проекта.** Всегда.
2. **Проект закрыт в IDE**, если схема правится файлом. При открытом проекте
   IDE держит схему в памяти и перезапишет файл при сохранении.
3. **Переменные уже в словаре этой программы.** Словари локальные. Нет
   переменной — сборка встанет с «Ошибка 19», хотя код на ST печатается.
4. **На каждый блок ФБ — свой экземпляр** (`_TON_1`, `_TON_2`, …), заведённый
   строкой `Type=U` в словаре. Два блока одного экземпляра = потеря всех связей
   программы при сохранении.
5. **Типы и константы по правилам компилятора**: REAL с точкой (`2.0`),
   отрицательные в скобках (`(-1.5)`), BOOL только `TRUE`/`FALSE`, никаких
   неявных преобразований — `INT_TO_REAL` и компания. `fbd_gen.py` проверяет.
6. **Никаких циклов по связям**: обратная связь — вторым блоком той же
   переменной. Настоящий цикл роняет IDE.
7. **После открытия — сверить код:** `Get-FbdStCode` (или «Сборка → Редактор →
   Вывести код на ST») → текст в файл → `fbd_dump.py prog.json --check-st st.txt`.
   Единственный надёжный способ убедиться, что IDE прочитала схему целиком; на
   сотне цепочек глазами расхождение не найти.
8. **Правили мышью — зафиксировать связи, сохранить, сверить файл:**
   `Submit-FbdLinks` → `Save-FbdProject` → `Assert-FbdFile -Links <сколько
   должно быть>` или `fbd_dump.py` (всё это делает `fbd_do.ps1 save`). Без
   фиксации связь, проведённая последней, остаётся только на экране.
9. **Предупреждения о порядке** из `save()` и `fbd_dump.py` читать: «читает
   раньше, чем её пишет» — значение прошлого цикла; «не тот порядок, что IDE
   назначит» — первая правка мышью поменяет логику.
10. **Сборка.** `app/project.app` появился или обновился — схема принята
    компилятором (старый файл от прошлой сборки — не признак).
11. Работая мышью, окно IDE закрепить `Set-UmTopmost`, после работы — `-Off`.

## Как IDE читает схему (и что она молча выбрасывает)

Редактор разбирает `text` из `prog.json` по принципу «что не понял — то
пропустил». **Ни одного сообщения при этом не появляется**: ни диалога, ни
строки в «Списке ошибок», а кнопка «проверить» показывает «ошибок нет».

Молча теряется:

| Что не так | Что происходит |
|---|---|
| `Define.block_count` / `track_count` меньше фактического | лишние блоки и связи не читаются; при 0 схема открывается пустой |
| у блока нет `sequence`, `dict`, `mode`, у оператора — `subtype` | блок выбрасывается вместе со связями |
| неизвестный `type` (например 99) | блок выбрасывается |
| связь ссылается на несуществующий `save_id` | связь выбрасывается |
| **на схеме два блока одного экземпляра ФБ** | схема рисуется, связи на экране есть, но **при сохранении из файла пропадают ВСЕ связи программы** |
| оператор на 3+ входа без поля `args` | код верный, но при первом сохранении из редактора оператор урезается до двух входов, лишние связи пропадают |
| `mode: 1` у связи | связь закомментирована: рисуется серым, для кода и проверки её нет |

Падает сама IDE (процесс завершается, остаётся `cache.tmp`):

| Что | Когда |
|---|---|
| цикл по связям (выход одного оператора на вход другого и обратно) | на «Вывести код на ST» |
| буква типа `Y` или `D` в `*.import.csv` | при открытии проекта — и при каждом следующем, пока файл не убрать |

Громко ломается (это хорошо):

| Что не так | Как проявляется |
|---|---|
| повторяющийся `sequence` | код на ST выходит обрубком (`sum_real := ;`), сборка падает с «Ошибка 19» |
| переменной нет в словаре программы | сборка падает с «Ошибка 19» |
| у оператора или ФБ не подключён вход | «: входы оператора не присоединены» и координаты блока в клетках схемы |
| две связи на один вход | обе рисуются (вторая — пунктиром наискось), сборка падает |
| неподходящая константа (`2` в REAL, `1` в BOOL, `2,5`, `1e3`, `a + -1.5`) | «Ошибка 29» или «Ошибка 30/58» при сборке; код на ST при этом печатается |
| разные типы без преобразования (`real := int`) | «Ошибка 29: Неправильный тип выражения» |
| неподключённый выход оператора | «выходы оператора не присоединены» |

Если исчезла целая цепочка, сборка пройдёт успешно и проект будет собран без
этой логики. Поэтому: **сгенерировал — сверь код на ST; поправил мышью — сверь
файл**.

## Порядок выполнения

Порядок задаёт поле `sequence`. Пока схему не трогают мышью, IDE берёт его из
файла как есть: открыть и сохранить — порядок прежний, даже если он не
совпадает с расположением. Но **перенос блока, удаление блока или связи,
добавление блока** заставляют IDE перенумеровать всю схему по правилу
(проверено 2026-09-14 номер в номер на 30 схемах, в том числе нарисованных
мышью):

1. **Блоки-результаты** — блоки без исходящих связей: переменные справа, ФБ с
   неподключёнными выходами — берутся **по верхнему краю** сверху вниз, при
   равенстве слева направо. Верхний край переменной и константы — `line`,
   оператора, ФБ, функции — `line − 1` (заголовок).
2. Перед каждым результатом — его **источники**, обходом в глубину по номерам
   входов; у ФБ после обычных входов — eni/eno.
3. Где стоят источники, значения не имеет: цепочка с источниками вверху и
   результатом внизу выполнится, когда до неё дойдёт очередь результата.

`fbd_gen.py` расставляет `sequence` ровно так (`ide_order()`), поэтому правка
сгенерированной схемы мышью порядок не меняет — `fbd_diff.py` пишет «не
изменился».

Следствия:

- **Цепочка, которая читает переменную, записанную другой цепочкой, должна иметь
  результат ниже (или на той же строке правее) результата пишущей.** Иначе она
  получит значение прошлого цикла. `save()` и `fbd_dump.py` предупреждают:
  ««lat_1» читает ack раньше, чем её пишет цепочка «ack»». Если так и задумано
  (фронт: `rise := x AND NOT prev` выше, `prev := x` ниже) — предупреждение
  можно принять.
- **Чужая схема** с порядком не по правилу поменяет логику при первой правке
  мышью. `fbd_dump.py`: «порядок в файле не тот, что IDE назначит после первой
  правки мышью» — и что с чем поменяется местами.
- Две цепочки, пишущие в одну переменную: последней выполняется нижняя.
- Накопитель (`sum := sum + 1`) делается двумя блоками одной переменной:
  один читает, другой пишет. Цикла по связям при этом нет.
- Проведение связи мышью порядок не перенумеровывает — и в модель эта связь
  до следующей правки не попадает (см. «Мышь»).

## Стандарт расположения

Каждый источник стоит **на строке своего входа**, результат — на строке выхода.
Тогда все провода прямые, схема читается глазами, а мышь не промахивается.
Строка вывода переменной с `line = L` совпадает со строкой первого вывода
оператора или ФБ с тем же `L`.

| Что | Колонка | Строка |
|---|---|---|
| источник для `inN` (переменная, константа) | 2 | `L + N − 1` |
| оператор, ФБ | 20 | `L` (выводы на строках `L`, `L+1`, …) |
| результат | 34 | `L` (строка выхода) |
| следующая вертикальная полоса | +43 | те же правила |

- Между цепочками 5 строк (`ROW_STEP`); у ФБ с k выводами — не меньше k + 2.
- Между блоками по горизонтали не меньше 2 клеток: проверка провода смотрит на
  клетку левее входа. Блоки **внахлёст** IDE заливает **жёлтым** (на сборку не
  влияет, но схема нечитаема); вплотную — не заливает (проверено 2026-09-14),
  но читать тяжело. Ширина блока в клетках — примерно половина длины подписи + 1,
  у оператора и ФБ не меньше 5; `fbd_gen.py` предупреждает о касании по этой
  оценке (она завышена на клетку — так надёжнее).
- Клетки 0–1 по горизонтали оставлять пустыми.
- **Результат цепочки, которая читает результат другой, — ниже неё** (или на
  той же строке правее). Правило порядка — в разделе «Порядок выполнения».
- Строки 0–1 не занимать: заголовок оператора на строке 0 уходит за край.
- На развёрнутом окне при `Scale=2` видно 91 колонку × 33 строки. Дальше поле
  прокручивается — `fbd_lib.ps1` делает это сам.

`fbd_gen.py` → `Scheme.chain()` строит цепочки ровно так (проверено: пять
цепочек в двух полосах — все провода прямые, код верный).

### Раскладка выражений: `expr()` и `fb_call()`

Координаты руками не нужны: выражение раскладывается само, типы проверяются до
записи.

```python
from fbd_gen import Scheme, K, Pin, Op
s = Scheme(dict_csv='tasks/main/big/prog.csv')
s.expr('hi_1', ('AND', ('OR', ('>', 'lvl_1', K('90.0', 'R')), ('<', 'lvl_2', ('10.0', 'R'))), '!ack'), line=3)
ton = s.fb_call('dly_1', 'TON', line=s.next_line,
                ins={'IN': ('AND', 'hi_1', '!lo_1'), 'PT': K('3000', 'I')}, outs={'Q': 'alm_1'})
s.expr('lat_1', ('OR', Pin(ton, 'Q'), 'lat_1'), line=s.next_line)      # провод прямо от выхода ФБ
s.expr('lvl_r', Op('INT_TO_REAL', 'cnt'), line=s.next_line)
s.save('tasks/main/big/prog.json')
```

| Операнд | Что это |
|---|---|
| `'lvl_1'` | переменная: словарь программы, глобальный словарь (блок `dict 1`) или другая программа `'big60.any_alm'` |
| `'!ack'`, `Inv(...)` | инвертированная связь к родителю (только BOOL) |
| `K('90.0', 'R')`, `('90.0', 'R')` | константа (правила литералов — «Константы и типы») |
| `('AND', a, b, c)` | оператор; `args` для 3+ входов пишется сам |
| `Op('INT_TO_REAL', x, in_t=, out_t=)` | оператор с явными типами выводов |
| `Pin(блок, 'Q')` | выход уже поставленного блока — провод без нового блока |

- Источники — в колонке `column` (по умолчанию 2), операторы — уровнями правее
  (первый через 18 клеток, дальше через 12), результат — через 14 после
  последнего. Для одного уровня это ровно 2 / 20 / 34 стандарта.
- У каждого поддерева свои строки: блоки не накладываются, провода от источников
  прямые. Между соседними операторами одной колонки — пустая строка.
- `s.next_line` — строка для следующего выражения (одна пустая строка и строка
  заголовка), `s.next_column` — первая свободная колонка правее результата
  (для следующей полосы).
- Ловится до IDE: разные типы на входах, выражение не того типа, что результат,
  инверсия не-BOOL, неподходящий вход преобразования, неподключённый вход ФБ.
- `Pin` к блоку выше и правее даёт провод, идущий назад, — работает, но читается
  хуже; потребителя лучше ставить в следующую полосу.

Проверено 2026-09-14: глубина 3, ФБ с выражением на входе, прямой провод от
выхода ФБ, преобразование типа — код IDE совпал со схемой (`--check-st`),
сборка прошла.

### Большая схема: строки — объекты, полосы — стадии

Схема из однотипных объектов (каналов, агрегатов) раскладывается таблицей:
**объект — группа строк, стадия обработки — вертикальная полоса**
(`column = 2 + k·43` при одном уровне операторов; при глубине D полосе нужно
около 41 + 12·(D−1) колонок — бери `s.next_column`).

```python
for k in range(1, n + 1):
    line = s.next_line
    s.expr('hi_%d' % k, ('>', 'lvl_%d' % k, K('90.0', 'R')), line=line)               # полоса 0
    s.expr('lo_%d' % k, ('<', 'lvl_%d' % k, K('10.0', 'R')), line=s.next_line)
    bottom = s.next_line
    s.fb_call('dly_%d' % k, 'TON', line=line, column=45,                                # полоса 1
              ins={'IN': 'hi_%d' % k, 'PT': K('3000', 'I')}, outs={'Q': 'alm_%d' % k})
    s.expr('lat_%d' % k, ('AND', ('OR', 'alm_%d' % k, 'lat_%d' % k), '!ack'), line=line, column=88)   # полоса 2
    s.next_line = max(bottom, s.next_line)
s.expr('any_alm', Op('OR', *['lat_%d' % k for k in range(1, n + 1)]), line=s.next_line)  # сводка внизу
```

Результаты стадий одного объекта стоят на одной строке, поэтому IDE выполняет
их слева направо — стадия читает результат предыдущей в том же цикле. Сводка
по всем объектам — внизу. Проверено: 21 канал — 402 блока, 316 связей, поле
132×191 клеток, код совпал, эмуляция: авария через 3 с, защёлка держит,
квитирование сбрасывает.

## Что схема даёт в коде ST

Проверено «Вывести код на ST», сборкой и в эмуляции (2026-09-12/13):

| На схеме | В коде ST |
|---|---|
| переменная → `:=` → переменная | `b := ( a ) ;` |
| переменная → переменная напрямую | `b := a ;` |
| оператор на 2 и 3 входа | `x := ( a + b ) ;`, `x := ( a AND b AND c ) ;` |
| одноместный оператор, преобразование | `x := SQRT( a ) ;`, `x := INT_TO_REAL( i ) ;` |
| вложенные операторы | `x := ( ( a + b ) * 2.0 ) ;` |
| инвертированная связь (`mode 2`) | `( flag1 AND (NOT flag2 ) )` |
| ФБ | `inst.IN:=src; inst.PT:=3000; inst.TON(); q := inst.Q ;` |
| выход ФБ во вход ФБ | `cnt1.CU:=blink1.Q;` |
| ФБ с подключённым eni | `if (flag1) then … cnt1.CTU(); end_if;` |
| поле экземпляра как переменная | `_TON_1.PT := ( t_int ) ;` |
| закомментированный блок, комментарий | ничего |

Порядок строк — порядок `sequence`. Номер строки в ошибках сборки совпадает с
номером строки этого вывода.

## Константы и типы

| Нужно | Писать | Нельзя (ошибка сборки) |
|---|---|---|
| REAL | `2.5`, `2.0`, `1.0E3` | `2` (29), `2,5` (30/58), `1e3` (30/58) |
| BYTE | `b#7` (буква типа в словаре — `K`) | десятичное число без `b#` |
| DOUBLE | `d#1.5` (буква типа — `N`) | число без `d#` |
| отрицательное на входе оператора | `(-1.5)` | `-1.5` → `a + -1.5` (30/58) |
| INTEGER | `3000`, `-7` | — |
| BOOL | `TRUE`, `FALSE` | `1`, `0` (29) |
| MESSAGE | `'abc'` | — |

`subtype` константы равен коду её типа (0 BOOL, 1 INT, 2 REAL, 5 BYTE, 6 DOUBLE) —
так пишет сама IDE.

**Неявных преобразований нет.** Любое смешение типов — «Ошибка 29».
Преобразования — операторы `<ИЗ>_TO_<В>` (`INT_TO_REAL`, `REAL_TO_INT`,
`REAL_TO_BOOL`, `BOOL_TO_INT`, …; из BOOL, INT, REAL, TIME, STRING, BYTE,
DOUBLE в любой другой). У них конкретные типы выводов:
`Scheme.op('INT_TO_REAL', 1, col, line, in_t='I', out_t='R')`.
`REAL_TO_INT(2.5)` = `2`; `REAL_TO_BOOL(2.5)` = `TRUE`.

`fbd_gen.py` отказывается создавать неподходящую константу и сам берёт
отрицательную в скобки.

## ФБ из системной библиотеки

Выводы и типы любого системного ФБ генератор берёт из библиотеки IDE
(`%APPDATA%\TREI\UnimodPRO2\library\types\types.json`), экземпляр для словаря
строит сам:

```python
from fbd_gen import Scheme, fb_catalog, instance_csv_rows
print(fb_catalog()['CTU'])     # {'method': 'CTU', 'inputs': [('CU','B'), ('RESET','B'), ('PV','I')], 'outputs': [('Q','B'), ('CV','I')], ...}

# 1-й заход IDE: словарь программы (полный — импорт заменяет словарь)
rows = old_prog_csv_rows + instance_csv_rows('cnt1', 'CTU') + instance_csv_rows('blink1', 'BLINK')
# 2-й заход: схема
s = Scheme(dict_csv='tasks/main/logic/prog.csv')
blink = s.fb_lib('blink1', 'BLINK', 20, 3)
cnt = s.fb_lib('cnt1', 'CTU', 40, 3)
s.link(s.var('flag1', 2, 3), blink, dst_slot=0)
s.link(s.const('500', 'I', 2, 4), blink, dst_slot=1)
s.link(s.const('1000', 'I', 2, 5), blink, dst_slot=2)
s.link(blink, cnt, src_slot=0, dst_slot=0)          # выход ФБ прямо во вход ФБ
en = s.eni(cnt)                                     # вызов CTU только при flag1
s.link(s.var('flag1', 30, 1), en)
```

Частые ФБ (выводы — вход | выход):

| ФБ | Назначение | Выводы |
|---|---|---|
| `TON` / `TOF` / `TP` | таймер по фронту / по спаду / импульс | `IN:B PT:I` \| `Q:B ET:I` |
| `CTU` / `CTD` | счётчик вверх / вниз | `CU:B RESET:B PV:I` \| `Q:B CV:I` (CTD: `CD LOAD PV`) |
| `CTUD` | реверсивный счётчик | `CU CD RESET LOAD:B PV:I` \| `QU QD:B CV:I` |
| `RS` / `SR` | триггеры | `SET:B RESET:B` \| `Q:B` |
| `F_TRIG` / `RF_TRIG` | спад / фронт и спад | `CLK:B` \| `Q:B` (один цикл) |
| `BLINK` | мультивибратор | `RUN:B Tpls:I Tprd:I` \| `Q:B P:I T:I` |
| `PULSE` | одновибратор | `CP:B Reset:B Tpls:I` \| `Q:B P:I` |
| `HYSTER` | порог с гистерезисом | `X:R H:R EPS:R` \| `Q:B` |
| `LIM_ALRM` | верхний/нижний предел | `H:R X:R L:R EPS:R` \| `QH:B Q:B QL:B` |
| `CMP_R` | сравнение REAL | `VAL1:R VAL2:R` \| `LT:B EQ:B GT:B` |
| `SEL_R` / `MUX4_R` | выбор | `SEL:B X1:R X2:R` \| `Q:R` |
| `FILTER` | экспоненциальный фильтр | `RUN:B X:R TF:R Cycle:I` \| `Y:R` |
| `LIMIT` | ограничение INTEGER | `MIN:I IN:I MAX:I` \| `Q:I` |

Проверено в эмуляции: CTU от BLINK досчитал до `PV`=5 и держит `CV`=5, сброс
обнуляет; RS ставится по `a > b` и помнит состояние; неподключённые выходы ФБ
(`P`, `T` у BLINK) сборке не мешают.

## Правка чужой схемы

Порядок, проверенный 2026-09-13 на двух схемах (нарисованная мышью `fbd_test`
и заготовка `project_FBD` без единой связи):

1. **Копия каталога** проекта и отдельная копия исходного `prog.json` — для диффа.
2. **Разобраться**: `fbd_dump.py prog.json --blocks --links` — что делает схема,
   какие блоки висят, чего не хватает.
3. **Словарь**, если нужны новые переменные: полный `<программа>.import.csv`
   (строки `prog.csv` + новые через `var_csv_row()`), заход IDE «открыть →
   сохранить → закрыть», проверить, что строки дошли.
4. **Правка файлом** через API (проект закрыт) и `save()` — валидация.
5. **`fbd_diff.py до.json после.json`** — удалено / добавлено / переставлено,
   изменился ли порядок выполнения, какие выражения поменялись.
6. **Открыть → «Вывести код на ST» → сборка → эмуляция.**
7. Если правили ещё и мышью — сохранить и снова `fbd_diff.py`: IDE после правки
   мышью перенумеровывает порядок по расположению блоков.

### API правки (`fbd_gen.py`)

```python
from fbd_gen import Scheme, var_csv_row
s = Scheme.load('tasks/main/logic/prog.json')          # все поля блоков сохраняются
plus = s.one('+')                                        # поиск по name / column / line / type
sumr = s.one('sum_real')
s.move(sumr, column=44, line=11)
mul = s.op('*', 2, 32, 11)
link = [l for l in s.links_of(plus, out=True) if l['dst_block'] == sumr['save_id']][0]
s.insert(link, mul, in_slot=0)                           # врезать в связь: + -> * -> sum_real
s.link(s.const('0.5', 'R', 26, 12), mul, 'R', dst_slot=1)
s.delete(s.one('NOT'))                                   # блок вместе со связями
s.rename(s.one('flag2', column=2, line=21), 'or_res')    # сменить переменную, имена связей тоже
s.save('tasks/main/logic/prog.json')                     # порядок старых блоков сохраняется
```

| Метод | Что делает |
|---|---|
| `Scheme.load(path)` | загрузить схему как есть; словарь — `prog.csv` рядом |
| `find()` / `one()` | блоки по `name`, `column`, `line`, `type` (`save_id` не годится — IDE его перенумеровывает) |
| `links_of(b, into=, out=)`, `source(b, slot)` | связи блока |
| `delete(b)` | удалить блок с его связями и eni/eno |
| `unlink(link)` | удалить связь |
| `move(b, column=, line= / dcol=, dline=)` | переставить (eni/eno едет следом), трассы IDE проложит сама |
| `rename(b, name)` | другая переменная того же типа; имена концов связей обновляются |
| `insert(link, block, in_slot, out_slot)` | врезать блок в связь; инверсия связи остаётся у приёмника |
| `resequence()` | порядок: старые блоки — как было, новые — сразу после своих источников (вызывается в `save()`) |
| `compact_ids()` | `save_id` подряд с нуля, связи и eni под новые номера (вызывается в `save()`) |

`var_csv_row(name, t, value, comment)` — строка словаря с проверкой: имя не
совпадает с системным ФБ и словом ST, буква типа из проверенных.

### Мышью

| Функция (`fbd_lib.ps1`) | Команда (`fbd_do.ps1`) | Что делает |
|---|---|---|
| `Remove-FbdBlock -Block` | `delete -DstCell c,l` | выделить блок и «удалить»; связи уходят вместе с ним |
| `Remove-FbdLink -Dst -DstSlot` | `unlink -DstCell c,l -DstSlot n` | клик по проводу у входа и «удалить» |
| `Move-FbdBlock -Block -Column -Line` | `move -DstCell c,l -Column -Line` | перетащить за заголовок в клетку |
| `Undo-Fbd` / `Redo-Fbd` | `undo` / `redo` | «отменить  изменения» / «повторить изменения» |

Проверено: вставка `NOT` между `AND` и результатом мышью (перенос результата,
удаление провода, новый блок, две связи) дала
`and_res := (NOT( ( flag1 AND or_res ) ))`, в файле 22 блока и 17 связей, как и
ожидалось. Отмена многошаговая: удаление → отмена (блок и все три связи на
месте) → повтор → снова отмена.

### Что узнали на правке

- **Правка мышью перенумеровывает `sequence` всей схемы по расположению.** После
  переноса цепочки OR ниже цепочки AND (файлом) порядок в коде был прежним, но
  первая же правка в редакторе поставила OR последней — AND стала читать
  `or_res` прошлого цикла. `fbd_diff.py` это ловит: «порядок выполнения ИЗМЕНИЛСЯ».
- **Имена в связи должны совпадать с именем блока.** Сменили `name` у блока, а
  `src_name` в связи оставили: код генерируется по `save_id` и верен, но провод на
  схеме не рисуется, а при первой правке в редакторе (даже при отмене) связь
  теряется — «входы оператора не присоединены». `Scheme.rename()` обновляет обе.
- IDE переписывает `save_id` подряд и `src_name`/`dst_name` по блокам.
- Перенесённый мышью блок остаётся выделенным красной рамкой; пока выделение не
  снято, пиксельный детектор блок не видит (`Move-FbdBlock` снимает сам).

### Геометрия (проверено 2026-09-13)

### Как это устроено и почему так

- **Режимы.** Кликом мыши «режим редактирования» и «режим соединения»
  взаимоисключающие, и `ToggleState` после клика верен. `TogglePattern.Toggle()`
  меняет только вид кнопки — отсюда когда-то и было «включены оба режима».
- **Связь — два клика в любом порядке**: выход → вход или вход → выход.
  Выбранный вывод помечается **пурпурной точкой**. Клик по пустому месту
  выбор снимает. Если второй клик промахнулся, выбор остаётся «висеть» и
  съедает следующий клик — связь уходит не туда. Поэтому перед каждой связью
  `Clear-FbdSelection`, после первого клика — проверка точки, после второго —
  проверка провода.
- **Проверка провода**: тёмная линия в полоске шириной ½ клетки левее входа на
  строке вывода. Тёмное = серое/чёрное (max RGB < 200), пурпурная точка сюда не
  попадает.
- **Клик по выводу — внутри блока** (0,6 клетки от края). Прежняя беда «провод
  перехватывает клик» была следствием кликов по кромке: при кликах внутри блока
  она не воспроизводится.
- **Размещение.** Точка отпускания — левый верхний угол блока:
  `x = поле.X + sx·column + sx/4`, `y = поле.Y + sy·(line − строк_заголовка) − sy/4`.
  Цель заранее выводится в середину поля.
- **ФБ из словаря тащат за узел метода**: раскрыть экземпляр `_TON_1` и тащить
  дочерний `TON`. Сам экземпляр не перетаскивается.
- **Комбобоксы панели**: `SetValue`, `Select()` и `Invoke()` значение не меняют.
  Работает клик по пункту раскрытого списка; координаты пунктов в UIA —
  смещения `(0, 19·N)` от окна всплывающего списка.
- **Поиск элементов**: `FindAll` с условием в 10–50 раз быстрее обхода дерева
  (`Get-UmAllElements`): 40 мс против 500.
- **Сохранение кнопкой** синхронное: к возврату из `Invoke` файл уже записан.
- **Элементы без списка** (константа, метка, прыжок, шина, соединение) ставятся
  перетаскиванием значка-руки «Применить в программе» на клетку поля; клик по
  значку не делает ничего. Значение (число константы, имя метки) набирается с
  клавиатуры — `ValuePattern.SetValue` в это поле не проходит. Пиксельная
  проверка блока работает для константы, но не для метки, шины и прыжка — их
  сверять по файлу.
- **Клик по значку палитры иногда не доходит**: `Select-FbdPalette` теперь
  проверяет верхний комбобокс и повторяет клик до трёх раз.
- **Связь фиксируется только следующей правкой блока** (проверено 2026-09-14
  пошагово, с сохранением и чтением файла после каждого шага). После проведения
  связи провод нарисован, но у вкладки не появляется « *», сохранение пишет схему
  без связи, «Вывести код на ST» её не видит. Щелчок по полю, смена режима, пауза,
  повторное сохранение, сдвиг блока в пределах клетки — не помогают. Помогают
  перенос блока, удаление блока или связи, новый блок: все висящие связи разом
  попадают в модель. `Submit-FbdLinks` делает перенос туда и обратно.
- **Размер поля** — из `Define` схемы, прочитанной `Read-FbdProg` (запоминается в
  `$script:FbdGrid`). Шаг клетки = (максимум полосы + ширина поля) / `column_max`.

## Что чем ставится

| Элемент | `type` | Обязательные поля сверх общих | Имя |
|---|---|---|---|
| переменная | 0 | `dict=0`, `mode=4` | имя из словаря программы |
| константа | 1 | `subtype=0`, `dict=3`, `mode=0` | сам литерал: `3000`, `2.5`, `true` |
| оператор | 4 | `subtype` (0 — один вход, 1 — два и больше), `args` при 3+ входах, `dict=3`, `mode=0` | ST-токен: `:=`, `+`, `AND`, `SQRT`, `INT_TO_REAL` |
| функциональный блок | 3 | `dict=0`, `mode=4`, имена выводов | `<экземпляр>.<ФБ>`, например `_TON_1.TON` |
| eni/eno | 13 | `block` = `save_id` ФБ, `line` ФБ − 2, `subtype=0`, `dict=0`, `mode=4` | имя ФБ; выводы `eni` / `eno` BOOL |
| функция проекта | 15 | `dict=3`, `mode=0`, входы — параметры функции с их типами, один выход | имя функции (и то же имя у выхода) |
| дочерняя программа | 16 | `dict=3`, `mode=0`, входы — параметры (`Attribute 1`), один выход | имя дочерней программы |
| метод структуры | 3 | как ФБ: `dict=0`, `mode=4`, входы — поля `inout 1`, выходы — поля `inout 2` | `<экземпляр>.<метод>` |
| структура с полями | 2 | `dict=0`, `mode=4`, все поля и во входах, и в выходах | имя экземпляра |
| структура целиком | 12 | `dict=0`, `mode=4`, один вход и один выход типа 32 | имя экземпляра |
| комментарий | 14 | `dict=3`, `mode=1`, `sequence=-1`, без выводов | текст комментария |

Общие обязательные поля: `save_id`, `sequence`, `column`, `line`, `type`,
`name`, `dict`, `mode`, `inp_count`, `out_count` и тип каждого вывода. Пустые
`inpN_name` / `outN_name` у переменных можно не писать.

**Функциональный блок**: экземпляр заводится строками в словаре программы
(`<программа>.import.csv` в корне проекта, UTF-8):

```
_TON_1;U;;TON;4;;0;;false;0;;;;;;false;;;;;Таймер по фронту
_TON_1.IN;B;;;;0;1;;false;0;0;0;;;;false;0;0;0; ;TRUE - запустить таймер
_TON_1.PT;I;;;;0;1;;false;0;0;0;;;;false;0;0;0; ;Время отсчёта (мсек)
_TON_1.Q;B;;;;0;2;;false;0;0;0;;;;false;0;0;0; ;TRUE - если PT истекло
_TON_1.ET;I;;;;0;2;;false;0;0;0;;;;false;0;0;0; ;Текущее время
```

`Library` — имя ФБ, `Length` — число полей, `Attribute` 1 — вход, 2 — выход.
Для системных ФБ в `types/` ничего не нужно. Импорт словаря **заменяет**
словарь программы целиком. Схема с ФБ даёт на ST вызов метода:
`_TON_1.IN := flag1; _TON_1.PT := 3000; _TON_1.TON(); and_res := _TON_1.Q ;`

## Структуры, дочерние программы, массивы

Проверено 2026-09-18 (`fbd_j`, копия `s2_lab`): всё это ставится и файлом, и
мышью, собирается и считает в эмуляции то же, что ST.

| Что нужно | Блок | Как в коде ST |
|---|---|---|
| вызвать метод структуры | `type 3` (как ФБ), имя `<экземпляр>.<метод>`; входы — поля с `inout 1`, выходы — поля с `inout 2` | `t2.Level_pct:=…; t2.calc(); s_vol := t2.Volume_m3 ;` |
| записать и прочитать поля экземпляра | `type 2` «структура с полями»: все поля и на входах, и на выходах | `_tank_1.Level_pct:=arr_sum; s_pct := _tank_1.Level_pct ;` |
| скопировать структуру целиком | два блока `type 12` «структура» (вывод типа 32), связь между ними | по присваиванию на каждое поле: `_tank_2.Level_pct:=t2.Level_pct;` и так все |
| вызвать дочернюю программу | `type 16`, `dict 3`, `mode 0`; входы — параметры (строки словаря с `Attribute 1`), выход назван её именем | `y_lim := ch_lim(x_in) ;` |
| элемент массива | обычный блок переменной с именем `buf[1]`, `g_mat[1,2]`, `abuf[idx]` | `buf[0] := ( s_vol ) ;`, `buf[2] := ( g_real[0] ) ;` |

```python
s.struct_call('t2', 'calc', line=3,
              ins={'Level_pct': 'sim_main.t1.Level_pct', 'Area_m2': K('3.0', 'R'),
                   'H_max_m': K('5.0', 'R'), 'SP_hi': K('80.0', 'R'), 'SP_lo': K('20.0', 'R')},
              outs={'Volume_m3': 's_vol', 'Alarm_hi': 's_alm'})
s.child_call('ch_lim', line=s.next_line, ins={'x': 'x_in'}, out='y_lim')
s.expr('arr_sum', Op('+', 'buf[0]', 'buf[1]', 'buf[2]'), line=s.next_line)   # массив как переменные
sf = s.struct_fields('_tank_1', line=L, column=20)     # запись поля и чтение его же
s.link(a, s.struct_pin('_tank_2', line=L2, column=20)) # копия структуры целиком
```

Поля структур генератор берёт из `types/structs.json` (`struct_catalog(root)`),
параметры дочерней — из её `prog.csv` (`Scheme.child_params`), типы элементов
массива — из словаря программы, как у обычных переменных.

Что важно помнить:

- **Экземпляр структуры заводится словарём** (`t2;U;;tank;9;…` — `Library` = имя
  структуры, `Length` = число полей); поля и элементы массива IDE разворачивает
  сама. Массив — одна строка: `buf;A;;R;[4];…`.
- **Блок структуры, поставленный мышью, создаёт новый экземпляр** в словаре
  программы: `_tank_1`, `_tank_2` — как `_TON_1` у ФБ. Если нужен свой экземпляр,
  заводить его импортом словаря заранее и ставить блок файлом.
- **Параметр дочерней программы — строка словаря с `Attribute 1`.** С `Attribute 0`
  блок дочерней получается без входов, и вызов выходит `ch_lim()`. Возвращаемое
  значение — строка с именем самой программы (`Attribute 2`), её создаёт IDE.
- Дочернюю программу видно **только из её родителя**; в палитре «Дочерняя
  программа» перечислены дочерние текущей программы.
- Значения элементов массива в словаре видны, только когда строка массива
  раскрыта; в свёрнутом виде колонка «Значение» пустая.
- Проверено в эмуляции: объём, посчитанный методом структуры на схеме, совпал с
  объёмом ST до последнего знака; дочерняя программа ограничила значение сотней;
  сумма по элементам массива сошлась; поле, записанное блоком `type 2`, тут же
  читается его выходом.

## LD: релейные цепи, метка и прыжок

Проверено 2026-09-18 (`fbd_k`): цепи собираются, компилируются и работают в
эмуляции. Элементы LD спокойно живут в FBD-программе.

| Элемент | Блок | Что в коде ST |
|---|---|---|
| левая силовая шина | `type 5`, `subtype 0`, поле `slots` (3 выхода) | питание цепи — это `( TRUE )` |
| правая силовая шина | `type 5`, `subtype 1` (3 входа) | ничего |
| контакт | `type 8`, `subtype` 0 прямой, 1 инвертированный, 2 (N), 3 (P) | `( TRUE ) AND a`, `AND (NOT(c ))` |
| виток | `type 7`, `subtype` 0 прямой, 1 инв., 2 (N), 3 (P), 4 (R), 5 (S) | `q1:=…;` или `if … then q2:=TRUE; end_if;` у (S) |
| метка | `type 9`, выводов нет | строка `skip_here:` |
| прыжок | `type 10`, один вход BOOL | `if flag_j then goto skip_here; end_if;` |

```python
busL = s.bus('left', line=4, column=2)          # одна пара шин на три цепи
busR = s.bus('right', line=4, column=60)
for k, (cname, ckind, qname, qkind) in enumerate(rungs):
    ct = s.contact(cname, line=4 + k, column=16, kind=ckind)   # 'direct' | 'inv' | 'N' | 'P'
    cl = s.coil(qname, line=4 + k, column=40, kind=qkind)      # + 'R' | 'S'
    s.link(busL, ct, 'B', src_slot=k); s.link(ct, cl, 'B'); s.link(cl, busR, 'B', dst_slot=k)
s.link(s.var('flag_j', 2, 12), s.jump('skip_here', line=12, column=20), 'B')
s.label('skip_here', line=17, column=2)
```

- Одна шина обслуживает **три** цепи: у неё три вывода (`slots`), цепь k цепляется
  к выводу k на строке `line + k`.
- **Контакт по фронту (P) и по спаду (N)** IDE разворачивает через скрытую
  переменную: `q3:=( TRUE ) AND (trig_in AND (NOT _temp_front_7 ));`, а в конце
  программы дописывает `_temp_front_7:=trig_in;`. Точный текст не воспроизвести,
  поэтому `fbd_dump.py` помечает такие цепи как `<фронт/спад>`, а `--check-st`
  их пропускает с обеих сторон.
- Проверено в эмуляции: прямой контакт → прямой виток повторяет переменную;
  виток (S) держит значение после снятия условия.

## Массивы на схеме

- Элемент массива — **обычный блок переменной** с именем `abuf[1]`, `arr3[1,1,1]`,
  `g_mat[1,2]`: локальный `dict 0`, глобальный `dict 1`.
- **Индекс может быть переменной**: `abuf[idx]` работает и на чтение, и на запись
  (проверено в эмуляции: при `idx=1` запись ушла именно в `abuf[1]`). Индекс —
  целая переменная словаря; генератор проверяет это сам (`Scheme.elem_type`).
- Массив объявляется одной строкой словаря; **трёхмерный тоже**:
  `arr3;A;;R;[2,2,2];…` — IDE разворачивает восемь элементов `arr3[0,0,0]` …
- В словаре в эмуляции значения элементов видно только у раскрытой строки массива.

## Функция проекта на схеме

Функция ставится блоком `type 15` (`dict 3`, `mode 0`): входы — параметры функции
в порядке объявления, единственный выход назван именем функции, тип выхода — тип

s.func_call('norm_pct', line=3,

## Каталог операторов

Операторы опознаются в файле по имени — токену ST. Токены из палитры редактора
(панель «Добавить/Изменить» → «Оператор»), жирным — проверенные записью файла
и полученные в коде на ST.

| Категория | Токены |
|---|---|
| Присваивание | **`:=`** · `A_TO_R` · `R_TO_A` |
| Арифметические | **`+`** · **`-`** · **`*`** · **`/`** · `NEG` · `ROL` · `ROR` · `SHL` · `SHR` |
| Логические | **`AND`** · **`OR`** · **`XOR`** · **`NOT`** |
| Поразрядные для целых | `AND_MASK` · `OR_MASK` · `XOR_MASK` · `NOT_MASK` |
| Поразрядные для байтов | `BYTE_AND_MASK` · `BYTE_OR_MASK` · `BYTE_XOR_MASK` · `BYTE_NOT_MASK` |
| Сравнение | **`<`** · **`<=`** · **`>`** · **`>=`** · `=` · **`<>`** |
| Преобразование типов | **`INT_TO_REAL`** · **`REAL_TO_INT`** · **`REAL_TO_BOOL`** · … — `<ИЗ>_TO_<В>` для BOOL, INT, REAL, TIME, STRING, BYTE, DOUBLE (в палитре двухуровнево: «из целого значения (INT)» → «в вещественное (REAL)») |
| Математические | `SIN` · `COS` · `TAN` · `ASIN` · `ACOS` · `ATAN` · **`SQRT`** · `POW` · `EXPT` · `LOG` · `MOD` · **`ABS`** · `ODD` · `TRUNC` · `RAND` |
| Системные | `System` · `TSTART` · `TSTOP` |
| Сервисные | **`GETBIT`** · `GETBYTE` · `SETBIT`✗ · `SETBYTE` · `MLEN`✗ · `CHAR`✗ · `ASCII`✗ · `TO_IP_ADDR` · `FROM_IP_ADDR` · `CHECK_DOUBLE` · `CHECK_FLOAT` · `TIME_TO_UNIX` · `TIME_FROM_UNIX` · `TO_EUHI` · `FROM_EUHI` |

Проверено сборкой 2026-09-18 (жирным — прошли): `NEG`, `SHL`, `SHR`, `ROL`, `ROR`,
`OR_MASK`, `XOR_MASK`, `NOT_MASK`, `AND_MASK`, `GETBIT`, `MOD`, `ODD`, `COS`, `TAN`,
`ASIN`, `ACOS`, `ATAN`, `SIN`, `POW`, `EXPT`, `LOG`, `TRUNC`, `RAND`, `=`,
`BYTE_AND_MASK`, `BYTE_OR_MASK`. Сигнатуры, которые пришлось подобрать:

| Оператор | Как надо | Как не работает |
|---|---|---|
| `LOG` | два аргумента: `LOG( r1, i1 )` | один аргумент — «Ошибка 40: неверное количество параметров» |
| `EXPT` | степень целая: `EXPT( r1, i1 )` | `EXPT( r1, r2 )` — «Ошибка 29» |
| `TRUNC` | результат REAL | результат INT — «Ошибка 29» |
| `RAND` | `RAND( i1 )` → INT | `RAND( r1 )` → REAL — «Ошибка 29» |
| `SETBIT`, `MLEN`, `CHAR`, `ASCII` | в палитре есть, но компилятор их не принял ни в одной из проб (ошибки 19/30/58/43) | — |

**Почти все многоаргументные операторы печатаются функцией**, а не инфиксно:
`MOD( i1,i2 )`, `AND_MASK( i1,i2 )`, `POW( r1,r2 )`, `SHL( i1,i2 )`; `NEG` — это
унарный минус `(- i1 )`. Разборщик это учитывает.

В палитре оператор ищется по полному названию: `'Сложение (+)'` в категории
`'Арифметические'`.

## Симптом → причина → лечение

| Симптом | Причина | Что делать |
|---|---|---|
| «Вывести код на ST» печатает только заголовок | в схеме есть блок, ни к чему не подключённый | `fbd_dump.py` покажет такие блоки |
| схема открылась пустой | `Define.block_count` = 0 или меньше числа блоков | пересчитать счётчики (генератор делает сам) |

## Сначала посмотреть, нет ли готового блока

В библиотеке 204 системных ФБ, и половина задач, которые тянет написать руками,
там уже есть: ШИМ (`PWM`), гистерезис (`HYSTER`), ограничение диапазона
(`LIMITR`) и скорости (`LRATE`), зона нечувствительности (`DZONE`), скользящее
среднее (`AVRGD`), интегратор (`INTEG`), задержка сигнала (`DELAY`), защёлка
(`LATCH`), выбор из нескольких (`MUX4_R`, `SEL_R`), максимум и минимум с
номерами каналов (`MAX_MIN4`), работа с массивами (`AR_COPY`, `GETAR`, `SETAR`),
битовые поля (`GETFIELD`, `SETFIELD`), строки (`MID`, `FIND`, `I_TO_S`), время
(`TIME_GET`, `TIME_TO_TEXT`).

```python
from fbd_gen import fb_find, fb_info
fb_find('скорост')            # [('LRATE', 'ограничения скорости изменения сигнала.'), ...]

fb_info('LRATE')['emul']      # 'V — единиц в СЕКУНДУ ...'
```
