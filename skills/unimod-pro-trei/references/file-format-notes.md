# Unimod PRO 2 — карта формата проекта

Подтверждено на: **Unimod PRO 2, версия 2.3.43.15** (сборка от 24.05.2026),
Windows 11. Проверялось на четырёх реальных проектах и на проектах, созданных
экспериментально с нуля.

## Расширения файлов

| Файл | Назначение | Формат | Кто пишет |
|---|---|---|---|
| `*.uprj` | файл проекта (метаданные) | JSON, LF | IDE |
| `*.ua2` | архив проекта целиком | **ZIP с шифрованием** (сигнатура PK, general purpose flag 0x0001) | IDE |
| `*.import.csv` | импорт локального словаря | CSV `;`, UTF-8 | человек/скрипт |
| `import.prj` | импорт структуры проекта | текст с тегами, CRLF | человек/скрипт |
| `prog.import.st` | импорт текста ST-программы | текст | человек/скрипт |
| `*.var` | словарь переменных | **бинарный `umvar`** | IDE |

## Каталог проекта

Проект = подкаталог с именем проекта. Имя: только латиница, цифры, `_`,
начинается с буквы, не длиннее 128 символов.

```
<project>/
├── project.uprj              # JSON: name, uid, last_uid, build_number, app_crc, app_size
├── proj_structure.prj        # список всех POU (пишется при сохранении)
├── configuration.json        # контроллер, сеть, линии связи, Modbus, OPC, IEC104, МКО
├── settings.ini              # параметры подключения к ПЛК, счётчик сборок (INI, CRLF)
├── usr.cfg                   # пользователи/роли/пароли проекта (INI, CRLF)
├── unet.xml                  # выгрузка тегов для OPC (генерируется)
├── modified.list             # служебный, часто пустой
├── cache.tmp                 # ЛОК открытого проекта: pid, имя, хост, uuid; удаляется при закрытии
├── project.ua2               # авто-архив проекта, создаётся при сохранении
├── tags/
│   ├── global.var            # ГЛОБАЛЬНЫЙ СЛОВАРЬ — источник истины (бинарный)
│   ├── global.csv            # зеркало глобального словаря (UTF-8, LF)
│   └── base.csv              # база тегов для сборки (CP1251, LF) — генерируется
├── tasks/main/               # задача всегда одна и всегда называется main
│   ├── task.json             # cycle, name, num, priority, programs[] — ПОРЯДОК ВЫЗОВА
│   └── <имя_программы>/
│       ├── prog.json         # ИСТОЧНИК ИСТИНЫ: name, uid, lang, childPrograms, text{md5, st}
│       ├── prog.st           # зеркало текста (CRLF)
│       ├── prog.csv          # зеркало локального словаря (UTF-8, LF)
│       └── prog.var          # локальный словарь — источник истины (бинарный)
├── functions/
│   ├── functions.json        # ИСТОЧНИК ИСТИНЫ по всем функциям: tags[] + text{}
│   └── <имя_функции>/prog.{json,st,csv,var}   # то же, что у программ
├── types/
│   ├── structs.json          # ИСТОЧНИК ИСТИНЫ: структуры, их словари и код их ФБ
│   ├── arrays.json           # определения массивов
│   ├── <Структура>.<ФБ>.st   # зеркало кода ФБ (CRLF)
│   ├── <Структура>.<ФБ>.csv  # зеркало словаря структуры (UTF-8, LF)
│   └── io/module<N>.{xml,lib}# описания модулей ввода-вывода, используемых в проекте
├── varLists/varLists.json    # списки слежения
└── app/                      # РЕЗУЛЬТАТ СБОРКИ (бинарники)
    ├── project.app           # само технологическое приложение
    └── tag.cfg, master.cfg, common.prj
```

## Минимальный пустой проект (эталон в assets/skeleton/)

Ровно 11 файлов. Всё остальное создаётся при сохранении и сборке:

```
project.uprj  configuration.json  unet.xml  usr.cfg
functions/functions.json    tags/global.csv   tags/global.var
tasks/main/task.json        types/arrays.json types/structs.json
varLists/varLists.json
```

`project.uprj` пустого проекта:

```json
{"app_crc":0,"app_size":0,"build_date":"","build_number":0,
 "fileversion":1,"last_uid":"4096","name":"<имя>","uid":"","version":1}
```

Поле `name` должно совпадать с именем каталога проекта.

## Модель POU: чем Unimod отличается от классического МЭК

- **Задача ровно одна и всегда `main`** (каталог `tasks/main/`). Нескольких задач
  не бывает. Период цикла — `task.json` -> `cycle` (мс), порядок вызова программ —
  массив `programs[]`.
- **Функциональный блок — это МЕТОД СТРУКТУРЫ**, а не самостоятельный объект.
  ФБ адресуется парой `<структура>,<имя_ФБ>`. Его словарь — это словарь данных
  структуры-владельца. Вызов из программы: `<экземпляр>.<ФБ>()`.
- **Структура** (`STRUCTED_UNIT`) — пользовательский тип. Её переменные лежат в
  `structs.json` -> `struct_defs[].tags[]`, её ФБ — в `struct_defs[].programs[]`.
- **Функция** возвращает значение через переменную, одноимённую с функцией
  (в `functions.json` первый тег = имя функции = возвращаемое значение).

## proj_structure.prj / import.prj

Один и тот же формат. `proj_structure.prj` пишет IDE при сохранении;
`import.prj`, положенный в корень, IDE читает при открытии и создаёт объекты.

```
<PROGRAM>
имя_программы,ST,
</PROGRAM>

<FUNCTION>
имя_функции,ST,R,
</FUNCTION>

<STRUCTED_UNIT>
имя_структуры,
</STRUCTED_UNIT>

<FBLOCK>
имя_структуры,имя_ФБ,ST,
</FBLOCK>

<CHILD_PROGRAM>
имя_дочерней,ST,R,имя_родителя,
</CHILD_PROGRAM>
```

Третье поле в секции `FUNCTION` — буква типа возвращаемого значения.
В секции `CHILD_PROGRAM` поля: имя, язык, **буква типа выходной переменной**,
имя родительской программы. Проверено 2026-09-12: `child_sq,ST,R,sim_main,` в
`import.prj` создал дочернюю программу с выходом REAL. Созданная через GUI
получает `B` (булевский выход), и буква меняется, когда в словаре дочерней
программы меняют тип выхода.
Все пять секций обязательны, даже пустые. Переводы строк — CRLF.

**Язык программы.** В `import.prj` принимаются и `ST`, и `FBD`, и `FBD/LD`.
IDE нормализует запись: в `proj_structure.prj` пишет `ST` либо **`FBD`**,
а в `prog.json` — `"lang": "st"` либо **`"lang": "fbd"`**. Проверено
2026-09-10: две программы, объявленные как `fbd_a,FBD/LD,` и `fbd_b,FBD,`,
создались одинаково с `lang: fbd`.

Пустая FBD-программа на диске выглядит как обычная: `prog.json` (с `lang: fbd`
и пустым `text`), `prog.csv`, `prog.var` на 26 байт. Проект с пустыми
FBD-программами собирается без ошибок.

## Формат FBD-программы (разобран 2026-09-12)

У программы с `lang: fbd` поле `text` содержит **не** `md5`/`st`, а три массива:

```json
"text": {
  "Define": [{"block_count": 3, "column_max": 500, "line_max": 500,
              "track_count": 2, "version": 0}],
  "Blocks": [ … ],
  "Links":  [ … ]
}
```

`Define` — всегда один элемент: `block_count` — число блоков, `track_count` —
число линий связи, `column_max`/`line_max` — размер поля в клетках. IDE пишет
500×500, но принимает и сохраняет 1000 и 5000 — клетка при этом та же, растёт
прокрутка (проверено 2026-09-14). Блоки с `column`/`line` вне поля (в том числе
отрицательными) компилируются, но не видны.

**Блок** (`Blocks[]`):

| Поле | Смысл |
|---|---|
| `save_id` | идентификатор блока внутри программы, на него ссылаются связи |
| `sequence` | **порядок выполнения схемы**; читается из файла, после правки мышью IDE пересчитывает его по расположению результатов — правило в «Что IDE меняет при сохранении схемы» |
| `column`, `line` | позиция: `column` — левый край блока, `line` — строка первого вывода |
| `type` | вид элемента, полная таблица кодов ниже |
| `subtype` | у оператора: `0` — один вход (`:=`, `NOT`, `REAL_TO_INT`), `1` — два и больше (`+`, `AND`, в том числе на 3–4 входа); у константы 0; у LD-элементов — вид (см. таблицу кодов) |
| `args` | **число входов оператора, если их больше двух** (AND, OR, +, * на 3+ входа). Без него IDE при первом сохранении обрезает оператор до двух входов и выбрасывает лишние связи. Проверено 2026-09-13 |
| `dict` | `0` — локальный словарь программы (в том числе `программа.переменная` другой программы), **`1` — глобальный словарь**, `3` — встроенный элемент (константа, оператор, комментарий) |
| `mode` | `4` у блоков из локального словаря, **`0` у глобальной переменной** и у встроенных, **`1` — блок закомментирован** (тогда `sequence` = −1, а все его связи тоже `mode 1`) |
| `block` | только у eni/eno (`type 13`): `save_id` ФБ, к которому относится |
| `name` | переменная — `local_var_0001`, константа — `false`, оператор — `:=`, ФБ — `<экземпляр>.<ФБ>` (`_TON_1.TON`) |
| `inp_count`, `out_count` | число входов и выходов |
| `inpN_name`, `inpN_type`, `outN_name`, `outN_type` | имя и тип каждого вывода |

Коды `type` — проверено размещением каждого элемента палитры:

| `type` | Элемент | Примечание |
|---|---|---|
| 0 | переменная | `dict 0`, `mode 4` |
| 1 | константа | `subtype` = код типа (0 BOOL, 1 INT, 2 REAL, 5 BYTE, 6 DOUBLE), `name` — само значение: `false`, `4242`, `2.5`, `b#7`, `d#1.5` |
| 2 | структура с полями | `dict 0`, `mode 4`; все поля экземпляра и во входах, и в выходах (одни и те же имена и типы). Запись во вход = `<экземпляр>.<поле> := …;`, чтение с выхода = `… := <экземпляр>.<поле>` |
| 3 | функциональный блок | `name` = `<экземпляр>.<ФБ>` |
| 4 | оператор | опознаётся по `name` (токен ST); `subtype` 0/1, `args` при 3+ входах |
| 5 | шина (LD) | `dict 3`, `mode 0`, имя пустое, `subtype` 0 левая силовая (3 выхода), 1 правая (3 входа), поле **`slots`** — число выводов (IDE пишет 3). Левая шина в коде — это `( TRUE )` |
| 7 | виток (LD) | `dict 0`, `mode 4`, имя — булевская переменная, один вход и один выход; `subtype` 0..5: прямой, инвертированный, (N), (P), (R), (S). Прямой даёт `q:=<выражение>;`, (S) — `if <выражение> then q:=TRUE; end_if;` |
| 8 | контакт (LD) | `dict 0`, `mode 4`, имя — булевская переменная; `subtype` 0..3: прямой, инвертированный, (N), (P). Контакты (N)/(P) IDE разворачивает через скрытую переменную `_temp_front_N`, которой в схеме нет |
| 9 | метка | `dict 3`, `mode 0`, имя — цель прыжка, выводов нет; в коде строка `skip_here:` |
| 10 | прыжок | `dict 3`, `mode 0`, один вход BOOL (условие), `name` — цель: `Return` или имя метки; в коде `if cond then goto skip_here; end_if;` |
| 12 | структура (целиком) | `dict 0`, `mode 4`; один вход и один выход типа 32 — весь экземпляр. Связь между двумя такими блоками IDE разворачивает в присваивание **каждого** поля: `_tank_2.Level_pct:=t2.Level_pct;` и так далее |
| 13 | eni/eno ФБ | строка над ФБ (`line` ФБ − 2), `block` — `save_id` ФБ, вход `eni` и выход `eno` BOOL, `name` = имя ФБ |
| 14 | комментарий | `dict 3`, `mode 1`, `sequence −1`, выводов нет, текст в `name` (перевод строки рисуется пробелом) |
| 15 | функция проекта | `dict 3`, `mode 0`; входы — параметры функции (`x`, `xmin`, …) с их типами, один выход с именем функции и типом возвращаемого значения; в коде — обычный вызов `pct := norm_pct(h,0.0,5.0) ;` |
| 16 | дочерняя программа | `dict 3`, `mode 0`; входы — параметры дочерней (строки её словаря с `Attribute 1`), один выход с именем программы и типом возвращаемого значения; в коде — `y := ch_lim(x) ;`. Мышью ставится из палитры «Дочерняя программа», где перечислены дочерние текущей программы |

Коды 6 и 11 не встретились. Элементы LD (шина, виток, контакт)
спокойно ставятся и в FBD-программе.

Код типа вывода = `uid_type − 1`: `0` BOOL, `1` INTEGER, `2` REAL, `3` TIMER,
`4` MESSAGE, `5` BYTE, `6` DOUBLE; `-1` — «любой» (входы операторов).

**Связь** (`Links[]`):

```json
{"src_block": 1, "src_slot": 0, "src_name": "local_var_0001", "src_type": 2,
 "dst_block": 4, "dst_slot": 0, "dst_name": ":=.in1",         "dst_type": 2,
 "mode": 0}
```

- `src_block`/`dst_block` — `save_id` блоков, `slot` — номер вывода с нуля;
- `type` на обоих концах одинаковый — типы данных обязаны совпадать;
- `name` — имя вывода, у операторов с уточнением (`:=.in1`, `:=.out`);
- `mode` — **0** обычная связь, **1** закомментированная (рисуется серым, для
  проверки и генерации кода её нет: «входы оператора не присоединены»),
  **2** инвертированная (кружок у приёмника, в коде `NOT` над значением:
  `( flag1 AND (NOT flag2 ) )`). Проверено 2026-09-13 через контекстное меню
  «Инвертировать» / «Закомментировать» / «Раскомментировать»;
- на один вход — **одна** связь, выход можно ветвить на несколько входов.

Проверено: схема `переменная → := → переменная`, собранная мышью в редакторе,
даёт код `local_var_0001 := ( local_var_0001 ) ;` («Сборка → Редактор →
Вывести код на ST») и собирается в `app/project.app`. Рецепт рисования — в
`gui-guide.md`.

### Схема, записанная файлом (проверено 2026-09-12)

`prog.json`, написанный скриптом, принимается редактором как есть: схема
открывается, рисуется, даёт код на ST и собирается. Проверено на 22 схемах в
песочницах `fbd_b`/`fbd_c`. Рабочий путь и грабли — в `fbd-guide.md`,
генератор и разборщик — `scripts/fbd_gen.py`, `fbd_dump.py`.

**Обязательные поля блока.** Если любого из них нет, IDE **молча выбрасывает
блок** (вместе с его связями) — ни диалога, ни записи в «Списке ошибок»,
кнопка «проверить» показывает «ошибок нет»:

`save_id`, `sequence`, `column`, `line`, `type`, `name`, `dict`, `mode`,
`inp_count`, `out_count`, тип каждого вывода (`inpN_type`, `outN_type`), а у
константы и оператора ещё и `subtype`. Пустые `inpN_name`/`outN_name` у
переменных можно опускать. Неизвестный `type` (проверено на 99) — блок так же
выбрасывается молча; связь на несуществующий `save_id` выбрасывается молча.

**`Define.block_count` и `track_count` — не справка, а указание, сколько
читать.** При нуле схема открывается пустой, при заниженном значении часть
блоков и связей пропадает. Считать их обязательно.

**Порядок выполнения берётся из `sequence`, а не из геометрии.** Проверено:
нижняя цепочка (строки 12–13) с номерами 0–2 напечаталась в ST раньше верхней
(строки 5–6) с номерами 3–5. Повторяющиеся номера ломают генерацию: код выходит
обрубком (`sum_real := ;`), «проверить» и сборка дают «Ошибка 19». Правило для
генерации: топологический порядок, источник строго раньше приёмника, номера
уникальны и подряд.

**Операторы опознаются по `name`** — это токен ST, палитра тут ни при чём.
Проверены записью файла и получены в коде: `:=` `+` `-` `*` `/`, `AND` `OR`
`XOR` `NOT`, `<` `<=` `>` `>=` `<>`, `SQRT`, `ABS`. Одноместные печатаются
функцией: `sum_real := SQRT( a_real ) ;`.

**Имя вывода в связи** строится как `<имя блока>.<имя вывода>`: у оператора
`:=.in1`, `+.out`; у ФБ `_TON_1.TON.IN`, `_TON_1.TON.Q`; у переменной и
константы — просто имя блока. Тип на обоих концах одинаковый; у операторов
`inpN_type`/`out1_type` равны −1, а конкретный тип живёт в связи.

**Функциональный блок из файла.** Экземпляр заводится только словарём
(`<программа>.import.csv`, строка `Type=U`, `Library` — имя ФБ, `Length` —
число полей, плюс строки полей с `Attribute` 1/2). Для системных ФБ в `types/`
ничего создавать не нужно. Схема с `_TON_1.TON` даёт вызов метода
(`_TON_1.IN := flag1; … _TON_1.TON(); and_res := _TON_1.Q ;`) и в эмуляции
отсчитывает заданное `PT` время.

**Элемент массива — обычный блок переменной** с именем `buf[1]`, `g_mat[1,2]`
(локальный — `dict 0`, глобальный — `dict 1`). Массив объявляется одной строкой
словаря (`buf;A;;R;[4];…`), элементы IDE разворачивает сама; трёхмерный массив
(`arr3;A;;R;[2,2,2];…`) разворачивается в восемь элементов. **Индекс может быть
целой переменной** — `abuf[idx]` компилируется и работает на чтение и на запись
(проверено эмуляцией 2026-09-18).

**Блок структуры, поставленный мышью, заводит новый экземпляр** в словаре
программы (`_tank_1`, `_tank_2`) — как `_TON_1` у ФБ.

**Переменные — из словаря своей программы, глобального словаря или другой
программы с префиксом.** Имя переменной чужой программы без префикса печатается
в ST как есть, но сборка падает с «Ошибка 19». С префиксом — `big60.any_alm`,
`dict 0`, `mode 4` — собирается и читает переменную `big60` (проверено
эмуляцией 2026-09-14). Глобальная переменная — блок `dict 1`, `mode 0` (так её
ставит палитра «Переменная» → «Глобальный Словарь»).

**Новая FBD-программа, созданная IDE, хранит `text` в форме ST**
(`{"md5": …, "st": ""}`); форма `{Define, Blocks, Links}` появляется, когда в
схеме впервые что-то сохранено. Рукописная схема просто заменяет `text`
целиком.

**Сохранение проекта не переписывает `prog.json` тех программ, которые не
правились в редакторе** — рукописный файл остаётся байт в байт. Сохранение
после открытия без правок дало полностью идентичный файл (проверено sha256).

`prog.csv` локального словаря — **UTF-8** (в отличие от `tags/base.csv`, тот в
CP1251).

### Что IDE меняет при сохранении схемы (проверено 2026-09-13)

Программа, правленная в редакторе, переписывается целиком, и при этом:

- **`sequence` пересчитывается по расположению** после переноса блока,
  удаления блока или связи, добавления блока. Правило (проверено номер в номер
  на 30 схемах 2026-09-14): блоки без исходящих связей по верхнему краю (у
  переменной и константы `line`, у оператора, ФБ, функции `line − 1`), при
  равенстве по `column`; перед каждым — источники обходом в глубину по номерам
  входов, у ФБ после входов eni/eno. Порядок из файла переживает открытие и
  сохранение без правок. `fbd_gen.ide_order()` повторяет правило.
- **Связь, проведённая мышью, в сохранение не попадает**, пока после неё не
  будет правки блока (у вкладки нет « *», код ST её не видит).
- `src_name`/`dst_name` связей переписываются по именам блоков. Код генерируется
  по `save_id`, а провод рисуется по именам: связь с устаревшим именем в коде
  есть, на схеме не видна и теряется при первой правке в редакторе.
- **`save_id` перенумеровываются подряд с нуля** (после удаления блоков
  номера сдвигаются), связи пересчитываются под новые номера. Опираться на
  `save_id` между сохранениями нельзя — только на `name` + `column`/`line`.
- Оператор без `args` обрезается до двух входов, лишние связи выбрасываются.
- У операторов `-1` в типах выводов заменяется конкретным типом по связям.
- У константы `out1_type` и `src_type` её связи пишутся как `0`, какой бы ни был
  тип значения; компилятор берёт тип по приёмнику. Это не ошибка.

### Константы, преобразования и типы (проверено компиляцией 2026-09-13)

Генератор ST печатает `name` константы как есть, проверяет уже компилятор:

| Запись | Результат |
|---|---|
| `2.5`, `1.0E3`, `(-1.5)` | компилируется |
| `a + -1.5` (без скобок) | «Ошибка 30: Нет закрывающей скобки», «Ошибка 58: Ожидается ;» |
| `1e3` | те же ошибки 30/58 — экспонента только с мантиссой |
| `2,5` | ошибки 30/58/19 |
| `2` в REAL-переменную | «Ошибка 29: Неправильный тип выражения» |
| `1` в BOOL | «Ошибка 29» — только `TRUE`/`FALSE` |
| `-7` в INTEGER, `'abc'` в MESSAGE | компилируется |

**Неявных преобразований нет:** `real := int`, `int + real` — «Ошибка 29».
Преобразование — операторы `<ИЗ>_TO_<В>` из палитры «Преобразование типов»:
`INT_TO_REAL`, `REAL_TO_INT`, `REAL_TO_BOOL`, `BOOL_TO_INT`, … (у них
конкретные типы выводов). Записи `REAL(x)`, `INT(x)` не компилируются
(«Ошибка 58», «Ошибка 19»). `REAL_TO_INT(2.5)` в эмуляции дал `2`.

Номер строки в «Списке ошибок» совпадает с номером строки в «Вывести код на ST».

### Прочее, проверенное на схемах

- Поля экземпляра читаются и пишутся как обычные переменные: блок переменной
  с `name` `_TON_1.PT` или `cnt1.Q` — `_TON_1.PT := ( t_int ) ;`.
- Выход ФБ можно вести прямо во вход другого ФБ (`cnt1.CU:=blink1.Q;`) и во
  вход оператора; неподключённые выходы ФБ сборке не мешают, неподключённый
  выход **оператора** — ошибка «выходы оператора не присоединены».
- eni: `if (flag1) then … cnt1.CTU(); end_if;` — вызов ФБ под условием.
- **Настоящий цикл по связям** (выход `*` на вход `+`, выход `+` на вход `*`)
  рисуется, но «Вывести код на ST» **роняет IDE** (процесс завершается).
- Накопитель и защёлка через два блока одной переменной циклом не считаются и
  работают: защёлка `or_res := (flag1 OR or_res) AND NOT flag2` в эмуляции
  ставится, держится и сбрасывается как положено.

## Формат CSV словаря (он же формат импорта)

Разделитель `;`, кодировка UTF-8, переводы строк LF, шапка обязательна:

```
Name;Type;ADDR_MOD;Library;Length;Value;Attribute;FRD;Save;Access;MOD_BUS_type;MOD_BUS;EDU;Cold_start;Index;Is_Ar;Ar_count;Ar_period;Ar_filter;AlphaServerName;Comment
```

Реально заполняются: `Name`, `Type`, `Library`, `Length`, `Value`, `Attribute`,
`Comment`. Остальное — пустые поля и нули, рабочий шаблон строки:

```
<имя>;<буква типа>;;<библиотека>;<длина>;<значение>;<атрибут>;;false;0;0;0;;;;false;0;0;0; ;<комментарий>
```

`Attribute` (имеет смысл только в словаре данных структуры):
`0` — внутренняя, `1` — входная, `2` — выходная, `3` — вход/выход.
В локальном словаре программы поле игнорируется и обнуляется при импорте.

Для переменной структурного типа в CSV пишется одна строка с `Type=U`, а строки
`<экземпляр>.<поле>` IDE разворачивает сама.

### Массивы в CSV и `types/arrays.json` (проверено 2026-09-12)

В CSV словаря массив — строка-заголовок плюс строки элементов:

```

…
```

`Length` — `[N]` или `[N,M]`. У заголовка поля архивации пустые.

`types/arrays.json` — список типов-массивов:


  тип или uid вложенного типа-массива.
- Двумерный `[2,3]` — две записи: внутренняя `size=3, uid_type_var=3` и внешняя
  `size=2, uid_type_var=<uid внутренней>`.
- Одинаковые типы переиспользуются: локальный `l_buf[3]` из REAL новой записи
  не добавил — взял внутренний тип `g_mat`.

## Формат umvar (*.var) — разобран частично

Читать можно, генерировать нельзя.

```
0x00  "umvar\0"                 магия (6 байт)
0x06  uint16  = 2               версия
0x08  uint32  count             число записей верхнего уровня
0x0c  12 байт нулей             резерв
0x18  записи по 22 байта:
        uint32 uid_type         тип (1=BOOL, 2=INT, 3=REAL, либо uid_type структуры)
        uint32 offset           глобальный индекс/смещение
        uint16 n_attr           сколько указателей на TLV принадлежит записи
        uint32 ptr_attr         смещение на первый слот в таблице указателей
        uint32 ptr_name         смещение на запись имени в пуле строк
        uint32 n_children       число вложенных записей (для структур)
      таблица указателей: массив uint32, по n_attr слотов на запись
      блоки TLV: uint8 tag, uint8 subtag, uint32 len, payload[len]
        tag 0x02          — начальное значение (len 4)
        tag 0x0c          — комментарий (UTF-8, len = длина строки + 2)
        tag 0x04 sub 0x01 — uid (uint64, len 8)
      пул строк: uint8 длина (с учётом завершающего нуля), строка, нулевой байт;
                 конец пула — одиночный нулевой байт
```

Пустой словарь — 26 байт: 24 байта заголовка и два байта хвоста. Байт по
смещению 0x18 у пустых словарей **произвольный** — в разных проектах там
встречались `0x00`, `0x2a`, `0x5c`, `0x74`. Это не маркер и не признак типа
словаря (см. ниже), а просто неинициализированный байт: записей нет, и позиция
0x18 ничем не занята.

Прямой перенос готового `prog.var` в `tags/global.var` НЕ работает — словарь
получается пустым.

Через GUI созданы ровно две глобальные переменные типа BOOL с известными
именами. `tags/global.var` вырос с 26 до 139 байт и разобрался полностью:

```

0x08  02 00 00 00                  count = 2
0x0c  12 нулевых байт
0x18  запись 1 (22 байта):
        01 00 00 00   uid_type = 1 (BOOL)
        02 00 00 00   offset = 2
        01 00         n_attr = 1

0x44  таблица указателей: 4c 00 00 00 | 5a 00 00 00
0x4c  TLV: 04 01 | 08 00 00 00 | uint64 = 534155570   (uid переменной 1)
0x5a  TLV: 04 01 | 08 00 00 00 | uint64 = 904266093   (uid переменной 2)

0x69  10 "g_station_ready" 00       длина 16 = 15 символов + NUL

```

Что из этого следует:

- Структура записи (uid_type, offset, n_attr, ptr_attr, ptr_name, n_children)

- Две подряд идущие BOOL получили `offset` **2 и 3** — логические занимают по

- `uid` у переменных, созданных через GUI, — большие псевдослучайные числа,
  не связанные с `last_uid` из `project.uprj`.
- Про «байт-маркер» на смещении 0x18: **никакого маркера нет**. Проверено на
  пяти проектах — в непустом словаре по этому смещению лежит просто первый байт

  | Файл | байт 0x18 | чем объясняется |
  |---|---|---|
  | `gui_lab/tags/global.var` | `0x01` | первая переменная BOOL, `uid_type=1` |
  | `project1/tags/global.var` | `0x6b` | первая типа `valve`, `uid_type=80314731=0x04C9816B` |

  У пустых словарей записей нет, и там остаётся неинициализированный байт —
  отсюда прежняя путаница с `0x2a`/`0x5c`/`0x00`/`0x74`. Так что структура
  `umvar` разобрана полностью и препятствий к её генерации со стороны «маркера»
  нет.

### Что даёт разбор словаря из семи типов (2026-09-10)

Через GUI создан глобальный словарь из семи переменных всех простых типов,
у одной задано значение `12.5` и комментарий. `global.var` — 428 байт,
разбирается скриптом полностью:

```python
import struct
b = open('tags/global.var','rb').read()
n = struct.unpack_from('<I', b, 8)[0]          # число записей
off = 0x18
for i in range(n):
    uid_type, offset = struct.unpack_from('<II', b, off)
    n_attr = struct.unpack_from('<H', b, off+8)[0]
    ptr_attr, ptr_name, n_children = struct.unpack_from('<III', b, off+10)
    ln = b[ptr_name]                            # длина с учётом NUL
    name = b[ptr_name+1:ptr_name+ln].decode('cp1251')
    off += 22
```

Что уточнилось по сравнению с первым разбором:

- **`n_attr` — это число TLV-слотов записи, и оно зависит от заполненных
  атрибутов.** У переменной без значения и комментария слот один (только uid).
  У переменной со значением и комментарием — три: uid, значение, комментарий.
  Поэтому таблица указателей имеет переменную длину, а не «по одному на запись».
- **TLV с тегом `0x02` — начальное значение.** Для REAL это 4-байтовый float
  little-endian: `12.5` записалось как `00 00 48 41`.
- **Комментарий в TLV `0x0c` хранится в CP1251**, а не в UTF-8. «Давление на
  выходе НПС» лежит как `c4 e0 e2 eb e5 ed ...`. Это отличается от `global.csv`,
  который UTF-8. При чтении `*.var` декодировать только CP1251.
- Строки в пуле имён тоже CP1251 (для латинских имён неразличимо, но
  декодировать надо им).

|---|---|
| `LIBRARY_PATH` | каталог пользовательской библиотеки, по умолчанию `%APPDATA%\TREI\UnimodPRO2\library\` |
| `projects_folder` | каталог проектов по умолчанию (`Documents\UnimodPRO2\`) |

часть проекта**. При переносе проекта на другую машину они не поедут.
Состава списков слежения в реестре тоже нет (искал рекурсивно).

### Что делает «Файл → Сохранить проект как»

Создаёт **полную копию исходников** в подкаталоге с новым именем и переключает
IDE на копию. Каталог берётся из поля «Путь:» диалога (по умолчанию
`Documents\UnimodPRO2\`), а не из расположения оригинала.

Чем копия отличается от оригинала (сверено побайтно):

| Что | Как в копии |
|---|---|
| `app/` | **отсутствует** — результат сборки не копируется |
| `modified.list` | отсутствует |
| `project.uprj` | новое `name`, а `build_number`, `app_crc`, `app_size` сброшены в 0 |
| `usr.cfg` | **новый `idProject`**, и вслед за ним новые `hash$6$` и `dsig$1$` |
| `project.ua2` | свой авто-архив |
| словари `*.var` | содержимое то же |

Отсюда важный вывод про `usr.cfg`: `idProject` — идентификатор экземпляра
проекта, он выдаётся при создании и при копировании, а `hash$6$`/`dsig$1$` от
него производны. Копировать `usr.cfg` между проектами без нужды не стоит.

### `settings.ini` хранит ещё и состояние редакторов

Кроме `[General]` и `[connectionPLC]` в файле появляются секции по имени
программы — например `[fbd_a]` с ключом `Scale=2` (масштаб схемы в редакторе
FBD/LD). Это пользовательские настройки вида, а не часть приложения: при
генерации проекта их писать не нужно, IDE заведёт их сама.

Значения `Scale` (проверено 2026-09-13 правкой `settings.ini` перед открытием):
`1` — клетка схемы 12 × 18 px, `2` (по умолчанию) — 16 × 24, `3` — 22 × 30.
Кнопки «увеличить шрифт»/«уменьшить шрифт» переключают эти же ступени; ключ
записывается при закрытии проекта. Для работы мышью значение знать не нужно —
шаг клетки вычисляется по полосам прокрутки (`fbd_lib.ps1`).

### `varLists/varLists.json` хранит только перечень списков

Объект списка состоит из одного поля `name`. Переменные, добавленные в список
слежения, в файлах проекта **не сохраняются** и теряются при закрытии проекта
(проверено дифом каталога, поиском по файлам и повторным открытием в GUI).

### Созданные, но не используемые глобальные переменные не попадают в base.csv

После сборки в `tags/base.csv` оказались только 27 локальных переменных —
обеих глобальных там нет, хотя в `global.csv` и `global.var` они есть, а сборка
прошла успешно. Похоже, в базу тегов идёт только то, что реально задействовано
в коде. Проверить на глобальной переменной, используемой в программе.

### `usr.cfg` и режимы безопасности (проверено 2026-09-11)

INI-файл с секциями `[role]`, `[function]`, `[user]`, `[system]`,
`[history passwords]`, `[crypto]`. В открытом режиме `[role]`, `[function]`,
`[user]` пустые.

**Однопользовательский режим** («Инструменты → Безопасность → Выбор режима
проекта → Однопользовательский», логин `lab`, пароль `Lab12345`) добавил одну
строку в `[user]`:

```
lab:$6$uToVmM5Q$5171c7b0…d26462:0:3:0:0:0:0:2026/9/11/23/27/59:::
```

- `lab` — логин; `$6$uToVmM5Q$<128 hex>` — хеш пароля: маркер `$6$` (SHA-512
  crypt), соль из 8 символов, но сам хеш записан **в hex** (128 символов = 64
  байта), а не в base64 как у настоящего crypt;
- дальше поля через `:` — `0:3:0:0:0:0`, затем дата установки пароля
  `ГГГГ/М/Д/ч/м/с`, затем три пустых поля. Смысл числовых полей пока не
  разобран (вероятно роль, число оставшихся попыток `3`, флаги блокировки).
- `edition` в `[system]` **остался 0** — режим определяется не этим ключом.
- В `[crypto]` пересчитываются `hash$6$…` и `dsig$1$…` — это подпись
  содержимого файла. **Редактировать `usr.cfg` руками нельзя**: подпись не
  сойдётся (что именно тогда делает IDE — не проверялось).
- Подпись **детерминированная**: после возврата «однопользовательский →
  открытый» строка пользователя удалилась, а `hash$6$` и `dsig$1$` вернулись
  **побайтно к исходным значениям** — `usr.cfg` совпал с оригиналом целиком.
  То есть в подписи нет ни соли, ни времени, только содержимое файла (и,
  видимо, `idProject`). Смена «однопользовательский → открытый» пароля не
  спрашивает — только информационное окно «Изменен режим проекта» с кнопкой OK.

Больше при смене режима не меняется ничего (сравнение с оригиналом:
отличаются только `usr.cfg` и то, что меняется при любом сохранении).

При открытии такого проекта IDE показывает окно **«Введите учетные данные»**.

**Защищённый режим** (из открытого; логин администратора `admin`, пароль
`Adm12345`) добавил в `[user]`:

```
admin:$6$H6DwCbKZ$0c70fbdf…7d082d22:0:2:0:0:0:0:2026/9/11/23/36/46:::
```

Отличие от однопользовательского — **второе числовое поле: `2` у
администратора защищённого режима, `3` у единственного пользователя**
однопользовательского. Судя по всему, это тип учётной записи, по нему IDE и
определяет режим (`edition` остаётся 0 в обоих случаях). Соль снова своя
(8 символов), подпись `[crypto]` пересчитана. `[role]` и `[function]` сразу
после включения режима пустые.

**Политики паролей** (диалог «Настройка политик паролей»: включены «Текст» и
«Цифры», попыток 3 → 5):

```
compositionPassword=3          ; было 0 — «Текст»=1 | «Цифры»=2 (битовая маска)
maxCountFailInputPassword=5    ; было 3
```

- В `usr.cfg` изменения попадают **только при закрытии проекта**: ни
  «Применить», ни `Ctrl+Shift+S` (у администратора кнопки сохранения и так
  неактивны) файл не трогают. Закрыть можно `WM_CLOSE` главного окна — диалога
  «сохранить изменения?» не было.
- Строка пользователя получила **вторую дату**:
  `…:0:2:0:0:0:0:2026/9/11/23/36/46:2026/9/11/23/37/43::` — первая — установка
  пароля, вторая — последний успешный вход (я вошёл как `admin` в 23:37).
- Биты «Специальные символы» и «Переменный регистр» не проверялись (вероятно 4
  и 8).

**Роли и пользователи** (роль `operator`, пользователь `op1` / `Op123456` с
этой ролью):

```
[role]
30:operator
[function]
[user]
admin:$6$H6DwCbKZ$…:0:2:0:0:0:0:2026/9/11/23/36/46:2026/9/11/23/43/15::
op1:$6$elG62X7E$…:0:30:1:0:0:0:2026/9/11/23/52/50:::
```

Формат строки пользователя (поля через `:`):

| № | Пример | Смысл |
|---|---|---|
| 1 | `op1` | логин |
| 2 | `$6$соль$hex` | хеш пароля (SHA-512, соль 8 символов, хеш в hex) |
| 3 | `0` | не выяснено (у всех 0) |
| 4 | `2` / `3` / `30` | **идентификатор роли**: 2 — администратор, 3 — единственный пользователь однопользовательского режима, 30 и дальше — роли из `[role]` (`30:operator`) |
| 5 | `1` у нового `op1`, `0` у остальных | вероятно флаг «сменить пароль при первом входе» (по руководству новый пользователь обязан сменить выданный пароль) |
| 6–8 | `0:0:0` | не выяснено (блокировка, счётчик неудачных попыток — кандидаты) |
| 9 | `2026/9/11/23/52/50` | дата установки пароля |
| 10 | `2026/9/11/23/43/15` | последний успешный вход (пусто, пока не входил) |
| 11–12 | пусто | не выяснено |

**Возврат «защищённый → открытый»** (администратор, «Выбор режима проекта →
Открытый», окно «Изменен режим проекта», закрытие проекта): из `[user]`
удалены **все** пользователи (и `admin`, и `op1`), а `[role]` (`30:operator`),
политики (`compositionPassword=3`, `maxCountFailInputPassword=5`) и
`siemIsLinuxFile=1` **остались** — как и обещает руководство: роли
сохраняются для следующего включения защищённого режима. Значит, «открытый
режим» = пустая секция `[user]`, а не исходный `usr.cfg`.

**Журнал событий безопасности** —
`%USERPROFILE%\Documents\UnimodPRO2\data\log_siem\unimod_siem.log` (не в
проекте; общий для всех проектов пользователя). Текст UTF-8, запись на строку,
поля `ключ=значение` через `;`:

```
timestamp=2026-09-11 23:37:43;Severity=Medium;EventID=1;EventName=Успешная аутентификация пользователя;UserName=admin;ClientAddress=127.0.0.1;ClientHostName=<хост>;ServerAddress=;ServerHostName=;TargetUserName=;TargetAddress=;TargetHostName=;Result=Success;Detail=
```

- `EventID` — **порядковый номер записи в сеансе** (1, 2, 3… и заново в
  каждом сеансе), а не код типа. Тип события — только в `EventName`:
  «Успешная аутентификация пользователя», «Выход из системы», «Роли были
  отредактированы: <роль>», «Добавление пользователя».
- `Result=Success` ставится у аутентификации, у остальных пусто.
- События пишутся в защищённом режиме независимо от `siemIsLinuxFile`.
- В файле остаются записи всех прошлых сеансов, в том числе других проектов, —
  при разборе фильтровать по времени.

`[role]` — строки `<id>:<название>`. `[function]` — функции среды,
разрешённые ролям; у `operator` функций не назначено, секция пуста.
Как назначаются функции — не выяснено: список «Функции» в диалоге не
заполнился (см. `gui-guide.md`). Роль записалась в файл при закрытии
проекта, как и всё остальное в `usr.cfg`.

### Библиотеки вне проекта (проверено 2026-09-11)

Пути берутся из реестра `HKCU\Software\TREI\UnimodPRO2`: `LIBRARY_PATH` =
`%APPDATA%\TREI\UnimodPRO2\library\`, `projects_folder` =
`%USERPROFILE%\Documents\UnimodPRO2\`.

**Системная библиотека** — `%APPDATA%\TREI\UnimodPRO2\library\`:

| Файл / каталог | Что это |
|---|---|
| `types/types.json` | вся библиотека структур, обычный JSON ~132 МБ: `version` (118), `last_uid`, `sys_arrays` (2), `sys_struct_defs` (5842) |
| `types.u2lib` | тот же `types.json` в ZIP с шифрованием (как `*.ua2`) |
| `mods.json` | справочник: `master_defs` (тип мастер-модуля ↔ `typeMaster`: M401E 75, M1201E 76, **M501E 77**, F1001E 79, M101E 81, M102ER 82, S370 83, M515E 84), `protocol_defs` (ST-BUS(N) 1, ST-BUS(S) 3), `series_defs` (серии TREI-5B-04/05, FIRE) |

| `io/ui/*.ui`, `io/master/` | формы и расшифровки для диагностики |
| `docs/` | HTML-справка части блоков (`docs/sys/ADDM.html`, …) |

В `sys_struct_defs` два вида записей:
- `lib_mod_<МОДУЛЬ>` и его блоки (`lib_mod_M558O_v2_in`, `…_param`, …) —
  5630 штук, модульные структуры;
- `lib_struct_<БЛОК>` — 212 системных ФБ. Пример: `lib_struct_SIN_GEN`,
  `lib_id` = "1", в `programs` одна запись `{"name": "SIN_GEN", "inputs":
  ["RUN","T","F"], "outputs": ["Y"], "text": {}, "uid": "137"}` — **текста нет**,
  блок встроен в исполнительную систему.

`lib_id` в описании структуры: "0" — структура проекта, "1" — системная
библиотека, "2" — пользовательская библиотека.

**Пользовательская библиотека** — `%USERPROFILE%\Documents\UnimodPRO2\_userlib\structs.json`
(появляется при первом «Сохранить» на панели). Формат — как `types/structs.json`
проекта: `{"arrays": [], "struct_defs": [ … ]}`, у добавленной структуры
`lib_id` = "2", новый `uid_type`, методы с ST-кодом в `text.st` (base64) и тем
же `md5`, поля `tags[]` как в проекте.

**Журналы IDE** — `%USERPROFILE%\Documents\UnimodPRO2\log\unimod_<дата>_<время>.umlog`,
по файлу на запуск. Двоичный формат со строками в CP1251: «Unimod start.»,
«Пользователь выбрал пункт меню "Сохранить проект"», «… "Сборка"» и т. п. —
можно проверить, какие команды меню действительно выполнились. Пункты меню
«Отладка» в эмуляции туда не попадали.

### Экземпляр системного ФБ в словаре (проверено 2026-09-11)

Переменная типа системного ФБ (`SIN_GEN`, `BLINK`, `CTU`, …) пишется в CSV
словаря **так же, как экземпляр структуры проекта** — тип `U`, в колонке
`Library` имя блока, в `Length` число полей, поля развёрнуты с атрибутом
1 (вход) или 2 (выход):

```
gen1;U;;SIN_GEN;4;;0;;false;0;;;;;;false;;;;;Генератор синусоидального сигналас заданным периодом и фазой
gen1.RUN;B;;;;0;1;;false;0;0;0;;;;false;0;0;0; ;Режим работы
gen1.T;R;;;;0;1;;false;0;0;0;;;;false;0;0;0; ;Период колебаний (сек)
gen1.F;R;;;;0;1;;false;0;0;0;;;;false;0;0;0; ;Фаза колебаний (рад)
gen1.Y;R;;;;0;2;;false;0;0;0;;;;false;0;0;0; ;Основной выход
```

- Комментарий блока в библиотеке двухстрочный; в CSV перевод строки просто
  выброшен (`сигналас`).
- `prog.json` программы и каталог `types/` **не меняются**: описание
  системной структуры в проект не копируется (в отличие от модулей
  ввода-вывода, у которых появляется `types/io/moduleN.*`). Меняются
  `prog.csv`, `prog.var` и `tags/base.csv` (поля получают смещения:
  `sim_main.gen1.RUN;bool;108;…`, `…T;real;109`, `…F;real;113`, `…Y;real;117`).
- Вызов из ST — как метод структуры: `gen1.SIN_GEN(true, PERIOD_S, 0.0);`
  (входы позиционно, в порядке полей), выход читается как `gen1.Y`.

## Конфигурация контроллера: что где лежит (проверено 2026-09-10)

Настройки контроллера разнесены по **двум** файлам, и это неочевидно:

- **`settings.ini`, секция `[connectionPLC]`** — параметры подключения среды
  разработки к контроллеру (раздел дерева «Загрузка/отладка проекта →
  Подключение к PLC_1», гл. 7.1 руководства). Ключи нумерованы по контроллеру:
  `1\name`, `1\IpAddress`, `1\IpAddressRes`, `1\port`, `1\typeSocket`
  (0=TCP, 1=SSL), `1\mtu` (размер фрейма), `1\repeatCount`, `1\ansverTimeout`,
  `1\privateKey`, `1\privateCertificate`, `1\publicCertificatesPath`, плюс
  `size=<число контроллеров>`. Проверено: ввод IP на форме и сохранение меняют
  ровно строку `1\IpAddress=`.
- **`configuration.json`, `controllers[0]`** — всё остальное: имя и тип
  мастер-модуля, резервирование (`reservParam_*`), сеть (`net_*`,
  `remoteAccess_*`, `ethComponents[]`), режим выполнения (`watchdogTime`,
  `runModeParam_*`), аппаратная конфигурация (`stBus*Mode`, `serialPort*`,
  `unit1..4Type/Mode`), линии связи (`communicationLines[]`).

Разница по смыслу: в `settings.ini` — адрес, по которому IDE **сейчас**
достучится до контроллера; в `configuration.json` — адреса, которые будут
**установлены** на контроллер после загрузки приложения. Они могут не совпадать.

`typeMaster` — числовой код мастер-модуля (у M501E это 77). Список доступных
типов в IDE: M401E, M1201E, M501E, F1001E, M101E, M102ER, S370, M515E.

### Модуль ввода-вывода в `configuration.json`

Модуль записывается в `communicationLines[N].modilesIO[]`:

```json
{
  "address": 1,
  "comment": "",
  "libStructUid": 11186,
  "moduleType": 3604,
  "requestTimeout": 0,
  "structName": "mod1",
  "structOffset": 0
}
```

- `structName` — **имя переменной** в глобальном словаре, а не имя типа;
- `moduleType` — заводской код модуля (совпадает с атрибутом `type` в
  `types/io/moduleN.xml`);
- `libStructUid` — `uid_type` модульной структуры (он же в `.lib`);
- `address` — адрес на линии ST-BUS, `requestTimeout` — период опроса (0 =
  каждый цикл).

Источник истины — глобальный словарь: модуль появляется в `modilesIO` только
как следствие переменной модульного типа и исчезает при смене её типа.

### `types/io/` — описание модульных структур

Каталог появляется, **только если в проекте есть модуль ввода-вывода**. На
каждый модуль пишется пара файлов с порядковым номером:

- **`moduleN.lib`** — JSON описания структуры, по форме такой же, как элемент
  `struct_defs` в `types/structs.json`, но одиночный. Ключи верхнего уровня:
  `name` (`lib_mod_M558O_v2`), `comment`, `uid_type` (`"11186"`), `uuid`,
  `lib_id`, `library_version`, `align`, `hidden`, `programs` (пусто — у
  модульных структур нет методов), `tags[]` — дерево переменных с
  `attributes.local_offset` и вложенными `children`.
- **`moduleN.xml`** — заводское описание модуля (UTF-8, CRLF): корень `<CONF
  type="3604" name="M558O" count="32" analog="false">`, внутри `<PARAMS_MST>` и
  блоки `<BLK num= attr= type= struct_name=>` с полями `<VAR size= name=
  comment=>`, где `size` — разрядность в битах (`01`, `08`, `16`, `32`).
  Именно отсюда берутся имена и комментарии переменных модуля.

Одна переменная модульного типа разворачивается в глобальном словаре в ~110
строк: `control` (одинакова у всех модулей), `statistic`, `param`, `in`, `out`.
В `global.csv` корневая строка выглядит так:

```
mod1;U;1;M558O_v2;5;;0;;false;0;;;;;;false;;;;;32-канальный дискретный вывод
```

`Type=U` (структура), `ADDR_MOD=1` — адрес модуля на линии, `Library` — имя
модульной структуры, `Length` — число блоков-детей.

### Modbus в `configuration.json` (что пишет GUI 2.3.43.15)

Связи лежат в корневом массиве `modbus[]` (не внутри `controllers[]`). Через GUI
созданы связи всех пяти видов — коды:

| Раздел дерева | `type` | `mode` |
|---|---|---|
| Modbus-RTU Master | 6 | 0 |
| Modbus-RTU Slave | 6 | 1 |
| Modbus-TCP Master | 8 | 0 |
| Modbus-TCP Slave | 8 | 1 |
| Modbus-UDP Master | 11 | 0 |

`type` — транспорт, `mode` — 0 Master / 1 Slave. Modbus-UDP Master есть в
дереве IDE, но **в руководстве пользователя не описан**.

Все связи несут **один и тот же полный набор ключей** независимо от вида —
последовательные поля остаются и у TCP, сетевые и у RTU:

```json
{
  "comment": "", "enable": true, "mode": 0, "name": "Modbus", "num": 1, "type": 8,
  "ipAddress": "", "ipAddressRes": "", "ipPort": 502, "ipPortRes": 0,
  "maxConnectOnOnePort": 10, "timeoutRetention": 15000,
  "serialPort": 0, "serialPortRes": 0, "speed": 115200, "parity": 0, "stopBits": 1,
  "timeoutAnswer": 1000, "timeoutBeforeAnswer": 0, "timeoutBreach": 0, "timeoutRequest": 0,
  "modbusParameters": [
    {
      "address": 1, "function": 1, "type": 0, "endianness": 0,
      "beginReadDataRemote": 0, "beginReadVariableLocal": "", "readVariablesCount": 1,
      "beginWriteDataRemote": 0, "beginWriteVariableLocal": "", "writeVariablesCount": 1,
      "diagVariable": "", "comment": "", "pollingPeriod": 0,
      "ranges": "", "masksAndOr": "", "isReadTimestamp": false
    }
  ]
}
```

- Новая связь сразу получает **один запрос по умолчанию** (`address 1`,
  функция `01 READ COILS`, булевский, 1 переменная) — и у Master, и у Slave.
- `num` — «Номер связи» (1–99, уникален среди всех Modbus-связей), `name` —
  «Название связи», по умолчанию у всех `Modbus`; IDE не делает имена
  уникальными, в дереве узел называется `<num> <name>`.
- В массиве связи идут **в порядке разделов дерева** (RTU Master, RTU Slave,
  TCP Master, …), а не по `num`.
- Параметры Modbus-TCP Slave на уровне контроллера (макс. соединений, время
  удержания) лежат не здесь, а в `controllers[0]`:
  `modbus_tcpSlaveMaxConnectOnOnePort`, `modbus_tcpSlaveTimeoutRetention`.
- В дереве под связью Master — подузел **«Modbus-запросы»**: таблица запросов
  с кнопками `+`/`-` (адрес устройства, функция, тип данных, порядок байт,
  начальный адрес и массив для чтения/записи, количество, диагностическая
  структура `MODBUS_DIAG`).

### МКО (Treinet) и МЭК-104 в `configuration.json`

**Связь межконтроллерного обмена** — корневой массив `mko[]`. Через GUI
(контекстное меню «Межконтроллерный обмен» → «Добавить связь Treinet») создаётся:

```json
{ "num": 1, "type": 5, "inOut": 0, "enable": 1, "port": 8001,
  "ipAddress1": "0.0.0.0", "ipAddress2": "0.0.0.0",
  "ipAddress3": "0.0.0.0", "ipAddress4": "0.0.0.0",
  "timeout": 3000, "ackTo": 70, "sndPause": 0,
  "dataVarName": "", "diagVarName": "", "comment": "" }
```

**Флаг `enable` имеет разный тип у разных связей:** у Modbus — булев
(`true`/`false`), у МКО — целое (`1`/`0`). При генерации файла не
унифицировать. Отключённая связь («Отключить/Задействовать» в контекстном
меню) компилятором не проверяется: проект с пятью пустыми, но отключёнными
Modbus-связями собрался.

Переменные, созданные кнопками «Добавить в словарь» формы МКО, попадают в
**глобальный словарь**: `mko1_diag;U;;MKO_DIAG;10;…` (10 полей: `not_valid`,
`err_task`, `current_line`, `diag_line_1..4`, `block_poll`, `command`,
`tm_task`) и `mko1_data;U;;tank;9;…` — структура выбранного типа.

`type 5` = Ethernet-res (единственный тип связи), `inOut` — направление,
`dataVarName` — переменная-структура/массив с данными (≤ 65 Кбайт),
`diagVarName` — переменная типа `MKO_DIAG`. В дереве узел называется
`<num> (Ethernet-res)`. Флаг `controllers[0].isTreinet` при этом остаётся
`false`; размер фрейма формы «Межконтроллерный обмен» — `controllers[0].treinetFrame`.

**МЭК-104** разнесён на два места:

- `controllers[0].iec104[]` — задачи связи (кнопка «Добавить задачу» на форме
  «МЭК-104 (Slave)»):
  `{"port": 2404, "k": 12, "t1": 500, "ta": 300, "ksync": false, "timeZone": false}` —
  порт, максимум неподтверждённых APDU, таймаут подтверждения, синхронизация
  меток времени, UTC+0. Ключа `ta` на форме нет.
- корневой `iec104` — общий адрес ASDU и группы переменных (форма «Группы
  переменных», кнопки `+`/`-`):

  ```json
  { "ASDUAddr": 1,
    "groups": [ { "number": 1, "typeUnimod": 0, "type": 1, "sq": 0, "sporadic": false } ] }
  ```

  `typeUnimod` — тип переменных группы в Unimod (0 = логический), `type` — тип
  МЭК-104 (1 для логического: пары кодов 1/30, 7/33, 11/35, 13/36 из
  руководства), `sq` — метод адресации, `sporadic` — спорадическая передача.
  Ключ `groups` появляется только после добавления первой группы; в дереве
  группа — узел `Группа <number>` под «Группы переменных».

**OPC-сервер контроллера** (узел дерева с флажком, в руководстве не описан) —
плоские ключи `controllers[0].opcServerController_*`: `on` (главный флажок),
`separateWarningCritical`, `separateHighLow`, `criticalIsStop`, `enableTrei`,
`enableTreis`, `expandArrays`, `kernelPriority` — по одному на каждый флажок
формы, в том же порядке. Работает на исполнительной системе 2.11 и выше.

### `project.ua2` — зашифрованный ZIP, а не JSON

В корне проекта лежит `project.ua2`, и это **ZIP-архив со снимком всего
проекта**, обновляемый при каждом сохранении (сигнатура `PK\x03\x04`, метод
deflate). Все записи имеют флаг шифрования (`flag_bits & 1`), поэтому прочитать
содержимое обычными средствами нельзя — только список имён и размеров. Тот же
формат у архива, который делает «Файл → Архив проекта → Упаковать проект в
файл». Восстановление — только через IDE («Распаковать проект из файла»).

## Открытые вопросы

- Алгоритм `text.md5`. Проверены и не сошлись: md5 от текста как есть, от
  base64-строки, от файла `prog.st`, от текста с LF вместо CRLF, от текста в
  UTF-8 и UTF-16LE, от «длина+текст». IDE эту сумму не проверяет — при записи
  файла можно ставить любую.
- Полная спецификация `umvar`, в первую очередь — как записать `tags/global.var`.
- ~~Буквы типов для BYTE и DOUBLE~~ — выяснено 2026-09-18: **BYTE — `K`,
  DOUBLE — `N`** (созданы переменные в редакторе словаря, затем такой
  `*.import.csv` принят без падения). `uid_type` у них 6 и 7. Литералы в коде —
  `b#7` и `d#1.5`.
- ~~`prog.import.st`: условия срабатывания~~ — выяснено 2026-09-12: работает
  для программ верхнего уровня, текст попадает в `prog.json` только после
  Ctrl+Shift+S (раньше, видимо, смотрели без сохранения). Дочерние программы
  его не поддерживают (Рецепт 10).
- ~~Трёхмерные массивы, дочерняя программа у дочерней~~ — проверено 2026-09-18:
  массив `[2,2,2]` разворачивается в восемь элементов и компилируется; дочерняя
  `ch_deep,ST,R,child_sq,` создаётся у дочерней, вызывается из неё
  (`child_sq := ch_deep(x);`) и собирается.
- ~~Формат FBD/LD программ внутри `prog.json`~~ — разобран 2026-09-12 (см.
  «Формат FBD-программы»). Инверсия и комментирование связи, комментарии,
  eni/eno, операторы на 3+ входа — разобраны 2026-09-13. Не проверено: язык LD
  (виток, контакт, шина) в работе; ручная трасса (в файле не хранится —
  трасса всегда автоматическая); блоки структуры, функции и дочерней
  программы с параметрами.
- Буквы типов BYTE и DOUBLE в CSV словаря: `Y` и `D` не подходят — такой
  `*.import.csv` роняет IDE при открытии проекта (см. known-issues).
- Пароль и схема шифрования архива `*.ua2`.
