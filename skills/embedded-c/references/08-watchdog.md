# 08. Сторожевой таймер (watchdog)

Аппаратный таймер, который **сбрасывает процессор**, если программа вовремя его не «покормила»
(pet/feed/kick). Он нужен для восстановления после зависания, которое больше ничем не лечится: ошибка в коде,
космическая частица, наводка, отвалившийся провод. Цель — отказ, который приводит систему в безопасное
состояние (fail-safe). Watchdog не заменяет нормальную обработку ошибок.

## Где кормить
**Правило:** в **одном** месте, через которое проходит нормальная работа **всей** системы. Обычно это конец
итерации главного цикла, и только если все подсистемы отчитались, что живы.
```c
static uint32_t s_alive_mask;                 /* each subsystem sets its bit when it made progress */
void alive_report(uint32_t bit) { s_alive_mask |= bit; }

void watchdog_service(void)                   /* called once per main-loop pass */
{
    if ((s_alive_mask & ALIVE_ALL) == ALIVE_ALL) {
        s_alive_mask = 0;
        hw_watchdog_feed();
    }
    /* else: do not feed -> reset if a subsystem is stuck */
}
```
Лучше длинный таймаут, который следит за всей системой, чем короткий, который следит за её частью.

## Где нельзя кормить (антипаттерны)
- **В прерывании таймера**: прерывания продолжаются, даже когда main завис в бесконечном цикле.
  Watchdog никогда не сработает.
- **В функции задержки `delay_ms()`**: задержки разбросаны по коду, и зависание рядом с одной из них
  останется незамеченным.
- **В нескольких «долгих» функциях подряд**: это размывает смысл. Если кормить приходится глубоко в коде,
  значит, это опасное место, и его нужно отдельно проверить на возможность зависнуть.

## Практика
- На время отладки с точками останова watchdog выключают, иначе остановка вызовет сброс. Сделай простой
  способ его отключить и **печатай при старте, включён ли он**, чтобы не забыть включить в продакшене.
- Мигание светодиодом при кормлении — наглядный «пульс» системы.
- После сброса по watchdog причину нужно сохранить и отправить (регистр причины сброса, счётчик
  в памяти, которая переживает сброс). См. `18-debugging-faults.md`.
- Во сне watchdog либо работает (и тогда нужен таймер для пробуждения и кормления), либо засыпает вместе с МК
  (и тогда страховки нет). Это компромисс, решай сознательно.

## ESP8266
- Два сторожа: **программный** (≈ 3,2 с, реализован в ядре на прерывании) и **аппаратный** (≈ 8 с).
  `loop()` должен возвращаться, или долгий код должен вызывать `yield()`/`delay()`. Иначе сброс
  с `rst cause: 4` (hardware WDT) или «Soft WDT reset» в логе.
- `ESP.wdtFeed()` кормит оба. `ESP.wdtDisable()` отключает **только программный**, аппаратный всё равно
  сбросит примерно через 8 с. Не отключай watchdog, чтобы «вылечить» перезагрузки: ищи блокирующий цикл.
- `yield()`/`delay()` нельзя вызывать из ISR и callback-функций `Ticker`.
- Причину сброса даёт `ESP.getResetReason()` / `ESP.getResetInfoPtr()`: печатай её при старте.
