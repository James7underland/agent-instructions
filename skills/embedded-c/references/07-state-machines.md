# 07. Конечные автоматы

Автомат ведёт себя по-разному в зависимости от **состояния** (истории) и **события** (среды).
Любая блок-схема реактивного поведения — это автомат. Стрелки (переходы) важны не меньше кружков.

## Порядок разработки
1. Нарисуй диаграмму: состояния — кружки, переходы — стрелки с событиями.
2. Составь **таблицу состояния × события** и заполни **каждую** клетку: переход, «ничего» или
   «ошибка + лог». Таблица сразу показывает дыры. Пользователь обязательно нажмёт кнопку, которая «в этом
   состоянии не нужна».
3. Реши, как вести себя при недопустимом событии (игнорировать или логировать как ошибку) и при
   испорченном значении состояния (`default:` → безопасное состояние).
4. Каждое внешнее событие асинхронно: обработчик должен быть готов к нему в любом состоянии.
5. Не забудь таймауты: автомат не должен застрять навсегда из-за сломанного датчика.

Пример, светофор: КРАСНЫЙ —go→ ЗЕЛЁНЫЙ —stop→ ЖЁЛТЫЙ —timeout→ КРАСНЫЙ. Тонкость: go в ЖЁЛТОМ не
возвращает в ЗЕЛЁНЫЙ, жёлтый всегда переходит в красный. Хорошо бы добавить короткий «все красные»
между фазами.

## Реализации
**1. По состояниям (`switch (state)`), переходы внутри веток.** Самая распространённая. Каждое состояние знает
соседей.
```c
switch (s_state) {
case ST_GREEN:
    if (ev == EV_STOP) { light_set(LIGHT_YELLOW); timer_start(YELLOW_MS); s_state = ST_YELLOW; }
    break;
case ST_YELLOW:
    if (ev == EV_TIMEOUT) { light_set(LIGHT_RED); s_state = ST_RED; }
    break;
case ST_RED:
    if (ev == EV_GO) { light_set(LIGHT_GREEN); s_state = ST_GREEN; }
    break;
default:
    light_set(LIGHT_RED); s_state = ST_RED;      /* recover to a safe state */
    break;
}
```
**2. Со скрытыми переходами:** состояние делает свою работу и вызывает `next_state()`, а логика «куда»
собрана в одной функции. Хорошо, когда следующее состояние не зависит от события.

**3. По событиям (`switch (event)`, внутри проверка состояния).** Удобно при многих событиях и
малом числе состояний. Периодические проверки (таймауты) делать неудобно — их оформляют как событие «тик».

**4. «Паттерн State»:** каждое состояние — структура указателей на функции `enter/exit/on_go/on_stop/on_tick`.
Контекст хранит указатель на текущее состояние. Нет `switch`, состояния легко тестировать по отдельности.

**5. Табличный:** данные (таблица переходов) плюс универсальный «движок». Лучший выбор при большом числе однотипных
состояний. Таблицу можно генерировать скриптом из CSV, так она и документация, и код.
```c
typedef enum { ST_RED, ST_YELLOW, ST_GREEN, ST_COUNT } state_t;
typedef enum { EV_GO, EV_STOP, EV_TIMEOUT, EV_COUNT } event_t;

typedef struct {
    light_t on_enter;              /* action of the state */
    state_t next[EV_COUNT];        /* transition for each event */
} state_row_t;

static const state_row_t s_table[ST_COUNT] = {
    [ST_RED]    = { LIGHT_RED,    { [EV_GO] = ST_GREEN,  [EV_STOP] = ST_RED,    [EV_TIMEOUT] = ST_RED    } },
    [ST_YELLOW] = { LIGHT_YELLOW, { [EV_GO] = ST_YELLOW, [EV_STOP] = ST_YELLOW, [EV_TIMEOUT] = ST_RED    } },
    [ST_GREEN]  = { LIGHT_GREEN,  { [EV_GO] = ST_GREEN,  [EV_STOP] = ST_YELLOW, [EV_TIMEOUT] = ST_GREEN  } },
};

state_t fsm_step(state_t s, event_t e)
{
    if (s >= ST_COUNT || e >= EV_COUNT) { return ST_RED; }   /* defensive: corrupted input */
    state_t n = s_table[s].next[e];
    if (n != s) { light_set(s_table[n].on_enter); }
    return n;
}
```
Назначенные инициализаторы (C99) защищают от ошибки «сдвинул строку — всё поехало».

## Как выбрать
Меньше кода и меньше дублирования. Если одинаково, то то, что другой человек прочитает быстрее.
Держи состояние отдельно от контекста, тогда каждое состояние тестируется юнит-тестом на ПК.
Автоматы легко превращаются в спагетти, поэтому **документация (диаграмма или таблица) обязательна**.

## ESP8266
Автомат вызывается из `loop()` с событиями от флагов ISR и таймаутами на `millis()`. Никаких `delay()`
внутри состояний: ожидание — это отдельное состояние плюс проверка `millis() - t0 >= T`.
Пример — в `examples/state_machine.c` скилла `embedded-c`.
