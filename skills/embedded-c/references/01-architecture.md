# 01. Архитектура прошивки

## Встраиваемая система — это не «маленький ПК»
Особенности, из которых вытекают все правила ниже:
- ресурсы ограничены: RAM, flash, такты, энергия, периферия; обычно их можно менять одно на другое;
- кросс-компилятор, отладка через JTAG/SWD или только через UART-лог;
- аппаратные точки останова в дефиците, отладчик и `printf` меняют тайминги;
- система живёт годами, её не всегда можно перезагрузить или обновить;
- требования меняются, а прототип на макетной плате — ещё не продукт: нужны обновление, сон,
  watchdog, запас ресурсов, производство.

**Правило:** проектируй под изменения. Раздели систему на модули с узкими интерфейсами и скрытыми данными
(инкапсуляция). Оптимизируй только после того, как работает и измерено: преждевременная оптимизация вредна.

## Четыре взгляда на систему (набросок на бумаге)
1. **Контекстная диаграмма:** устройство в мире — пользователи, сервер, другие устройства, входы и выходы.
2. **Блок-схема:** процессор в центре, внутри блоки интерфейсов (SPI, UART, GPIO), снаружи чипы.
   Интерфейс связи и внешнее устройство — **разные** модули: flash-драйвер использует SPI-драйвер.
3. **Оргдиаграмма (кто кем командует):** `main` → алгоритмы → драйверы. **Общий ресурс**, которым
   командуют двое (например, одна flash для картинок и для серийного номера), — красный флаг:
   нужен арбитраж, и нужно думать о гонках.
4. **Диаграмма слоёв:** размер блока отражает сложность. Блоки, которые всегда используются вместе,
   объединяются в HAL. Ресурс, к которому тянутся все, — кандидат на отдельный модуль-владелец.

## Слои
```
приложение (логика продукта, алгоритмы, автоматы)
сервисы (лог, командный интерфейс, планировщик, хранилище)
драйверы устройств (датчик, дисплей, flash)      ← не знают, какой у нас МК
HAL / драйверы периферии МК (GPIO, SPI, UART, таймер)
регистры МК / SDK производителя
```
**Правило:** зависимость направлена только вниз. Драйвер датчика вызывает `spi_transfer()`,
но не трогает регистры SPI. Регистры видны только в самом нижнем слое.

## Интерфейс драйвера в стиле POSIX
`open/init`, `close/deinit`, `read`, `write`, `ioctl` (всё остальное: частота, режим). Знакомая форма
облегчает понимание и замену. Драйверы складываются в стопку: `display_init()` → `flash_init()` → `spi_init()`.

**Адаптер (adapter):** драйвер переводит «неудобный» интерфейс железа в удобный и стабильный.
Поменяли SPI-flash на I2C-EEPROM — верхний уровень не меняется.
**Фасад (facade):** упрощённый интерфейс поверх сложной подсистемы: `led_init()`, `led_blink()`
вместо манипуляций с портами. Скрывает детали, код читается проще.

## Инициализация модулей
- У каждого модуля свой `xxx_init()`. Модуль сам инициализирует пины и ресурсы, которые использует.
  Исключение — таблица распиновки (см. `03-registers-gpio.md`).
- Верхний модуль инициализирует нижние, от которых зависит.
- Хороший `init` можно безопасно вызвать повторно. Очень хороший возвращает подсистему
  в известное исправное состояние после сбоя.

## «ООП на C»
- **Публичная глобальная переменная** (`int g_x;` + `extern` в `.h`) — источник спагетти, избегай.
- **Приватные данные модуля** — `static` на уровне файла, лучше собранные в одну структуру.
- **Объект** — структура состояния плюс функции, которые принимают указатель на неё
  (`uart_t *u`). Так несколько экземпляров одного драйвера работают независимо.
- **Интерфейс/полиморфизм** — структура указателей на функции (vtable).
- **Синглтон** — единственный экземпляр ресурса (лог, UART отладки) с доступом через функции модуля.
- «Чёрный ход» к приватным данным для тестов: функция, возвращающая указатель на внутреннее состояние,
  закрытая `#if` в продакшене.

```c
/* Interface as a table of function pointers (adapter for any byte stream). */
typedef struct {
    int  (*write)(void *ctx, const uint8_t *data, size_t len);
    int  (*read)(void *ctx, uint8_t *data, size_t len);
    void *ctx;
} byte_stream_t;

/* The logger depends only on the interface, not on UART/USB/RAM. */
void log_init(const byte_stream_t *out);
```

## Внедрение зависимости (dependency injection)
Модулю передают его зависимость как параметр (указатель на функцию или структуру-интерфейс),
вместо того чтобы зашивать её внутрь. Пример: LED-модулю передают «ножку», которую он дёргает.
Плюсы: гибкость во время работы и возможность подсунуть в тестах фейковую реализацию.
Минусы: RAM, такты, сложность. Фасад уменьшает сложность, DI её добавляет — выбирай осознанно.

## Интерфейс логирования
Требования: реализацию можно менять (UART → RAM-буфер → светодиод), фильтр по подсистеме и
уровню важности, глобальное выключение (лог меняет тайминги!).
```c
typedef enum { LOG_SYS, LOG_COMM, LOG_SENSOR, LOG_SUBSYS_COUNT } log_subsys_t;
typedef enum { LOG_DEBUG, LOG_INFO, LOG_WARN, LOG_ERROR, LOG_CRITICAL, LOG_OFF } log_level_t;

void log_msg(log_subsys_t s, log_level_t l, const char *msg);
void log_msg_num(log_subsys_t s, log_level_t l, const char *msg, int32_t num); /* no varargs */
void log_set_level(log_subsys_t s, log_level_t l);
void log_global_enable(bool on);
```
`printf`-подобные функции первыми выкидывают при нехватке памяти, поэтому базовый интерфейс — строка плюс число.

## Версия прошивки
Версия всегда должна быть доступна: печатается при старте и отдаётся по команде. Формат major.minor.build.
Версия нужна и у всего, что обновляется отдельно: формат данных в EEPROM, протокол, ресурсы во flash.
Перед использованием данных проверяй их версию.

## Песочница (MVC для алгоритмов)
Алгоритм (model) не должен знать, откуда берутся данные и куда уходят (view/controller). Тогда его можно
гонять на ПК на записанных данных, повторять одни и те же прогоны и делать регрессионные тесты
(см. `21-testing-on-pc.md`).

## ESP8266 (Arduino)
- `setup()`/`loop()` — это фасад над скрытым `main` ядра: ядро само вызывает `loop()` и между вызовами
  обслуживает Wi-Fi. Слои те же: логика в своих модулях `.c/.cpp` + `.h`, в `main.cpp` только
  вызовы `xxx_init()` и `xxx_poll()`.
- Arduino API (`digitalWrite`, `Serial`) — это уже HAL. Свои драйверы строй поверх него,
  не трогай регистры `GPOS`/`GPOC` без нужды. Если нужно быстро, прячь их за своим фасадом.
- Лог — через свой модуль поверх `Serial`, с возможностью отключить (макрос уровня в `platformio.ini`
  через `build_flags = -DLOG_LEVEL=...`).
