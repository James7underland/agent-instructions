# 06. Главный цикл, события, мини-планировщик, гонки

## Термины
Задача (task) — то, что делает процессор. Поток (thread) — задача со своими ресурсами (стеком).
Процесс — отдельная программа со своей памятью. Без ОС планированием задач занимаешься ты сам.

## Варианты главного цикла (от простого к сложному)
**1. Опрос с задержкой (блокирующий).**
```
init; for(;;) { read_inputs(); write_outputs(); toggle_led(); delay(500); }
```
Прост, но пока идёт `delay`, входы не обрабатываются. Годится только для прототипа.

**2. Таймерное прерывание делает периодическую мелочь, main опрашивает.**
Мигание в ISR таймера, чтение и запись в цикле плюс watchdog. Цикл перестаёт зависеть от мигания.

**3. Прерывания делают всё, main спит.** Разделение отличное, энергопотребление минимальное, но ISR
становятся длинными, а поток выполнения трудно отлаживать.

**4. Прерывания порождают события, main их обрабатывает и засыпает (рекомендуемый вариант).**
```c
#define EV_TICK     (1u << 0)
#define EV_RX_BYTE  (1u << 1)
#define EV_BUTTON   (1u << 2)

static volatile uint32_t s_events;      /* set by ISRs */

void tick_isr(void)   { s_events |= EV_TICK; }     /* RMW inside ISR is fine if ISRs don't nest */

static uint32_t events_take(void)                   /* read-and-clear atomically */
{
    irq_state_t st = irq_save_disable();
    uint32_t ev = s_events;
    s_events = 0;
    irq_restore(st);
    return ev;
}

int main(void)
{
    system_init();
    for (;;) {
        uint32_t ev = events_take();
        if (ev & EV_TICK)    { app_on_tick(); }
        if (ev & EV_RX_BYTE) { cmd_poll(); }
        if (ev & EV_BUTTON)  { app_on_button(); }
        watchdog_feed();
        if (ev == 0) { sleep_until_interrupt(); }   /* see 17-power.md for the race-free version */
    }
}
```
Короткие ISR, порядок обработки задаётся в main, в main можно логировать. Флаги — `volatile`,
изменение из main — в критической секции.

**5. Мини-планировщик по времени** (кооперативный, все задачи в main):
```c
typedef struct {
    void     (*run)(void);
    uint32_t period_ms;
    uint32_t next_ms;
    bool     enabled;
} task_t;

static task_t s_tasks[] = {
    { sensor_task, 100, 0, true },
    { ui_task,      20, 0, true },
};

void scheduler_run(uint32_t now)
{
    for (size_t i = 0; i < ARRAY_LEN(s_tasks); i++) {
        task_t *t = &s_tasks[i];
        if (t->enabled && (int32_t)(now - t->next_ms) >= 0) {
            t->next_ms += t->period_ms;
            t->run();                 /* must return quickly: no preemption */
        }
    }
}
```
Задача, которая выполняется долго, задерживает все остальные. Таймаут watchdog должен покрывать худший
случай, когда все задачи сработали подряд.

**6. Активные объекты (actor) на RTOS:** у каждой задачи своя очередь сообщений и один «насос сообщений»
(`wait message → switch(event)`). Задачи не делят данные, общаются только сообщениями. Это инверсия
управления («не звоните нам, мы сами позвоним»). Так устроены SDK с BLE и Wi-Fi.

Смешивать варианты можно: тик и события плюс отдельное прерывание для срочного.

## Гонки и взаимное исключение
**Критическая секция** — код, который обращается к общему ресурсу (памяти, устройству). Ресурсом должен
владеть один в каждый момент (mutex). Между двумя задачами без ISR хватает флага владения или мьютекса ОС.
Если один из участников — ISR, даже флаг должен меняться атомарно, то есть с запретом прерываний.

Читать тоже опасно: прерывание между чтением «флаг изменился» и чтением «значение» даёт несогласованную пару.

## Инверсия приоритетов
Высокоприоритетный ждёт ресурс, который держит низкоприоритетный, а тот вытеснен среднеприоритетным.
В итоге средний блокирует высокого. На голом железе так бывает, если main запрещает **одно** прерывание
(кнопку), а другое (отладочный вывод) продолжает его вытеснять. **Правило:** в критических секциях запрещай
все прерывания (или все с приоритетом ниже нужного) и держи секции короткими. Спрашивай себя:
«что сейчас самое важное для процессора?»

## ESP8266 (Arduino)
- `loop()` — это вариант 4/5 без сна: пусть каждая итерация быстро возвращается, а работа идёт по
  флагам и `millis()`. Между вызовами `loop()` ядро обслуживает Wi-Fi.
- Задача, которая работает дольше ≈ 50 мс, должна периодически вызывать `yield()` или `delay(0)`
  (не из ISR!). Иначе ломается Wi-Fi, а через ≈ 3 с сработает программный watchdog.
- Своей RTOS в Arduino-ядре ESP8266 нет (это не ESP32), но есть `Ticker` для периодических callback-функций
  (коротких, без `delay`).
