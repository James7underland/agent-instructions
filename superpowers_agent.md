## 🛑 ЭКСПРЕСС-ИНВАРИАНТЫ SUPERPOWERS (GUARDRAILS TOP-5 ДЛЯ НЕЙРОСЕТИ)

1. **Правило 1 % (The 1% Rule):** Если существует хотя бы 1 % вероятности, что специализированный скилл применим к текущей задаче — агент **БЕЗУСЛОВНО ОБЯЗАН** активировать данный скилл. Отказ от использования скилла при наличии подходящего инструмента категорически запрещен.
2. **Инструментальный шлагбаум (Pre-Action Tool Gate):** Проверка и вызов релевантного скилла выполняются **ДО** вывода развернутого ответа, до уточняющих вопросов пользователю, до сканирования файлов и до написания кода.
3. **Беспощадная антирационализация (Red Flags):** При возникновении любой мысли-самооправдания (*«это просто вопрос»*, *«мне сначала нужен контекст»*, *«я только быстро гляну код»*, *«скилл здесь избыточен»*) агент обязан немедленно **ОСТАНОВИТЬСЯ** и задействовать соответствующий скилл.
4. **Приоритет процессов над реализацией (Process Skills First):** Процессные скилы (`brainstorming`, `systematic-debugging`) всегда предшествуют реализационным. Нельзя переходить к коду без исследования замысла (`brainstorming`), и нельзя править баг без локализации первопричины (`systematic-debugging`).
5. **Доказательная верификация (Verification Before Completion):** Запрещено заявлять пользователю о завершении задачи без свежего терминального прогона тестов и предъявления объективных доказательств работоспособности.

## 1. Фундаментальный закон применения скиллов (The Rule)

**Вызывай релевантные или запрошенные скиллы ДО любых действий и ответов** — включая уточняющие вопросы, обход кодовой базы или чтение файлов.

Если в процессе выяснится, что скилл не подходит к ситуации, агент вправе скорректировать маршрут. Но проверка и старт начинаются строго со скилла.

Перед входом в режим планирования: если замысел задачи еще не прошел этап концептуализации — сначала активируется [`brainstorming`](skills/brainstorming/SKILL.md).

При активации агент явно фиксирует вслух или в рассуждениях:
> *«Использую скилл `<имя_скилла>` (например, [`brainstorming`](skills/brainstorming/SKILL.md)) для задачи: <цель>»*
и неукоснительно следует чеклисту скилла.

## 2. Таблица когнитивных самооправданий (Red Flags vs Reality)

Каждая из следующих мыслей означает: **СТОП, ты рационализируешь лень или спешку**:

| Мысль агента (Ловушка) | Реальность (Требование стандарта) |
|---|---|
| *«Это просто короткий вопрос»* | Вопросы — это задачи. Проверь наличие скилла. |
| *«Мне сначала нужно собрать контекст»* | Проверка скиллов выполняется ДО сбора контекста и вопросов. |
| *«Я сначала быстро посмотрю код / git»* | Скиллы регламентируют, КАК именно исследовать код. Сначала открой скилл. |
| *«Для этого не нужен формальный скилл»* | Если специализированный скилл существует — используй его. |
| *«Я помню правила этого скилла по памяти»* | Скиллы развиваются и содержат тонкие детали. Прочти актуальную версию через `view_file`. |
| *«Скилл здесь явно избыточен (overkill)»* | Простые вещи становятся сложными именно из-за пренебрежения дисциплиной. Запусти скилл. |
| *«Я только сделаю это одно действие сначала»* | Проверяй и активируй скилл ДО первого действия. |
| *«Я и так знаю эту концепцию»* | Знать концепцию ≠ дисциплинированно соблюдать пошаговый протокол скилла. |

## 3. Приоритеты и цепочки рабочих процессов

Когда применимы несколько скиллов, **процессные скиллы выполняются первыми** — они задают архитектуру подхода, после чего реализационные скиллы воплощают решение:

```
[Новая задача / Новая функциональность]
   │
   ▼
1. brainstorming (исследование замысла короткими порциями диалога)
   │
   ▼
2. writing-plans (составление детального TDD/YAGNI плана)
   │
   ▼
3. executing-plans / subagent-driven-development (дисциплинированное пошаговое исполнение)
   │
   ▼
4. test-driven-development (цикл Red → Green → Refactor для каждого шага)
   │
   ▼
5. verification-before-completion (контрольная предсдаточная верификация)
   │
   ▼
6. finishing-a-development-branch (чистый мердж или фиксация релиза)
```

```
[Обнаружение бага / Падение тестов]
   │
   ▼
1. systematic-debugging (4 фазы: воспроизведение → локализация первопричины → минимальная правка → проверка)
   │
   ▼
2. test-driven-development (добавление регрессионного теста на баг)
   │
   ▼
3. verification-before-completion (полный прогон тестового набора)
```

## 4. Адаптация под среду разработки (Antigravity & Claude Harness)

1. **Отслеживание задач (Task Tracking):**
   - Для ведения задач в Antigravity поддерживается **Task Artifact**: markdown-чеклист, создаваемый и обновляемый через инструменты артефактов (`write_to_file` с `IsArtifact: true`, редактирование через `replace_file_content` / `multi_replace_file_content`).
   - По мере завершения каждого пункта чеклиста статус немедленно отмечается как выполненный (`- [x]`).
2. **Делегирование задач (Subagent Dispatching):**
   - При выполнении независимых исследовательских подзадач или изоляции изменений используется `invoke_subagent` с соответствующим типом (`self` для полной разработки, `research` для аналитического чтения).
3. **Строгая верификация в терминале:**
   - Перед завершением любой итерации агент обязан выполнить реальный запуск тестов через `run_command` и убедиться в 100 % зеленом статусе.
